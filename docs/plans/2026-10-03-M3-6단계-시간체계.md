# M3 6단계 — 시간 체계 (Fischer 게임 시계 · 접속 시계 · 데드라인 스위퍼 · 서버 유예 · 무효 처리)

## Context

ROADMAP M3 실행 순서 6단계. 지금 게임에는 **시간이 없다.** 차례인 플레이어가 영원히 생각할 수 있고, 끊긴 플레이어가
돌아오지 않아도 게임이 멈춘 채 남는다. 매칭 ready 기한(`ready_deadline_ms`)도 기록만 되고 아무도 감지하지 않는다
(`expire_match` 는 호출자가 없다). `eliminate(seat_no)` 도 "6단계 스위퍼 전용"으로 비어 있다.

6단계는 maze.md §8·§9 를 서버 권위로 구현한다.

- **두 시계 완전 분리** — Fischer 게임 시계(자기 차례에만, 수락 시 +증분)와 접속 시계(끊긴 동안만, 게임당 누적 60 s, 리셋 없음)
- **데드라인 ZSET + 스위퍼** — 게임 시계·접속 시계·매치 ready 만료를 워커 몇 개가 돌든 **정확히 한 번** 처리
- **서버 유예** — 배포(정상 종료)로 끊긴 좌석은 최대 30 s 동안 두 시계 정지. 크래시는 면제 없음
- **장애 처리** — Redis 장애 구간은 시계에서 빼고, 상한을 넘으면 무효. Redis 상태 유실은 `void_lost_game(server_fault)`

**진행 규칙 (사용자 지시, 2026-10-04):** 2.5단계 보류는 예외다 — 이 단계의 전제로 인용하지 않는다. **각 커밋은 검증을 마친 뒤에만
다음으로 넘어간다**(아래 "커밋별 검증 관문"). 그리고 마무리에 **구현 과정을 모르는 별도 상위모델의 독립 검토**를 거친다(커밋 6).
두 규칙은 이 단계 한정이 아니라 **모든 단계 공통**이므로, 승인 직후 첫 작업으로 메모리(feedback)에 저장한다 — 플랜 모드에서는
계획서 외 파일을 쓸 수 없어 미뤘다.

**사용자 결정 (2026-10-03, 이 계획 수립 중):**
1. 긴 Redis 장애 — **장애 구간을 두 시계에서 제외 + 상한 초과 시 무효** (maze.md §8 미결 1건 확정)
2. 스위퍼 동시성 검증 — **프로세스 내 동시 실행 + 장애 주입**. 실제 프로세스 2개 확인은 7단계 완료 판정에 넣는다

## 판단 1 — 시각의 출처: Redis `TIME` (주입 가능한 시계)

"워커가 2개면 무엇이 깨지는가?" — 워커마다 벽시계가 다르면(다른 호스트, 롤링 배포) 같은 게임의 차감이 워커에 따라 달라진다.
**시각은 Redis `TIME` 하나로 읽는다.** 모든 워커가 같은 시계를 본다. 비용은 행동당 왕복 1회(≈0.3 ms, E6 p99 2 ms 안).

```python
# app/core/time.py
class Clock(Protocol):
    async def now_ms(self) -> int: ...

class RedisClock:          # 기본값 — require_redis().time()
class FakeClock:           # tests 전용(tests/conftest.py) — set(ms)/advance(ms), sleep 없음
```

- 게임 서비스·매치메이킹·스위퍼가 `clock: Clock` 을 생성자로 받는다. 시각은 **락을 잡은 뒤** 한 번 읽어 그 처리 전체에 쓴다
- 클라이언트 시각은 어디에도 들어오지 않는다. 서비스 메서드 서명에 시각 인자가 없다(테스트로 고정)
- 매치메이킹의 큐 입장 점수(`_now_ms`)는 정렬용이라 그대로 두고, **ready 기한만** 주입 시계로 바꾼다(ZSET 비교 대상이므로)

## 판단 2 — 시계 상태: `game:{id}:clocks` STRING, state 와 같은 펜싱 쓰기 한 번

엔진(`GameState`)에 넣지 않는다 — 엔진은 프레임워크·시간 무의존이고 `schema_version` 을 건드리지 않는다. 순수 계산은
새 모듈 `app/services/maze_clock.py`(Redis 무의존)에 둔다.

```json
{ "v": 1,
  "turn_started_at_ms": 1759480000000,
  "stopped_at_ms": null,
  "seats": [
    { "seat_no": 1, "remaining_ms": 300000, "conn_remaining_ms": 60000,
      "disconnected_at_ms": null, "grace_from_ms": null, "grace_until_ms": null } ] }
```

**지연 정산(lazy settlement).** 저장하는 것은 "마지막으로 정산한 시점의 잔량 + 흐르기 시작한 시각"뿐이다. 임의 시각 t 의 잔량은

```
게임 시계(현재 차례 좌석) = remaining_ms      − charged(turn_started_at_ms, t)
접속 시계(끊긴 좌석)      = conn_remaining_ms − charged(disconnected_at_ms, t)
charged(a, b) = (b − a) − |[a, b] ∩ 면제 구간|      면제 = 그 좌석의 서버 유예 [grace_from, grace_until] ∪ 전역 장애 구간(판단 7)
```

| 사건 (모두 게임 락 안, 시각 = 판단 1) | 시계 갱신 |
| :--- | :--- |
| 게임 생성 | 전원 `remaining=clock_initial_ms`, `conn=connection_budget_ms`, 연결됨. `turn_started=now` |
| 이동·벽 **수락** | 행위자 `remaining −= charged(turn_started, now)`, `+= clock_increment_ms`. 다음 좌석 `turn_started=now` |
| 벽 **거절** | 없음 — 행위자의 시계는 계속 흐른다(§8 "경과분만큼은 자연히 줄어든다") |
| 현재 차례 좌석 탈락(항복·만료) | 그 좌석 `remaining −= charged(…)`(증분 없음), 다음 생존자 `turn_started=now` |
| 차례 아닌 좌석 탈락 | 게임 시계 변화 없음 |
| 탈락 좌석 전부 | 두 시계 정지(정산 후 동결), 데드라인 제거(§9 탈락 처리 3번) |
| 게임 종료 | 전원 정산, `stopped_at_ms=now`, 그 게임 데드라인 전부 제거 |

- **쓰기:** state·vision 과 **같은 Lua 한 번**(판단 4). 나눠 쓰면 장애 시 "턴은 넘어갔는데 시계는 이전 턴" 이 남아 이중 차감이 된다
- **이중 차감 없음의 근거:** 차감은 저장된 시작 시각에서 now 까지를 정산하고 시작 시각을 now 로 옮기는 연산이다. 게임 락 + 펜싱으로
  직렬화되므로 두 워커가 같은 구간을 두 번 정산할 수 없고, 락을 잃은 쪽은 아무것도 쓰지 못한다(`GameBusy`)
- 인원 수를 쓰지 않는다 — `seats[]` 는 좌석 목록에서 만든다

## 판단 3 — 만료 판정: 락 안의 재계산이 권위, ZSET 은 색인일 뿐

`settle(state, clocks, now, outages)` 가 now 시점에 소진된 좌석을 **소진 시각 순**(동률은 seat_no)으로 돌려주고, 호출자가
엔진 `eliminate(seat, time_forfeit | disconnect_forfeit)` 를 그 순서로 적용한다(탈락 순번 = 순위 근거).

- **어디서 부르는가:** 모든 `_act`(행동·항복·스위퍼·끊김·재접속)의 맨 앞. §8 "지연 보정 — 행동 수신 시에도 데드라인을 비교해 이미
  지났으면 만료를 먼저 처리" 가 이것이다. 행위자 본인이 그로 인해 탈락했으면 `not_in_game` 으로 거절한다
- **현재 차례 좌석이 시간패면 다음 좌석의 시계는 `now`(처리 시각)부터 흐른다** — 소진 시각부터가 아니다. 감지 지연(스위퍼 주기·장애)을
  다음 플레이어에게 물리지 않는다
- **ZSET 점수는 힌트다.** 스위퍼가 꺼낸 후보도 락 안에서 다시 계산해 아직 소진 전이면 아무것도 탈락시키지 않고 **올바른 데드라인으로
  다시 적는다.** 그래서 ZSET 점수가 낡아도(서버 유예·장애 구간이 나중에 기록돼도) 결과는 틀리지 않는다

## 판단 4 — 데드라인 ZSET: `deadlines:{game}`, 시계와 같은 Lua 로 갱신

| 요소 | 결정 |
| :--- | :--- |
| 키 | **`deadlines:{game}`** (예: `deadlines:maze_1p`). 예약 이름 `{game}:deadlines` 를 고친다 — 다른 키와 같은 "종류:식별자" 형태가 되고, 테스트 정리 접두어(`PREFIXES`)에 `deadlines:` 하나로 들어간다 |
| member | `clock:<game_id>` (현재 차례 게임 시계, 게임당 **항상 하나**) / `grace:<game_id>:<seat_no>` (끊긴 생존 좌석마다) / `ready:<match_id>` (매치 ready 기한) — §8 표 그대로 + ready |
| score | 소진 예정 시각(epoch ms, Redis TIME 기준) = 시작 + 잔량 + 그 사이 알려진 면제 |
| 게임 쪽 갱신 | `redis_lock.fenced_write(…, zset=…, zadd={member: score}, zrem=[…])` — **state·vision·clocks 와 같은 Lua.** 토큰이 내 것이 아니면 ZSET 도 건드리지 않는다. `fenced_mset` 은 이것에 위임(동작 동일) |
| 생성 | `create_game` 의 MULTI 에 `clocks` SET + `ZADD clock:<id>` |
| 매치 쪽 갱신 | `try_match` 가 매치 SET 과 `ZADD ready:<id>` 를 MULTI 한 번으로, `mark_ready`(전원 준비)·`expire_match` 가 `ZREM` |

> ZADD 를 펜싱 쓰기 밖에서 따로 하면 그 사이 장애로 "턴은 바뀌었는데 데드라인이 없다" → **그 게임은 영원히 멈춘다.** 같은 Lua 에 넣어
> 전부 또는 전무로 만든다(5단계 vision 과 같은 논리).

## 판단 5 — 스위퍼: 워커마다, 리스(lease) 클레임 + 락 안 재검사 (리더 없음)

maze.md §8 은 "후보마다 `ZREM` 반환값 1인 워커만 처리" 로 적었다. **그대로 하면 ZREM 직후 그 워커가 죽을 때 데드라인이 사라지고
게임이 영원히 멈춘다**(크래시는 E2 에서 실재한다). 그래서 지우지 않고 **빌린다.**

```lua
-- KEYS[1]=deadlines / ARGV: now, lease_until, limit
local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[3])
for _, m in ipairs(due) do redis.call('ZADD', KEYS[1], 'XX', ARGV[2], m) end
return due
```

- **이중 처리 없음 (두 겹):** ① 클레임은 Lua 한 번이라 같은 리스 창에서 두 워커가 같은 member 를 받지 못한다 ② 그래도(리스 만료 후 재클레임 등)
  처리는 게임 락 안에서 판단 3 의 재계산으로 한다 — 이미 탈락한 좌석은 다시 탈락하지 않고, 소진 전이면 아무 일도 없다. **정확성은 ②가 보장하고
  ①은 경합을 줄일 뿐이다**
- **누락 없음:** 처리한 쪽이 펜싱 쓰기로 점수를 실제 데드라인으로 덮거나 지운다. 처리 전에 죽으면 `lease_until`(=`now + sweeper_claim_lease_ms`)
  에 member 가 다시 나타나 다른 워커가 처리한다
- **처리 경로:** `clock:`·`grace:` → `maze_games.expire(game_id)`(= `_act` 의 정산 전용 경로, 같은 락·같은 쓰기·같은 발행). `ready:` →
  `matchmaking.expire_match(match_id)` — 매치 락 안에서 **기한이 아직이면** 실제 기한으로 다시 ZADD 하고 끝낸다(검사 추가). 게임 상태가 없으면
  member 를 지운다(유실 판정은 판단 8 몫)
- **주기·묶음:** `sweeper_interval_ms`(1000) 마다 `sweeper_batch`(100)개. 항목 하나의 실패는 로그만 남기고 다음으로 간다(리스가 재시도를 보장)
- **위치:** `app/services/sweeper.py` `DeadlineSweeper(games, matches, clock, …)` — `tick()` 이 한 회차, `start()/stop()` 이 루프.
  프로세스 로컬 상태는 태스크 핸들과 장애 관측(판단 7)뿐이다. **lifespan 배선은 7단계**(경계 표)
- **실측 하네스를 만들지 않는 근거 (사용자 결정 2):** 이 선택은 런타임 동작(분배·지연)이 아니라 Redis 스크립트 원자성과 게임 락(E6 에서
  정확성 확인)에 기댄다. 프로세스 내에서 연결이 다른 스위퍼 둘을 `gather` 로 동시에 돌리면 Redis 수준의 인터리빙은 실제와 같다. 프로세스
  경계는 7단계 `--workers 2` 완료 판정에서 확인한다

## 판단 6 — 끊김 신호의 경계: 6단계는 서비스 진입점까지, 소켓은 7단계

| 진입점 (6단계, `MazeGameService`) | 하는 일 | 부르는 쪽 (7단계) |
| :--- | :--- | :--- |
| `mark_disconnected(game_id, user_id) -> DisconnectOutcome` | 락 안 정산 → 생존·연결 중이면 `disconnected_at=now`, `ZADD grace:` → `seat_disconnected` 발행(hint: `seat_no`, `grace_remaining_ms`). 이미 끊김이면 아무것도 안 한다(시작 시각을 덮지 않는다) | 소켓 종료(ping 타임아웃 포함, `--ws-ping-*`) |
| `mark_connected(game_id, user_id)` | 락 안 정산 → 끊긴 구간 차감, `disconnected_at=None`, 서버 유예 창을 `now` 로 자른다, `ZREM grace:` → `seat_reconnected` 발행 | 재접속 수락 직후, `resync` 전 |
| 행동(`move`·`place_wall`·`surrender`) | 행위자가 끊김 상태로 기록돼 있으면 **먼저 재접속으로 처리**한 뒤 판정한다 — 행동을 보냈다는 것이 연결의 증거다 | 핸들러 |
| `apply_server_grace(entries, shutdown_at_ms)` | 판단 7 | lifespan shutdown |

- `user_id` 만 받는다. 좌석은 `meta.seat_of`(5단계 판단 9 유지). 같은 `user_id` 의 연결 교체(4000)는 끊김이 아니다 — 7단계가 새 연결 등록 후
  옛 소켓 종료에서 `mark_disconnected` 를 부르지 않도록 해야 한다(경계 표)
- **조작 경로 점검:** 클라이언트가 할 수 있는 것은 "끊기/붙기" 뿐이다. 접속 시계는 리셋되지 않고(누적 차감만), 끊김 중에도 자기 차례면
  게임 시계가 같이 흐른다(§8 "양쪽에서 손해"). 붙은 상태에서 `mark_connected` 반복은 no-op. 서버 유예는 판단 7 처럼 **서버 종료로만** 걸린다

## 판단 7 — 서버 유예: 소급 적용 (E3 순서 전제)

maze.md §8: 판별은 "서버 프로세스가 종료 단계에 들어갔는가"로만, close code 1012 는 쓰지 않는다, 소켓이 먼저 닫히고 lifespan 이 나중이다.

1. 끊김은 언제나 **일반 끊김**으로 기록한다(`mark_disconnected`). 핸들러는 그 사실을 워커 로컬 `RecentDisconnects`(`app/ws/server_grace.py`,
   `(game_id, user_id, disconnected_at_ms)` 를 짧게 보관)에도 남긴다
2. lifespan shutdown 이 `shutdown_at = now` 를 읽고 `apply_server_grace(recent.since(shutdown_at − server_grace_window_ms), shutdown_at)` 를 부른다
3. 서비스는 좌석마다 락 안에서 **그 좌석이 아직 같은 `disconnected_at` 으로 끊겨 있을 때만** `grace_from = disconnected_at`,
   `grace_until = disconnected_at + server_grace_max_ms` 로 두고 데드라인을 다시 적는다. 지연 정산이라 소급이 정확하다 — 그 사이 차감된 것이 없다

| 질문 | 답 |
| :--- | :--- |
| 무엇이 멈추나 | 그 좌석의 접속 시계와(자기 차례면) 게임 시계. 다른 좌석은 계속 진행한다 — 다른 워커에 붙은 좌석의 행동도 정상 처리 |
| 유예 중 들어온 행동 | 유예 좌석 본인의 행동은 재접속 후에만 가능하다(행동 = 재접속, 판단 6) → 창이 `now` 에서 잘리고 정상 판정. 남의 행동은 그대로 처리되고, 차례가 유예 좌석으로 넘어가면 그 좌석 게임 시계는 창 끝까지 멈춘다 |
| 상한 | 창이 `server_grace_max_ms`(30 s)에서 끝난다. 그 뒤로는 일반 끊김처럼 두 시계가 흐른다 — 별도 데드라인 없이 판단 2 의 식이 처리 |
| 크래시 | lifespan 이 돌지 않으므로 면제 없음(§8 그대로) |
| 창(window) 오탐 | 종료 직전 `server_grace_window_ms`(2 s) 안에 **우연히** 끊긴 좌석도 면제된다. 클라이언트가 배포 시각을 알 수 없어 악용 경로가 아니고, 이득은 ≤30 s 한 번이다. close code 로 거르지 않는다 — 설계서가 금지한다 |
| 종료 중인 인스턴스로 재접속(E4) | 그 워커도 종료하면서 자기 끊김에 같은 처리를 한다. 이미 재접속(`mark_connected`)으로 끊김 시각이 바뀐 좌석은 3번의 비교에서 빠진다 |

## 판단 8 — Redis 장애와 상태 유실 (사용자 결정 1)

**장애 구간 기록.** 스위퍼 루프가 장애를 관측한다(Redis 예외로 실패한 회차가 있었을 때만 — 워커 정지와 구분).
복구 후 첫 성공 회차에서 `[last_ok + (첫 실패 − last_ok 의 단조 시계 차), 복구 시각]` 을 `store:outages` ZSET(member `"<start>-<end>"`,
score = end)에 넣는다. 여러 워커가 같은 장애를 조금씩 다르게 적어도 **합집합**으로 쓰므로 무해하다.
`store_outage_min_ms`(3000) 미만은 적지 않는다(주기 지터). `outage_retention_sec` 지난 구간은 지운다.

| 장애 길이 | 처리 |
| :--- | :--- |
| < `store_outage_min_ms` | 아무것도 안 한다 (E7 의 ≈2 s 재시작) |
| ≥ min, < `store_outage_void_sec`(120) | 판단 2 의 면제 구간에 들어간다 — 두 시계 모두 그 구간을 차감하지 않는다. ZSET 점수는 낡지만 판단 3 이 재계산한다 |
| ≥ `store_outage_void_sec` | 장애를 기록한 워커가 그 시점의 진행 중 게임(`deadlines:{game}` 의 `clock:` member = 진행 중 게임 전부, 장애 종료 전에 생성된 것)을 **무효**로 닫는다 — `void_game(game_id)`: 게임 락 안에서 상태가 아직 진행 중일 때만 → DB void → `game_voided` 발행 → activity 해제 → 키 삭제. 두 번째 워커는 상태가 없어 no-op |

**상태 유실 감지.** `lost_scan_interval_sec`(30) 마다, `deadlines:{game}:scan` 락(SET NX PX)을 잡은 워커 하나가 DB `list_in_progress()` 를
읽어 **생성 후 `lost_game_min_age_sec`(30) 지난** 게임 중 `game:{id}:state` 가 없는 것에 `void_lost_game` 을 부른다.

- 나이 조건: 생성은 DB → Redis 순서라 생성 직후의 "DB 진행 중 + Redis 없음"은 정상이다
- Redis 가 통째로 비면 ZSET 도 사라진다 — 그래서 ZSET 이 아니라 **DB 가 출처**다
- `void_lost_game` 을 **멱등으로** 고친다: 게임 락 안에서 상태 부재를 다시 확인하고, `_void_record` 가 실제로 void 했을 때만 발행한다
- DB 접근은 주입한다(`in_progress_source`) — 테스트는 DB 픽스처 없이 가짜 출처를 쓴다
- **알려진 한계:** 종료 시 DB 결과 기록이 실패한 게임(`_finalize` 로그만)은 TTL(300 s) 뒤 이 스캔이 void 로 닫는다. 영원히 "진행 중"으로 남는 것보다
  낫고, 재시도는 범위 밖이다(의도적 제외)

## 판단 9 — 시계의 공개와 시야

- 좌석별 화면(`game_view`)에 `clocks` 를 붙인다: `{seats: [{seat_no, remaining_ms, connection_remaining_ms, connected}], current_expires_at_ms}`.
  **필드 이름은 잠정**(§12 `turn_change.clocks`·`clock_expires_at` 확정은 7단계). 값은 조회 시각 기준 지연 정산 결과
- 이벤트 hint 에 추가하는 것: `seat_disconnected`·`seat_reconnected` 의 `seat_no`·`grace_remaining_ms`, 시간패 `last_action.reason`. **좌표·벽·시야 없음**
- **시야 누출 점검:** 남의 시계 잔량·접속 여부는 §8 이 명시한 공개 정보다. 잔량의 변화가 드러내는 것은 "언제 행동했나"뿐이고 그것은
  이미 `last_action` 으로 공개된다. 위치·벽과 결합되는 값이 없다. 탈락 좌석 화면도 같은 `clocks` 를 받는다(5단계 동결은 시야 필드에만)

## 실행 비용

장시간 연산은 없다. 시간 의존 테스트는 전부 `FakeClock` 으로 즉시 진행하고 **실제 sleep 으로 만료를 기다리지 않는다**(스위퍼 루프 `start/stop`
1건만 짧은 주기로 수십 ms). **DB 픽스처는 쓰지 않는다.**

| 검증 | 규모 | 건당 | 추정 |
| :--- | :--- | :--- | :--- |
| 순수 시계 | ≈ 30건 (일부 × 3 모드) | < 1 ms | ≈ 0.1 s |
| 서비스·매치 | ≈ 30건 × Redis 왕복 수십 회 | ≈ 30–50 ms | ≈ 1.5 s |
| 스위퍼 | ≈ 20건, 동시 테스트 1건은 게임 20개 생성 | ≈ 50 ms / 동시 ≈ 1 s | ≈ 2 s |
| 화면·버스 | ≈ 6건 | ≈ 50 ms | ≈ 0.3 s |

- **추정: +≈85건, +4~6 s → 전체 ≈ 122 s** (기준선 ≈ 116 s / 494건)
- **기준선:** 커밋 1 전에 `server-test` 를 한 번 재서 커밋 메시지에 적는다
- **중단 조건:** 새 테스트 파일 하나가 단독 10 s 를 넘거나 전체가 기준선 + 30 s 를 넘으면 멈춘다 → 동시 테스트 게임 수(20 → 5)·모드 파라미터를
  줄인다. 그래도 넘으면 원인을 보고하고 묻는다
