# M3 4단계 — 워커 간 전달을 Pub/Sub 으로

> 착수할 때 `2026-10-02-M3-4단계-PubSub.md` 로 이름을 바꾸고 `**상태: 진행 중**` 머리글을 붙인다.
> 커밋 0(비밀번호 기본값 제거)은 이 계획 중에 사용자가 결정했고(2026-10-02, GitGuardian 경보), 4단계보다 먼저 실행한다.

## Context

ROADMAP M3 실행 순서 4단계. 3단계에서 큐·방·게임 상태를 Redis 로 옮겼고, 서비스는 결과(`ActionOutcome`·
`PendingMatch`·`ExpireResult`·`Room`/`LeaveResult`)를 **반환만** 한다. 남은 문제는 두 가지다.

- **알림 전달.** 같은 게임의 좌석들이 서로 다른 워커에 붙어 있으면, 행동을 받은 워커는 다른 워커의 소켓에 보낼 수 없다
- **소속 정보가 로컬에 있다.** `connection_manager._game_players`·`_room_players` 는 프로세스 안의 dict 다. 워커가 2개면 각자 다른 일부만 안다

4단계는 서비스 결과를 Redis Pub/Sub 으로 발행하고, 각 워커가 구독해서 **자기 프로세스의 소켓에만** 전달하게 한다.
소켓 객체와 연결 맵(`user_id → 소켓`)은 프로세스 안에 남는다. 누가 어느 게임·방에 속하는지는 Redis 를 권위로 삼는다.

**전제 (ROADMAP 2.5단계 보류 인용문):** 검증 없이 진행하고, 문제가 생기면 교체·수정으로 대응한다. 단계마다 테스트 전체 통과는 지킨다.

## 판단 1 — 구독 모델: 워커당 패턴 구독 1개

각 워커는 **기동할 때 패턴 구독 하나**(`PSUBSCRIBE <ns>:game:*:events <ns>:room:*:events <ns>:match:*:events`)만 연다.
게임이나 방이 생길 때마다 구독하고 해지하지 않는다.

| | 패턴 구독 (채택) | 게임·방마다 동적 SUBSCRIBE |
| :--- | :--- | :--- |
| 워커가 2개면 깨지는 것 | 없음 | 유저가 워커 B 에 붙은 직후, B 의 SUBSCRIBE 가 끝나기 전에 발행된 메시지를 잃는다. 이걸 막으려면 연결마다 재동기화해야 한다 |
| 로컬 상태 | 연결 맵 하나 | 채널별 참조 카운트(사실상 `_game_players` 의 부활) |
| 재연결 시 복구 | 패턴 1개만 다시 구독 | 채널 목록 전체를 다시 구독 |
| 비용 | 모든 이벤트가 모든 워커에 간다. 턴제라 이벤트가 적고(행동당 1건), 워커 수는 2~4개다 | 필요한 워커만 받는다 |

채널을 게임·방 단위로 나눠 두는 이유는, 팬아웃이 커지면 구독 쪽만 동적 SUBSCRIBE 로 바꿀 수 있게 하기 위해서다.
발행 쪽은 그대로 둔다. 예약된 `game:{id}:events` 이름도 그대로 쓴다.

**채널 네임스페이스:** 채널 이름 앞에 `db{n}:` 를 붙인다. `n` 은 `settings.redis_url` 의 논리 DB 번호다.
테스트(DB 1)와 개발 서버(DB 0)가 같은 Redis 를 쓰므로, 접두어가 없으면 테스트 이벤트가 개발 서버 소켓으로 간다(위 사실).
환경변수를 새로 만들지 않고 이미 있는 DB 번호에서 파생한다.

## 판단 2 — 이벤트 봉투: 수신자 목록 + 공개 힌트, 권위는 없다

```python
@dataclass(frozen=True)
class Event:
    kind: str                  # 아래 표
    scope: str                 # "game" | "match" | "room"
    scope_id: str              # game_id | match_id | room code
    recipients: tuple[int, ...]  # 사람 user_id. 발행자가 락 안에서 Redis 로 읽은 값
    hint: dict                 # 공개 정보만. 좌표·전체 상태는 넣지 않는다
    seq: int                   # game: turn_count, 그 외 0 — 수신 측이 낡은 이벤트를 알아보는 용도
```

- **수신자는 발행자가 정한다.** 발행자는 방금 락 안에서 Redis 를 읽었으므로 그 목록이 권위 있는 값이다. 수신 워커가 Redis 를
  다시 읽으면 그 사이에 바뀔 수 있고(방 해산이면 키가 이미 없다), 이벤트마다 워커 수만큼 GET 이 늘어난다.
  연결 맵은 이 목록과 교집합을 구하는 데만 쓴다
- **권위를 싣지 않는다.** 게임 이벤트를 받은 워커는 상태를 Redis 에서 다시 읽어 좌석별 화면(판단 4)을 만든다. 이벤트를 잃어도
  다음 이벤트나 재동기화가 최신 상태를 보내므로 결과는 수렴한다
- **힌트는 공개 정보만 담는다.** `last_action{seat_no, kind}`, 방 스냅샷(방은 비밀이 없다), 매치 좌석(닉네임·seat_no) 정도다.
  **게임 상태·좌표는 어떤 필드에도 넣지 않는다**(§6 MUST NOT — 채널은 모든 워커에 간다)

| 출처 (서비스 결과) | 채널 | kind | 수신자 | hint |
| :--- | :--- | :--- | :--- | :--- |
| `MazeGameService.create_game` | `game:{id}:events` | `game_started` | meta 의 사람 좌석 | `mode`, `players[{seat_no, nickname, is_ai}]` |
| `_act` — 수락된 행동 (`rejection is None`) | 〃 | `game_updated` | 〃 | `last_action{seat_no, kind: move\|wall\|eliminated, reason?}`, `ended` |
| `_act` — 거절 | 발행 안 함 | — | — | 거절은 행동한 사람에게만 응답한다(핸들러, 7단계). `wall_rejections` 는 남들에게 보이지 않는다 |
| `void_lost_game` | 〃 | `game_voided` | 〃 | — |
| `Matchmaking.try_match` (join·expire 경유) | `match:{id}:events` | `matched` | 매치 좌석 | `players[{seat_no, nickname}]`, `ready_deadline_ms` |
| `mark_ready` (아직 다 안 모임) | 〃 | `match_ready` | 〃 | `seat_no` |
| `expire_match` | 〃 | `match_expired` | requeued + dropped | `requeued`, `dropped` |
| `Rooms.create/join/leave(게스트)/set_ready(시작 전)` | `room:{code}:events` | `room_updated` | `room.user_ids` (+ 떠난 사람) | 방 스냅샷 |
| `leave_room` (호스트 → 해산) | 〃 | `room_dissolved` | `notify_user_ids` | `code` |

게임 시작은 `create_game` 이 한 번만 발행한다. 매치·방 쪽에서 따로 발행하지 않는다(출처는 하나).

## 판단 3 — 발행 위치: 서비스 안, 상태를 쓴 직후(락 안)

서비스가 `publisher` 를 주입받아(`MazeGameService(session_factory, publisher=…)`, `Matchmaking(…, publisher=…)`,
`Rooms(…, publisher=…)`) 상태를 쓴 바로 뒤에 발행한다.

- **누락을 막는다.** 6단계 스위퍼(`eliminate`, `expire_match`)와 7단계 핸들러가 같은 진입점을 부르므로 발행을 잊을 수 없다.
  핸들러가 발행을 맡으면 스위퍼에도 같은 코드가 한 벌 더 필요하다
- **락 안에서 발행한다.** 같은 게임의 이벤트가 상태 순서대로 나간다. 비용은 PUBLISH 1회(≈1 ms, E5)다
- **발행 실패가 행동을 실패시키지 않는다.** at-most-once 라 어차피 잃을 수 있고, 상태는 이미 Redis 에 기록됐다.
  `RedisError` 는 로그만 남긴다(재동기화가 복구한다). 진입 가드는 그대로 `require_redis()` 다
- 3단계 `maze_game.py` docstring 의 "메시지 전송은 하지 않는다"는 "발행만 한다. 소켓 전송은 ws 계층" 으로 고친다
- 계층 방향: `app/services/events.py`(이벤트 정의·발행)는 services 에, 구독·전달은 `app/ws/` 에 둔다. services 는 ws 를 import 하지 않는다

## 판단 4 — 플레이어별 개별 전송의 자리 (§6 필터)

`app/services/maze_view.py` — `async def game_view(game_id, user_id) -> dict | None`

- 락 없이 state·meta 스냅샷을 읽는다(meta 는 불변이고 state 는 단일 키 GET). 좌석이 아니면 `None` 이다
- §6 패킷 모양으로 만든다: `game_id`, `turn_count`, `current_seat_no`, `me{seat_no, position, walls_remaining, goals}`,
  `others[{seat_no, nickname, walls_remaining, eliminated, visible}]`
- 시야 필드(`discovered_edges`·`visible_edges`·`visible_players`·`last_seen_players`)는 **`vision_fields(state, seat_no)` 한 함수**에서
  받는다. 4단계 구현은 빈 목록과 `visible: false` 를 돌려준다. 시야 계산은 5단계에서 이 함수만 바꾼다
- 4단계의 기본값은 **덜 보여 주는 쪽**이다. 시야가 없어서 게임 화면이 불완전한 것은 감수한다. 그래도 남의 좌표나 벽을
  흘리지 않는다(§6 MUST NOT). 테스트로 고정한다

## 판단 5 — 구독 계층 (`app/ws/bus.py`) 과 재동기화

```python
class EventBus:
    def __init__(self, manager: ConnectionManager, deliver: Deliver, resync: Resync): ...
    async def start(self) -> None      # psubscribe + 수신 루프 태스크
    async def stop(self) -> None
    @property
    def subscribed(self) -> bool        # 7단계 /health 보고용
```

- **수신 루프:** 메시지마다 `Event` 를 디코드한다. `recipients ∩ manager.local_user_ids()` 의 유저마다 `deliver(event, user_id)` 가
  만든 메시지들을 `send_personal` 로 보낸다. 디코드에 실패하면 로그를 남기고 건너뛴다(루프를 죽이지 않는다)
- **끊김:** `ConnectionError`/`RedisError` 가 나면 새 PubSub 으로 다시 구독한다. 대기는 지수 백오프
  (`pubsub_reconnect_min_ms`=100 → `pubsub_reconnect_max_ms`=5000)다. **재구독에 성공한 직후** 그 시점의 로컬 유저 전원에게
  `resync(user_id)` 를 보낸다(E5)
- **`resync(user_id)`** (`app/ws/delivery.py`): `user:{uid}:activity` 를 읽고 종류에 따라 현재 상태를 보낸다 — `game` 이면 `game_view`,
  `room` 이면 방 스냅샷, `match` 면 매치 스냅샷, `queue` 면 `QueueStatus`. 7단계의 재접속 직후 동기화도 이 함수를 그대로 쓴다
- **`deliver(event, user_id)`** (`app/ws/delivery.py`): `game_*` 이벤트는 `game_view` 로 좌석별 상태를 붙이고(판단 4), 나머지는
  hint 를 그대로 보낸다. **와이어 페이로드(§12 필드 이름)는 이 단계에서 확정하지 않는다** — 타입 이름만 §12 를 따르고,
  필드는 7단계 핸들러를 쓸 때 맞춘다
- 전송은 루프 안에서 순서대로 한다. 소켓 하나가 느려 전체가 막히는 문제는 아래 "의도적으로 제외"에 적었다

## 판단 6 — `connection_manager` 정리

남기는 것: `connect`, `disconnect`, `get_connection`, `is_connected`, `send_personal`, `broadcast`, `local_user_ids()`(신규), `get_stats`(연결 수만).

지우는 것: `_game_players`, `_room_players`, `join_game`/`leave_game`/`get_game_players`, `join_room`/`leave_room`/`get_room_players`,
`send_to_game`/`send_to_room`, `set_in_queue`/`is_in_queue`, `PlayerConnection.current_game_id`/`current_room_code`/`is_in_queue`.
게임·방 대상 전송은 이제 이벤트 발행이 대신한다.

고치는 것: **`disconnect(user_id, websocket=None)`** — 소켓을 넘기면 그 소켓이 현재 등록된 소켓일 때만 지운다. 교체된 옛 핸들러가
새 연결을 지우는 문제(위 사실)를 막는다. 다른 워커에 붙은 같은 유저(다중 탭)는 7단계 접속 정책 몫이다.

## 실행 비용

장시간 연산은 없다. 늘어나는 테스트는 Redis 와 가짜 소켓만 쓰고 **DB 픽스처를 쓰지 않는다**(3단계 증가분의 원인).

- **추정:** 약 45건 추가 (events 15, view 8, bus 15, connection_manager ±0). 전달 대기는 이벤트당 수 ms 이고, 대기 상한
  1 s 짜리 폴링(`asyncio.wait_for`)으로 기다린다. 재구독 테스트는 백오프 최소값 100 ms + 재구독이다.
  **증가분 추정 +10 s 안팎 → 전체 ≈ 135 s**
- **기준선:** 커밋 0 전에 `server-test` 시간을 한 번 재서 커밋 메시지에 적는다
- **중단 조건:** 전체가 기준선 + 60 s 를 넘으면 멈추고 원인을 확인한다(전달 대기 타임아웃이 실제로 만료되는 테스트, 정리되지 않은 버스 태스크).
  그래도 넘으면 `--cpus 4` 와 `tests/ws` 분리 실행을 적용한다
- **누수 확인:** 테스트 후 `CLIENT LIST` 에 `gamemoa-bus-*` 연결이 남지 않아야 한다

## MUST / MUST NOT

- MUST: 커밋마다 `docker compose run --rm server-test` 전체 통과
- MUST: Redis 진입은 `require_redis()`, 호출은 `store_errors()`. 발행 실패만 예외로 삼켜 로그를 남긴다(판단 3)
- MUST: 채널 이름은 `redis_keys.py` 에만, 설정값은 `config.py` 에만 둔다. 테스트는 논리 DB 1 + `db1:` 네임스페이스
- MUST: 인원 수를 코드에 쓰지 않는다. 버스·이벤트 테스트는 quad 행 추가만으로 통과해야 한다
- MUST: 이벤트 hint 와 버스 메시지에 게임 상태·좌표를 싣지 않는다
- MUST NOT: WS 라우터 작성, `main.py` 수정(라우터 등록·lifespan 배선 모두 7단계)
- MUST NOT: 시야 계산, Fischer 시계, ZSET 스위퍼 (5·6단계)
- MUST NOT: 의존성 추가 (`fakeredis` 등). 필요해지면 멈추고 승인을 받는다
- MUST NOT: 엔진(`games/maze/core/*`)·리포지토리 동작 변경

## 의도적으로 제외

- **느린 소켓 격리** — 수신 루프는 로컬 전송을 순서대로 한다. 소켓 하나가 멈추면 그 워커의 전달이 늦어진다. 전송 타임아웃이나
  연결별 송신 큐는 7단계 접속 정책(다중 탭·끊김 처리)과 함께 정한다
- 이벤트 유실률 지표·관측 — 7단계 `/health` 와 함께
- Redis Streams 등 at-least-once 전송 — 재동기화로 수렴하므로 도입하지 않는다(E5 결론)
- 관전자 채널 구독
