"운영 중 조정 항목"(설계는 확정·숫자만 튜닝) 표가 들어간다.**

왜 지금인가: `ROADMAP.md` M3("WebSocket 상태 Redis 이전 + 1:1:1 확장")의 선행
조건이 "`maze.md` 확정"이다. 설계 없이 착수하면 1:1:1 확장 때 다시 뒤집힌다.

**가장 큰 변경 2건** — 단순한 값 채우기가 아니라 설계 교체다:

1. **시야 체계** — "시선 방향 기준 Raycasting(각도+사거리)" → **"방향 무관 3×3
   + 벽 차폐"**. `facing` 이 프로토콜에서 사라지고, 관측 단위가 *벽*에서
   *단위 변*으로 바뀐다. **SSOT 수정까지 이어진다.**
2. **시간 체계** — "턴당 30초 타이머" → **"Fischer 전체 시간제 + 접속 시계

3. **종료 조건의 N인 일반화** — 시간패·항복·접속 소진은 **게임 종료가 아니라

   탈락·생존·순위를 모드 무관 공통 규칙으로 재정의한다.

산출물: 설계서 4종 갱신 + 미결 표 재편 + 계획서 이관. **코드는 건드리지 않는다.**

## A. 시야 체계 — 전면 교체

### A1. 시야 규칙 = 방향 무관 3×3 + 벽 차폐 〔maze #1〕

```
   +---+---+---+   ← 3×3 외곽 변: 전송하지 않는다
   | a | b | c |
   +---#---#---+   ← # = 내부 변 12개 (가로 2줄×3 + 세로 2줄×3)
   | d | P | e |      P 가 어디를 보든 내용이 같다 (360° 시야)
   +---#---#---+
   | f | g | h |
   +---+---+---+
```

| 규칙 | 내용 |
| :--- | :--- |
| 범위 | 플레이어 중심 **3×3**(자신 포함 9칸). **`facing` 무관 — 전방향** |
| 직교 차폐 | `P`–`b` 사이에 벽이 있으면 **`b` 는 보이지 않는다** |
| 대각 차폐 | `c` 는 `P→b→c` 와 `P→e→c` 가 **둘 다** 막혀야 안 보인다. 하나라도 열려 있으면 보인다 |
| 보이는 변 | **보이는 칸에 접한 내부 변만.** `P` 는 항상 보이므로 **내 4면은 항상 보인다**(막혔다는 사실을 안다). `b` 가 안 보이면 `a｜b`·`b｜c` 는 전송하지 않는다 |
| 외곽 | 3×3 바깥 테두리 변은 **어떤 경우에도 전송하지 않는다** |

**설계서에 넣을 검증 예시**

```
   +---+---+---+          P–b 에 벽(===) 하나만 있는 경우
   | a | b | c |
   +---#===#---+          보이는 칸 : P d e f g h  +  a (d 경유)  +  c (e 경유)
   | d | P | e |          안 보이는 칸: b
   +---#---#---+
   | f | g | h |          전송하는 변: P 의 4면(P｜b 벽 포함) + a d e f g h 의
   +---+---+---+          내부 변.  a｜b · b｜c 는 제외
```

- **되돌림 비용: 중간.** 되돌리려면 `facing` 을 프로토콜에 복원해야 한다.
- **확장성:** 플레이어 중심 상대 좌표라 **인원 수와 완전히 무관**. ✅

### A2. `facing` 을 프로토콜에서 삭제 〔maze #3 과 동반〕

시야가 방향에 의존하지 않으므로 서버는 `facing` 을 알 필요가 없다.
**카메라 방향은 순수 클라이언트 상태**이며 서버 프로토콜에 나타나지 않는다.

- `move.payload.facing` 삭제 → `move` 가 구 Quoridor 와 동일해져 §12 에서
  "변경" → **"재사용"** 으로 내려간다
- `game_state.me.facing` 삭제
- §9 "현재 위치·방향으로 시야를 다시 계산" → "현재 위치로"

### A3. 관측 단위를 **벽**에서 **단위 변**으로 ⚠️

Quoridor 벽은 **2칸 길이**다. 벽의 절반만 시야에 들어왔는데 벽 전체를 보내면
**보이지 않아야 할 절반이 드러난다** — §6 MUST NOT 위반이다.

| 용도 | 단위 | 표현 |
| :--- | :--- | :--- |
| **설치·검증** (§7) | 벽 (2칸) | `{row, col, orientation}` — **변경 없음** |
| **관측** (§6) | 단위 변 | `{row, col, orientation}` 을 *변* 의미로 재정의:<br>`horizontal` = 칸 `(row,col)` 의 **북쪽** 변 (`row ≥ 1`)<br>`vertical` = 칸 `(row,col)` 의 **서쪽** 변 (`col ≥ 1`) |

→ `visible_walls` → **`visible_edges`**, `discovered_walls` → **`discovered_edges`**.
포함 관계와 단조 증가는 그대로 성립한다. `game_end.full_board`(§10)는 전부
공개되므로 **벽 단위 유지**.

### A4. 발견 맵 — 플레이어별 누적 상태 〔신규 확정〕

> "플레이어는 자신이 진행하면서 발견한 벽과 플레이어 위치가 맵 형식으로 뜬다.
> 이 맵은 오롯이 플레이어 각각이 **직접 확인한 경우에만** 갱신된다."

플레이어별로 **Redis 에 게임 수명 동안** 보관한다(워커가 바뀌어도 유지, 재접속
시 복원). 게임 종료 시 폐기.

| 필드 | 의미 | 갱신 |
| :--- | :--- | :--- |
| `discovered_edges` | 한 번이라도 **직접 본** 변의 누적 | 단조 증가 (벽은 사라지지 않는다) |
| `last_seen_players[]` | 좌석별 **마지막 목격 위치 + 목격 턴 번호** | 그 좌석이 내 시야에 들어온 순간에만 |

> **MUST NOT:** 서버가 **목격하지 않은** 위치를 추론해 채워 넣지 않는다.
> 상대가 시야 밖에서 이동해도 `last_seen_players` 는 그대로 둔다 — 낡은 정보라는
> 사실 자체가 게임성이다. 클라이언트는 목격 턴 번호와 함께 흐리게 표시한다.

### A5. 시야 밖 행동 통보 — 행위자와 종류만 공개 〔maze #2〕

> "남은 벽 개수와 **누가 설치 or 이동했는지**만 공개하고, 그 위치는 공개하지 않는다."

`turn_change` payload 에 `last_action: { seat_no, kind: "move" | "wall" }` 을
추가한다. **좌표는 담지 않는다.** 신규 메시지 타입 없음.

| 공개 | 비공개 |
| :--- | :--- |
| 누가 행동했는가 (`seat_no`) | 어디로 이동했는가 |
| 무엇을 했는가 (`move`/`wall`) | 어디에 벽을 놓았는가 |
| 남은 벽 개수 (기존 `others[].walls_remaining`) | 목표까지 남은 거리 |

근거: 남은 벽 개수가 이미 공개되므로 "벽을 놓았다"는 사실은 **어차피 추론
가능**하다. 추론 가능한 것을 숨기면 UI 가 일관되지 않을 뿐 정보 우위는 생기지
않는다. 위치만 끝까지 감춘다.

렌더링은 여전히 레이캐스팅/셰이더다. 바꾸는 것은 **서버 판정 문구뿐**이다.

## B. 시간 체계 — 전면 재설계 〔maze #4 · #11〕

### B1. 두 개의 시계를 완전히 분리한다

> "고의로 네트워크 차단하는 경우를 대비해, 게임 타이머와 접속 타이머를 완벽히
> 분리하는 이중 설계 필수"

| | **게임 시계** (Game Clock) | **접속 시계** (Connection Clock) |
| :--- | :--- | :--- |
| 측정 대상 | 플레이어의 누적 사고 시간 | 그 플레이어가 **끊겨 있던** 누적 시간 |
| 방식 | **Fischer** — 초기 `300s`, 수마다 `+5s` | 총량 `60s` 에서 차감 |
| 흐르는 조건 | **내 차례일 때만** | **연결이 끊긴 동안만** (차례 무관) |
| 소진 시 | 시간패 → `game_end.reason = "time_forfeit"` | 기권패 → `reason = "disconnect_forfeit"` |
| 재접속 시 | 영향 없음 | **리셋하지 않는다 — 절대 누적값** |

**왜 분리하는가:** 한 시계로 합치면 "끊고 생각하기"가 성립한다. 분리하면 끊은
동안 **게임 시계(내 차례라면)와 접속 시계가 동시에** 줄어 양쪽에서 손해다.

**재접속 예산을 리셋하지 않는 이유(사용자 지정):** 접속할 때마다 60초가
되돌아오면 "끊었다 붙었다"를 반복하는 악용이 성립한다. 한 게임 동안 **누적
60초**가 절대 상한이다.

### B2. Fischer 산정 — 서버 권위

```
턴 시작      : turn_started_at = 서버 수신 시각
행동 수락 시 : remaining -= (now - turn_started_at)
               remaining += increment
               remaining <= 0  →  time_forfeit
```

- **클라이언트가 보낸 시각을 쓰지 않는다.** 서버 수신 시각만 쓴다 (§3.3 원칙 2)
- **상행 지연 보정식을 두지 않는다** — 보정은 클라이언트 주장 시각을 신뢰해야
  성립하므로 Zero-Trust 위반이다. `increment 5s` 가 왕복 지연보다 훨씬 커서
  실질적으로 그 역할을 한다

### B3. 하트비트 — 신규 메시지 타입 없이

**uvicorn 의 WebSocket ping/pong 을 쓴다** (`--ws-ping-interval` /
`--ws-ping-timeout`). 프로토콜 레벨이므로 §12 에 앱 메시지를 추가하지 않는다.
→ 끊김 감지 지연 ≤ ping interval + timeout.

### B4. 서버 장애 Fail-safe — 무효 처리

> "서버 자체의 렉, 인프라 장애, 배포 재시작 등 서버 측 장애 시 무효 처리를 통해
> 레이팅 변동의 Fail-safe 가 필수"

| 요소 | 설계 |
| :--- | :--- |
| 워커 생존 | 각 워커가 Redis `worker:<id>:alive` 를 짧은 TTL 로 갱신 |
| 게임 소유 | `game:<id>:owner_worker` 기록 |
| 장애 판정 | 소유 워커의 `alive` 키 소멸 = 워커 사망 |
| graceful shutdown | 배포 종료 시 진행 중 게임을 **스스로** 무효 처리 |
| 결과 | `game_end.reason = "server_fault"`, 참가자 `result = "void"`<br>**MMR 변동 0, 전적 미집계** |

### B5. 만료 감지 = Redis ZSET + 스위퍼 〔maze #11〕

턴 타이머가 사라져도 감지해야 할 데드라인은 **두 종류**가 남는다.

| 요소 | 설계 |
| :--- | :--- |
| 색인 | 단일 ZSET `maze:deadlines` — score = 만료 epoch ms |
| member 형식 | `"clock:<game_id>"` (현재 차례의 게임 시계 소진 예정 시각)<br>`"grace:<game_id>:<seat_no>"` (재접속 예산 소진 예정 시각) |
| 감지 | 각 워커가 1초 주기: `ZRANGEBYSCORE key -inf <now> LIMIT 0 N` |
| 중복 방지 | 후보마다 `ZREM` → **반환값 1인 워커만** 처리. 원자적 claim 이라 **리더 선출 불필요** |
| 지연 보정 | 행동 수신 시에도 데드라인을 비교해 이미 지났으면 먼저 처리 |
| 통보 | Redis **Pub/Sub** 으로 방 채널 발행 → 연결을 가진 워커가 **플레이어별 개별 전송**(§6) |

**기각한 대안**

| 대안 | 기각 이유 |
| :--- | :--- |
| 키 TTL + keyspace notification `Ex` | ① `notify-keyspace-events` 를 Redis 설정에 켜야 한다 — `docker-compose.yml:54` 의 `command` 에 없다 ② Pub/Sub 은 **at-most-once**. 구독자 재연결 중이면 이벤트가 영구 소실되고 **그 게임이 영원히 멈춘다** ③ 통지 지연이 비결정적. 결국 복구용 폴링을 또 만들어야 한다 |
| 전 게임 주기 폴링 | 게임 수에 비례하는 스캔. ZSET 은 `O(log N + k)` |
| APScheduler 잡 등록 | 기본 잡 저장소가 프로세스 메모리라 워커 사망 시 소실 |
| `asyncio.call_later` | 워커 종속. `PLATFORM_ARCHITECTURE.md` §2.2 위반 |

- **되돌림 비용: 낮음.** 스위퍼는 독립 모듈이고 감지 방식만 교체하면 된다.
- **확장성:** member 접두어가 kind 다 — kind 추가 = **핸들러 등록 한 줄**.
  키를 `{game}:deadlines` 로 두면 오목도 같은 구조를 쓴다. 인원 수 무관. ✅

### B6. 시간패는 **게임 종료가 아니라 좌석 탈락**이다 — N인 일반화

> 2인전에서는 시간패 = 게임 종료지만, 3인·4인전에서는 **그 플레이어만 행동
> 불가(패배) 상태**가 되고 게임은 계속된다.

현 설계가 2인 전제였다. **탈락과 종료를 분리해 모드 무관 공통 규칙으로 쓴다.**
`§9` 를 "재접속·이탈·항복" → **"이탈·탈락·종료 조건"** 으로 확장하고 여기에
공통 규칙을 둔다. `§11` 에는 3인 **전용** 잔여분(좌석·목표·벽·턴 순서)만 남긴다.

#### 탈락 사유 (좌석 단위)

| 사유 | 트리거 |
| :--- | :--- |
| `surrender` | 본인이 `surrender` 전송. 시작 후 방 이탈도 동일 처리 |
| `time_forfeit` | **게임 시계 소진.** 시계는 자기 차례에만 흐르므로 **항상 자기 차례에** 발생한다 |
| `disconnect_forfeit` | 재접속 예산(누적 60s) 소진 |

#### 탈락 처리 절차

1. 좌석을 `eliminated` 로 표시하고 **탈락 순번(`eliminated_order`)** 을 부여
2. **턴 순환에서 제외**한다
3. 그 좌석의 게임 시계·접속 시계 데드라인을 ZSET 에서 **제거**한다
4. **§7 경로 보장 검증 대상에서 제외한다** ⚠️ — 빠뜨리면 탈락자의 경로 때문에
   벽 설치가 영구히 거절된다. `pathfinder.py` 는 **생존자 목록**만 받아야 한다
5. 탈락자가 현재 차례였다면 **즉시 다음 생존자로 턴 전환** + 새 `clock:` 데드라인
6. 남은 전원에게 `player_left` 로 통보 — **신규 메시지 타입 없음**

#### `player_left` 로 일시 끊김과 확정 탈락을 모두 표현한다

```json
{ "type": "player_left",
  "payload": {
    "seat_no": 2,
    "state": "reconnecting" | "eliminated",
    "reason": "surrender" | "time_forfeit" | "disconnect_forfeit" | null,
    "grace_remaining_ms": 42000,
    "survivors": 2
  } }
```

`grace_remaining_ms` 는 `state:"reconnecting"` 일 때만. 기존 §12 분류("변경")가
유지되므로 집계가 바뀌지 않는다.

#### 게임 종료 조건 — 셋뿐이다

| 조건 | `game_end.reason` | 결과 |
| :--- | :--- | :--- |
| 누군가 목표에 도달 | `goal_reached` | 도달자 1위, 즉시 종료 |
| **생존자가 1명만 남음** | `last_standing` | 그 1명 1위, 즉시 종료 |
| 서버 장애 (B4) | `server_fault` | 전원 `result: "void"`, MMR 변동 0 |

**2인전은 자동으로 성립한다** — 1명 탈락 = 생존자 1명 = `last_standing`.
모드별 분기가 필요 없다. ✅

> **`reason` 은 게임 수준, 탈락 사유는 좌석 수준으로 분리한다.** 왜 끝났는지는
> `reason`, 누가 왜 빠졌는지는 `results[].elimination_reason` 이 답한다.
> 구 `reason` 값 `surrender`·`disconnect_timeout`·`turn_timeout` 은 **좌석 사유를
> 게임 사유 자리에 쓰던 것**이라 2인에서만 성립했다 — 전부 삭제한다.

#### 순위 산정 — 모드 무관

```
순위 = [목표 도달자]
     > [생존자 : 목표까지 남은 최단거리 ↑ → 사용 턴 수 ↑ → 공동]
     > [탈락자 : eliminated_order 내림차순 — 나중에 탈락한 쪽이 상위]
```

> **탈락 역순인 이유:** 오래 버틴 것은 성과다. 전원을 공동 최하위로 두면 10턴에
> 끊고 나간 사람과 25턴을 싸우다 항복한 사람의 MMR 변동이 같아지고, **조기 이탈에
> 불이익이 없어진다.**

예 (4인전): `seat2` 10턴 시간패, `seat4` 25턴 항복, `seat1` 목표 도달
→ 1위 `seat1`(도달) / 2위 `seat3`(생존) / 3위 `seat4`(25턴) / 4위 `seat2`(10턴)

- **확장성:** 전부 좌석 목록 연산이다. 인원이 늘어도 **배열 길이만** 는다. ✅

#### 파급 — `turn_timeout` 메시지 타입 폐기

탈락은 `player_left`, 종료는 `game_end` 가 통보한다. `turn_timeout` 은 쓰임이
없다 → **폐기.** 어휘를 늘리지 않고 **줄인다** — "신규 0종" 원칙은 유지된다.

`results[]` 항목 확장: `elimination_reason`(위 3값 또는 `null`),
`result` 에 **`void`** 추가(B4).

## C. 규칙 확정

### C1. 방향 전환은 턴이 아니다 〔maze #3〕

360° 시야이므로 회전은 **서버 상태를 전혀 바꾸지 않는다.** 회전 전용 메시지를
만들지 않고, 서버는 카메라 방향을 알지 못한다. 신규 타입 0종 유지.

- **되돌림 비용: 낮음.** 방향 의존을 되살리려면 A1 자체를 뒤집어야 한다.

### C2. 3인전 시작·목표 = 꼭짓점 랜덤 + 대각 반대 두 변 〔maze #5〕

> "FOV 를 도입했으므로 공정성이 어느 정도 상쇄된다. 정사각형의 각 꼭짓점에
> 랜덤으로 시작."

| | 값 |
| :--- | :--- |
| 시작 | 보드 네 꼭짓점 `(0,0) (0,8) (8,0) (8,8)` 중 **랜덤 3개**를 좌석에 배정 |
| 목표 | **대각 반대편 두 변의 합집합.** 예: `(0,0)` → `row=8` ∪ `col=8` (L자 17칸) |
| 공정성 | 네 꼭짓점 모두 목표 17칸·최단거리 16으로 **완전 대칭** |

**목표 표현을 `goals` 목록으로 일반화한다** — 2인전은 원소 1개, 3·4인전은 2개.
`Player.goal_row`(단일 축) → `goals: [{axis, value}, …]`.

```
   시작 (0,0)                  목표: row 8  ∪  col 8
     0 1 2 3 4 5 6 7 8
   0 S . . . . . . . G
   1 . . . . . . . . G
   …                 G
   8 G G G G G G G G G
```

- **기각한 대안:** 목표 1칸(꼭짓점) → 벽 2개로 봉쇄돼 §7 경로 보장 검증이 상시
  발동, 벽 설치가 자주 거절된다 (C4 의 거절 2회 제한과 충돌).
  목표 3×3 영역 → 목표가 `(축,값)`이 아니라 *영역*이 되어 엔진 일반화 범위가 커진다.
- **확장성:** 꼭짓점 4개 = **4인전까지 그대로**. `goals` 가 목록이라 축 수가 늘어도
  행만 는다. ✅

### C2-b. 2인전은 **변 중앙을 유지한다** — 설계서에 이유를 적는다

`(8,4)→goals:[{axis:"row",value:0}]`, `(0,4)→goals:[{axis:"row",value:8}]`.

꼭짓점으로 통일하지 않는 이유를 §11 에 1단락으로 남긴다 — 적어두지 않으면
"왜 모드마다 다른가"가 반복 질문이 된다.

| 쟁점 | 판단 |
| :--- | :--- |
| **왜 3인은 꼭짓점인가** | 취향이 아니라 **제약**이다. 4변 중 3변에 배치하면 비대칭이 되어 꼭짓점이 필연이었다 |
| **일관성 손실은?** | 없다. 데이터 구조가 이미 통일돼 있다 — `goals[]` 목록 + 좌석별 시작 테이블. 시작 좌표는 **테이블의 값일 뿐**이고, 확장성 기준("행 추가 외에 변경이 필요한가")을 만족한다 |
| **밸런스** | 변 중앙은 목표 9칸·최단 8수로 **벽 10개의 가치가 높다.** 꼭짓점+두 변은 목표가 17칸이라 봉쇄가 어려워져 벽 가치가 떨어지고 재조정이 필요하다 |
| **상호작용** | 변 중앙은 두 경로가 `col 4` 에서 **정면 충돌**한다. 3×3 FOV 에서도 중앙에서 반드시 조우하므로 점프 규칙·막기가 살아 있다. 대각 출발은 서로 못 만나고 끝날 수 있다 |

> **배치 테이블로 표현한다** (행 추가로 확장):
>
> | mode | 시작 | 목표 |
> | :--- | :--- | :--- |
> | `duel` | 변 중앙 대향 2점 | 반대 변 1개 |
> | `trio` | 네 꼭짓점 중 **랜덤 3** | 대각 반대 두 변 |
> | `quad` *(미래)* | 네 꼭짓점 전부 | 대각 반대 두 변 |

### C3. 3인전 벽 = 인당 7개 〔maze #6〕

총 21개. 2인전 총 20개(인당 10)와 근사해 보드 포화도가 유지된다.

### C4. 턴당 벽 거절 2회 + 3회째 잠금 〔maze #7〕

| 항목 | 값 |
| :--- | :--- |
| 턴당 허용 거절 | **2회** (단순 실수·가벼운 탐색 보장) |
| 3회째 거절 시 | 그 턴 **벽 설치 잠금** — 반드시 말을 이동해야 한다 |
| 잠금 후 벽 시도 | `probe_limit_exceeded` (의미를 "이번 턴 벽 설치 잠김"으로 **재정의**. 새 코드 추가 없음) |
| 시간 페널티 | **없다.** 거절 자체는 게임 시계를 추가로 깎지 않는다 (내 턴이므로 시계는 경과분만큼 흐른다) |
| 리셋 | 턴이 바뀔 때 |
| 저장 | Redis (M3 의존) |

**자기 억제 메커니즘(사용자 지정) — 설계서에 근거로 남긴다:**

> 허공에 찔러서 **벽이 정상 설치되어 버리면** 턴이 끝나고 벽 1개를 낭비한다.
> 이 손실이 무분별한 탐색을 스스로 억제한다. 횟수 제한은 그 위의 상한일 뿐이다.

제한이 필요한 이유는 기존 §7 서술 유지 — 무제한이면 한 턴에 126개 후보를 훑어
**벽 그래프를 역산**할 수 있고 Fog of War 가 무너진다.

### D2. 유저 선택 병합 — **솔로 플레이 도입 시점**으로 〔platform #2〕

Phase 1 에 넣지 않는다. 충돌 시 `merge.performed:false` + `merge_not_applicable`
로 로그인만 시킨다(현 설계 유지). **§2.3 에 MUST 를 박는다:**

> **MUST:** 병합이 거절되면 클라이언트는 **로컬 솔로 진행도를 삭제하지 않는다.**
> 선택 병합 API 가 추가될 때 복구할 원본이 사라진다.

설계 후보 명시: `PUT /api/v1/me/solo-progress/{game}` (전체 교체, 멱등).

- **되돌림 비용: 낮음** — **단 위 MUST 가 없으면 무한대다.** 클라이언트가 로컬
  데이터를 지우면 나중에 API 를 만들어도 합칠 원본이 없다.

### D3. `refresh_tokens` 정리 = 토큰 회전·로그인 시 〔platform #3〕

1. 모든 조회에 `revoked_at IS NULL AND expires_at > now()`
2. **토큰 회전·로그인 시** 같은 `user_id` 의 만료 행을 함께 삭제
   (`DELETE … WHERE user_id=? AND expires_at < now()`) — 정리 부하가 유저
   트래픽에 비례하고, 유저당 행 수가 활성 기기 수 수준으로 유지된다
3. 인덱스 `(user_id, expires_at)`
4. 삭제 기준은 `revoked_at` 이 **아니라** `expires_at` — 폐기된 행이 만료까지
   남아야 `replaced_by_jti` 체인으로 재사용(탈취)을 잡는다 (§1.4)

**주기 작업을 만들지 않는다.** → ROADMAP "스케줄러 제거"의 근거 1.

### D4. 매칭 시도 통계 = 구조화 로그 〔platform #4〕

전용 테이블을 만들지 않는다. **필드 이름을 지금 고정**해 둔다(나중에 집계
테이블로 그대로 옮긴다):

| 필드 | 값 |
| :--- | :--- |
| `event` | `match_found` \| `match_cancelled` \| `queue_left` |
| `game` / `mode` | `maze_1p` / `duel`·`trio`… |
| `wait_ms` | 큐 진입 ~ 이벤트 |
| `mmr_gap` | 성사 시 참가자 MMR 최대 차 |
| `queue_size` | 이벤트 시점 큐 길이 |

- **유일한 비용:** 소급 데이터가 로그 보존 기간까지만 복구된다.
- **확장성:** `mode` 가 필드이므로 `quad` 가 생겨도 **값만 늘고 스키마 불변**. ✅

### D5. 매칭 MMR 제한 — **Phase 1 은 제한 없음** 〔maze #10〕

> "MMR 기능만 도입하고 나중에 제한함. 현재는 모든 MMR 과 매칭 가능"

- MMR 은 **계산·기록·리더보드에 정상 사용**한다. 매칭 **필터만** 걸지 않는다
- §3 의 확장 표(±100→±500, `trio` ±700)는 **"큐 인구 확보 후 도입"** 으로 옮긴다.
  서버 설정으로 on/off
- **근거:** 출시 직후 동시 접속자가 적다. MMR 필터를 걸면 **매칭이 성사되지
  않는다.** 품질보다 성사가 우선이다
- **되돌림 비용: 낮음.** `matchmaking.py:41,164` 의 기존 범위 로직은 그대로 두고
  비활성화만 한다
- **확장성:** 범위 테이블을 설정값으로 두면 모드 추가가 **행 추가**. ✅

### D6. `chat` — 게임 완성 후 별도 추가 〔maze #9〕

`WSMessageType.CHAT` 을 어휘에 남긴다. 서버는 수신 시 `feature_disabled` 로
거절한다. **게임 6종이 완성된 뒤** 운영 체계(금칙어·신고·차단·보관·미성년자
보호)와 **함께** 설계한다.

`platform.md` §0 공통 에러 코드에 `feature_disabled`(400) 1행 추가 — 게임 전용이
아니므로 공통에 둔다.

### D7. 종료 후 공개 = 최종 상태만 〔maze #8〕

`game_end.full_board` 유지. **담는 것을 한정한다:**

- 담는다: 최종 **벽** 배치(2칸 단위), 좌석별 최종 위치 `[{seat_no, row, col}]`
- **담지 않는다: 이동 경로·수 기록.** 리플레이 재도입 시 함께 추가한다
  (명시하지 않으면 `full_board` 가 리플레이의 우회로가 된다)
- 랭크·친선 구분 없이 동일 공개. 단 **`server_fault` 무효 게임도 공개**한다
  (복기 가치는 동일하고 MMR 만 미반영)

- **확장성:** 좌석 정보가 **배열**이라 4인이 되어도 행만 는다. ✅
