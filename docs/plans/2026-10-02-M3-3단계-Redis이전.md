# M3 3단계 — 큐·방·게임 상태를 Redis 로

> 착수 시 `2026-10-02-M3-3단계-Redis이전.md` 로 이름을 바꾸고 `**상태: 진행 중**` 머리글을 붙인다.

## Context

ROADMAP M3 실행 순서 3단계. 1단계로 엔진이 N인 좌석 모델이 되었고(`GameState.to_dict()` = Redis 상태 형태),
2단계로 DB 가 `game_sessions`(시작·종료 기록) + `game_participants` 가 되었다. 그런데 큐·방·게임 상태는
아직 프로세스 내 dict 이다(`app/ws/room_manager._rooms`, `matchmaking._queue`, `quoridor_service._games`).
이 때문에 워커가 2개 이상이면 매칭이 깨지고, 재접속하는 3~15% 는 다른 워커에 붙어 게임을 잃는다(실측 E1).
3단계는 이 세 가지를 **Redis 권위 + 게임별 락**(실측 보고서 판정, maze.md §8)으로 옮기고, 게임이 끝나면
DB 에 기록한다.

**2.5단계 보류에 따른 전제 (ROADMAP 인용문):** 규칙·보안 검증을 거치지 않고 스키마를 굳힌다. 문제가 드러나면
교체·수정으로 대응한다. 단계마다 테스트 전체 통과는 지킨다.

**사용자 결정 (2026-10-02, 이 계획 중)**

1. **`ws_game.py` 는 삭제한다.** 구 2인 Quoridor 핸들러이고 이미 shim 과 어긋나 있다. `room_manager`·`matchmaking`·
   `quoridor_service` 와 해당 테스트도 함께 지운다. `connection_manager` 는 남긴다(소켓은 본래 프로세스 안에 있고,
   4단계에서 Pub/Sub 을 붙인다). **새 maze WS 핸들러(§12)는 7단계에서 이번에 만든 저장소를 대상으로 새로 작성한다.**
   구 코드는 `git show` 로 참고한다
2. **좌석 배정:** 랭크 매칭은 seat_no 를 **무작위로 섞는다**. 큐에 먼저 들어왔다고 선수를 가져가지 않게 하기 위해서다.
   친구 방은 **방 seat_no(호스트 = 1, 나머지는 입장 순)를 그대로 게임 seat_no 로 쓴다**. §4 `room_created` 페이로드와 맞추기 위해서다

## 판단 1 — Redis 키 스키마 (확정)

모든 키는 `app/db/redis_keys.py` 한 곳에서 만든다. 문자열 리터럴을 흩어 쓰지 않는다.
`{game}` = 게임 식별자(`maze_1p`), `{mode}` = 배치 테이블 키(`duel`/`trio`/…). **인원 수가 들어가는 키는 없다.**

| 키 | 타입 | 값 | TTL | 쓰는 쪽 | 읽는 쪽 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `game:{id}:state` | STRING | `GameState.to_dict()` JSON | 진행 중: 없음 / 종료 후: `game_finished_ttl_sec`(300) | 게임 서비스(락 안에서, 락 토큰 펜싱) | 게임 서비스, 재접속(7단계) |
| `game:{id}:meta` | STRING | JSON `{game, mode, is_ranked, room_code, created_at, players:[{seat_no, user_id, nickname, is_ai}]}` — 생성 후 불변 | state 와 동일 | 게임 서비스(생성 시 1회) | 게임 서비스(user → seat 매핑), 7단계 핸들러 |
| `game:{id}:lock` | STRING | 무작위 토큰 | `PX game_lock_ttl_ms`(5000) | `redis_lock` | `redis_lock`, 펜싱 쓰기 Lua |
| `queue:{game}:{mode}` | ZSET | member=`user_id`, score=입장 시각(epoch ms) | 없음(항목은 매칭·이탈 때 빠진다) | 매치메이킹 | 매치메이킹(순번·대기 인원) |
| `queue:{game}:{mode}:entries` | HASH | field=`user_id`, value=JSON `{nickname, mmr, joined_at_ms}` | 없음 | 매치메이킹 | 매치메이킹(매칭 Lua) |
| `match:{match_id}` | STRING | JSON `{game, mode, ready_deadline_ms, players:[{seat_no, user_id, nickname, mmr, joined_at_ms, ready}]}` | `match_record_ttl_sec`(60) — 안전망. 실제 기한은 6단계 스위퍼 | 매치메이킹 | 매치메이킹(`ready`, `expire_match`) |
| `match:{match_id}:lock` | STRING | 토큰 | PX | `redis_lock` | `redis_lock` |
| `room:{code}` | STRING | JSON `{code, game, mode, capacity, status, game_id, created_at, players:[{seat_no, user_id, nickname, is_host, is_ready}]}` | `room_ttl_sec`(3600). 변경 시 갱신 | 방 서비스(코드는 `SET NX` 로 확보) | 방 서비스 |
| `room:{code}:lock` | STRING | 토큰 | PX | `redis_lock` | `redis_lock` |
| `user:{uid}:activity` | STRING | `queue:{game}:{mode}` \| `match:{id}` \| `room:{code}` \| `game:{id}` — **유저당 활동 하나** | 담는 대상과 같게 맞춘다(game: 없음) | 전 서비스. 진입은 `SET NX`, 전이·해제는 Lua CAS | 전 서비스, 재접속(7단계) |

**예약만 해 둔다(이 단계에서 만들지 않음):** `game:{id}:events`(Pub/Sub 채널, 4단계), `game:{id}:vision:{seat_no}`
(5단계), `game:{id}:clocks`·`maze:deadlines`(6단계). 표에는 행으로 적어 두되 "생성 단계"를 표시한다.

설계 근거:

- **meta 를 state 와 분리한다.** 엔진은 프레임워크와 유저를 모른다(`to_dict()` docstring). meta 는 불변이라 락 없이 읽어도 된다
- **`user:{uid}:activity` 하나로 배타성을 보장한다.** "한 사용자는 동시에 하나의 큐에만"(§3)과 "방·큐 동시 참가 금지"가 키 하나의
  `SET NX` 로 원자적으로 성립한다. 전이(queue → match → game, room → game)는 기대값 비교 Lua 로 처리한다. 재접속할 때 게임을
  찾는 색인으로도 쓴다
- **매칭 = Lua 원자 연산.** `ZCARD ≥ seats` 일 때만 `ZPOPMIN seats` + `HMGET`/`HDEL` 을 한다. `seats` 는 `get_layout(mode).seats`
  에서 받아 ARGV 로 넘긴다 → 4인 모드는 배치 테이블 행만 추가하면 된다. 매칭은 **입장할 때마다 시도**한다(Phase 1 은 MMR 필터가
  없는 FIFO 라 주기 루프가 필요 없다)
- **MMR 범위 로직은 남긴다(비활성).** 구 `SCORE_RANGE_*` 확장 규칙을 순수 함수 `mmr_window(wait_sec, mode)` 와 모드별 상한 표로
  옮기고, `settings.match_mmr_filter_enabled = False` 일 때는 호출하지 않는다. 함수 단위 테스트만 둔다(maze.md §3)
- **방 코드 = `SET NX room:{code}`** 로 충돌 없이 확보한다. 구 `MAX_ROOMS` 상한은 없앤다(TTL 이 누수를 막는다)
- **누수 대비:** 크래시로 큐에 남은 유령은 매칭된 뒤 `ready` 를 보내지 않으므로 `expire_match` 가 걸러낸다. 응답한 쪽만 **원래
  `joined_at` 점수로** 큐에 복귀해 순서를 잃지 않는다(§3). 진행 중 게임 키에 TTL 이 없는 것은 6단계 fail-safe 가 정리한다

## 판단 2 — 게임별 락과 쓰기 펜싱

`app/db/redis_lock.py` — `async with redis_lock(key, ttl_ms, wait_ms) as token:`

- 획득: `SET key token NX PX ttl`. 실패하면 10 ms 간격으로 `wait_ms` 까지 재시도하고, 그래도 안 되면 `LockTimeout`
- 해제: Lua `if GET == token then DEL`
- **펜싱 쓰기:** `fenced_set(lock_key, token, key, value, ...)` Lua — 락 토큰이 아직 내 것일 때만 쓴다. 락 TTL 을 넘긴 행동이
  다른 행동의 결과를 덮어쓰지 못한다(E6 가 확인하지 않은 경계)
- 게임 락·매치 락·방 락이 같은 헬퍼를 쓴다

## 판단 3 — 게임 서비스 (`quoridor_service` shim 대체)

`app/services/maze_game.py` — 싱글톤 대신 **함수 + 주입 가능한 의존성**(redis, session_factory)으로 만든다. 테스트가 DB 1 Redis 와
테스트 엔진을 주입한다.

```python
GAME = "maze_1p"

@dataclass(frozen=True)
class SeatPlayer: seat_no: int; user_id: int | None; nickname: str; is_ai: bool = False

@dataclass(frozen=True)
class ActionOutcome:
    rejection: str | None        # §13 코드
    state: GameState
    ended: bool

async def create_game(*, mode, is_ranked, players: Sequence[SeatPlayer], room_code=None, rng=None) -> GameState
async def load_game(game_id) -> GameState | None             # schema_version 불일치 → StateVersionMismatch
async def get_meta(game_id) -> GameMeta | None
async def move(game_id, user_id, row, col) -> ActionOutcome
async def place_wall(game_id, user_id, row, col, orientation) -> ActionOutcome
async def surrender(game_id, user_id) -> ActionOutcome
async def eliminate(game_id, seat_no, reason) -> ActionOutcome   # 6단계 스위퍼(time/disconnect_forfeit)가 호출
async def void_lost_game(game_id) -> None                       # 6단계 fail-safe 가 호출
```

- **행동 경로(공통 `_act`):** 락 → `GET state` → `from_dict` → meta 로 `user_id → seat_no` 매핑(좌석이 아니면 `not_in_game`) →
  엔진 호출 → **결과와 무관하게 펜싱 저장**(거절도 `wall_rejections` 를 바꾼다) → 종료면 `_finalize` → 락 해제
- **생성 순서:** DB `create`(진행 중 기록) → Redis `state`·`meta` → 사람 좌석의 `activity` 를 `game:{id}` 로 전이. DB 를 먼저 쓰는 이유는
  §8 fail-safe 가 "DB 에는 진행 중인데 Redis 상태가 없다"를 유실 판정 기준으로 쓰기 때문이다. Redis 쓰기가 실패하면 DB 행을 `void` 한다.
  DB 가 없으면(`is_db_available()` false) 기록 없이 진행한다(graceful degradation)
- **`_finalize` (standings → SeatResult):** `rank` 는 `standings()` 값을 그대로 쓴다. `result` 는 rank 1 = `win`, 나머지 = `lose` 이다
  (rank 1 은 항상 단독 — 위 사실). `elimination_reason` 은 `Player` 에서 가져온다. `mmr_*` 는 `None`(MMR 산정은 인증·MMR 작업 몫).
  `end_reason`·`winner_seat_no`·`turn_count` 는 state 에서 가져온다 → `record_result`. 이어서 state·meta 에 `EXPIRE game_finished_ttl_sec`
  (재접속자가 `game_end` 를 받을 수 있게), 사람 좌석의 `activity` 를 해제한다. **DB 쓰기가 실패해도 게임 종료는 확정한다**(로그만 남긴다.
  재시도는 범위 밖)
- **오류 표면:** Redis 호출부는 `redis.exceptions.RedisError` 를 `StoreUnavailable` 로 감싼다(E7). 진입 시 `is_redis_available()` 가 false 면
  즉시 `StoreUnavailable`. 락 대기 초과는 `GameBusy`. 7단계 핸들러가 이것들을 §13 코드로 바꾼다

## 판단 4 — 매치메이킹·방 서비스

`app/services/matchmaking.py`, `app/services/rooms.py` — 둘 다 게임 무관(`game` 인자).

- 매치메이킹: `join(game, mode, user_id, nickname, mmr) -> QueueStatus`, `leave`, `status`, `try_match(game, mode, rng) -> PendingMatch | None`
  (join 이 호출한다), `mark_ready(match_id, user_id) -> PendingMatch | GameState`(전원 준비되면 `create_game(is_ranked=True)`),
  `expire_match(match_id)`(6단계 스위퍼가 호출. 응답한 쪽만 원래 점수로 복귀), `mmr_window(...)`(비활성)
- 방: `create_room(game, mode, user_id, nickname) -> Room`, `join_room(code, ...)`(정원 = `get_layout(mode).seats`. 초과 시 `RoomFull`),
  `leave_room(user_id) -> LeaveOutcome`(호스트가 나가면 해산하고 남은 user_id 목록을 돌려준다. 게스트가 나가면 seat_no 를 다시 매긴다),
  `set_ready`, 전원 준비 시 `create_game(is_ranked=False, room_code=…)`. 방 seat_no = 게임 seat_no(결정 2)
- 오류는 도메인 예외(`AlreadyBusy`, `RoomNotFound`, `RoomFull`, `RoomStarted` …)로 둔다. 메시지 문구가 아니라 §13 코드와 1:1 로 매핑할 수 있게 한다

## 실행 비용

장시간 연산이 없다. 엔진 자가대전이나 대량 시뮬레이션 같은 작업이 없고, Redis 테스트는 테스트당 수 ms~수십 ms 이다.

- **추정:** 추가 테스트 약 60건, 전체 `server-test` 증가분 10초 이하
- **기준선:** 커밋 1 전에 `docker compose run --rm server-test` 소요 시간을 한 번 재서 커밋 메시지에 적는다
- **중단 조건:** 전체 실행이 기준선 + 2분을 넘으면 멈추고, 원인(락 대기 루프, 픽스처 정리 누락)을 확인한 뒤 진행한다. 이 경우 CPU 상한 4(`--cpus 4`)와 분리 실행을 적용한다

## MUST / MUST NOT

- MUST: 커밋마다 `docker compose run --rm server-test` 전체 통과
- MUST: Redis 를 쓰는 진입점은 `is_redis_available()` 로 가드하고 `RedisError` 도 처리한다(E7)
- MUST: 테스트는 논리 DB 1. 픽스처가 이를 강제하고 FLUSHDB 는 쓰지 않는다
- MUST: 설정값은 `app/core/config.py` 에만 둔다. 키 문자열은 `redis_keys.py` 에만 둔다
- MUST: 인원 수는 `get_layout(mode).seats` 에서만 얻는다. 테스트는 quad 행 추가만으로 통과해야 한다
- MUST NOT: `main.py` 라우터 등록, WS 핸들러 작성(7단계)
- MUST NOT: Pub/Sub 발행·구독, `connection_manager` 수정(4단계). 시야(5단계). 시계·ZSET·스위퍼·서버 유예(6단계)
- MUST NOT: 의존성 추가(`fakeredis` 등). 실제 Redis 컨테이너로 테스트한다
- MUST NOT: 엔진(`games/maze/core/*`)과 `GameSessionRepository` 의 동작 변경. 필요하면 멈추고 보고한다
