# M3 7단계 — maze WS 핸들러 · 배선 · 다중 워커 완료 판정

## Context

ROADMAP M3 실행 순서 7단계(마지막). 1~6단계로 엔진·Redis 상태·Pub/Sub·시야·시간 체계가 **서비스 계층까지** 완성됐지만
클라이언트가 접속할 길이 없다. WS 라우터가 없고(`main.py` 에 등록된 것은 구 `/users`·`/ranking` 뿐), 구독 버스·스위퍼·서버 유예가
lifespan 에 걸려 있지 않으며(배포하면 아무도 만료를 처리하지 않는다 — 검토 L25), prod 는 `--workers 1` 로 묶여 있다.

7단계는 maze.md §12 메시지 24종(어휘 25종, `turn_timeout` 폐기)의 핸들러를 새로 쓰고, lifespan 에 배선하고, 6단계 독립 검토가
넘긴 항목(H4 나머지·M9·L19·L23·H8 나머지·M18-2·7)을 처리한 뒤, **실제 uvicorn 워커 2개 + 실제 Redis 장애**로 ROADMAP
"완료 판정"을 확인하고 prod 를 `--workers 2` 로 올린다.

**진행 규칙:** 커밋마다 검증 관문 G1~G5(plans/README "검증 관문과 독립 검토"). 2.5단계 보류는 예외일 뿐 전제가 아니다.

**사용자 결정 (2026-10-05, 이 계획 수립 중):**
1. **인증 = 검증만 + 신원 조회 인터페이스.** §1.3 access token 검증(typ·auth·exp·서명)과 close 4001~4003 만 구현한다. 닉네임은 DB
   `users`, MMR 은 초기값 1000 임시 — `IdentityDirectory` 프로토콜 뒤에 둔다. 토큰 발급(`/auth/*`)·users 개편은 인증 작업 몫
2. **한 계획서 3부 + 독립 검토 2회.** A 핸들러·와이어·인증 / B 배선·이관·레이트 리밋 / C 실제 다중 워커·장애 실측. 검토는 B 끝(코드
   전체)과 C 끝(하네스·실측 보고서)
3. **레이트 리밋 = 소켓별 메모리 토큰 버킷 + 접속(핸드셰이크)은 Redis 논리 DB 2 유저 단위.** 초과 → `error rate_limit_exceeded`
   (처리·락 없음), 지속 → close 1008. 같은 계정 연결을 클러스터 전체에서 하나로 강제(아래 판단 4)하므로 버킷이 사실상 유저 단위다
4. **`allow_spectate` 변경 = 대기 중인 방장이 `create_room` 재전송.** mode 는 그대로, `allow_spectate` 만 바꾼다. 새 타입 없음

## 판단

### 1. 와이어 대응 — 내부 이벤트 → §12

`delivery` 가 유일한 대응 지점이다. 서비스·이벤트 이름(내부)은 바꾸지 않고 수신자별 메시지만 §12 로 만든다.

| 내부 | §12 메시지 (수신자별) |
| :--- | :--- |
| `game_started` | `game_start`(mode·is_ranked·`players[]`·`my_seat_no`) → `game_state` → `turn_change`(`last_action: null`) |
| `game_updated` move/wall | `game_state` → `turn_change`(`last_action {seat_no, kind}`) — 종료면 `turn_change` 대신 `game_end` |
| `game_updated` eliminated | `player_left`(`state: eliminated`, `reason`, `survivors`) → `game_state` → `turn_change`(`last_action: null`) 또는 `game_end` |
| `seat_disconnected` | `player_left`(`state: reconnecting`, `reason: null`, `grace_remaining_ms`, `survivors`) |
| `seat_reconnected` | `player_joined`(`seat_no`, `state: "reconnected"`) — 게임 범위 재사용. 새 타입 없음 |
| `game_voided` | `game_end`(`reason: server_fault`, 전원 `result: void`, `full_board` = state 가 남았으면 채움 / 유실이면 `null`) |
| `matched` | `matched`(`match_id`·`my_seat_no`·`players[]{seat_no, nickname, mmr}`·`ready_deadline_sec`) — §3 예시의 `game_id` 는 `match_id` 로 정정(게임은 ready 뒤 생긴다) |
| `match_ready` | `player_ready`(`seat_no`) |
| `match_expired` | 복귀자 `queue_status`(`requeued: true`), 탈락자 `queue_status`(`requeued: false`, `position: 0`) |
| `room_updated` + `change` hint | 행위자 외에게 `player_joined` / `player_ready` / `player_left` (+ 항상 최신 스냅샷 `room`). 행위자는 핸들러 응답(`room_created`·`room_joined`, `ack_seq`)으로 받는다 |
| `room_dissolved` | `player_left`(`seat_no: 1`, `room_closed: true`) |

- `rooms.py` 발행에 `change: {kind: created|joined|left|ready|settings, seat_no}` hint 를 더한다(공개 정보만 — 방은 비밀이 없다)
- **수락된 행동에는 직접 응답이 없다.** 행위자도 수신자이므로 버스 경로 하나로 받는다(출처 하나). 거절만 `error`(`ack_seq`)
- `turn_change.clocks` = `[{seat_no, remaining_ms, connection_remaining_ms, connected}]`, `clock_expires_at` = ISO 8601 UTC 문자열
  (끝난 게임이면 `null`). `game_state.clocks` 도 같은 모양(§8 "turn_change.clocks 와 game_state 로 공개"). `voided` 필드는 내보내지 않는다
- `queue_joined.estimated_wait_sec` 은 `null`(근거 데이터 없음), 주기 `queue_status` 는 워커별 티커(판단 6)
- `game_end.results[].mmr_*` 는 랭크전도 `null` — MMR 산정은 인증·MMR 작업 몫(임시, maze.md §10 에 명시)
- **`game_end` 는 재동기화에서도 나간다** — 끝난 게임(종료 TTL 300 s 안)에 재접속하면 최종 `game_state` + `game_end`

### 2. `full_board` — 읽을 때 만든다

종료(`state.is_finished`) 또는 무효(`clocks.voided`)인 state 에서 `delivery` 가 `walls`(2칸)·`final_positions` 를 만든다. 별도 저장 없음.
진행 중 state 로는 **만들 수 없게** 빌더가 `ValueError` — 경기 중 전체 맵이 나갈 경로를 함수 수준에서 막는다. 무효 게임: 장기 장애
무효는 state 를 보존하므로(6단계 M13) 채우고, **상태 유실 무효는 `null`**(잃은 것을 보여줄 수 없다). 결과 목록은 meta 가 있으면
meta, 없으면 빈 배열.

### 3. 이벤트 버전 (L23)

게임별 단조 카운터 `game:{id}:version`(STRING int). `_run` 의 MGET 에 넣고, outbox 이벤트마다 +1 한 값을 `seq` 로 매기고, 같은
`fenced_write` 로 기록한다 — 커밋된 이벤트만 번호를 받는다. `create_game` MULTI 에서 1(=`game_started`), 유실 무효는 지우기 전에
읽은 값 +1. 와이어는 게임 범위 서버 메시지 봉투의 최상위 `version`(재동기화 `game_state` 는 현재 값). `turn_count` 와 분리한다.
클라이언트 규칙(§1): `version ≤ 마지막 값` 이면 중복으로 버린다. 키 표·`_void_lost` 삭제 목록·종료 TTL 에 포함.

### 4. 같은 계정 연결은 클러스터에 하나 (4000 보강)

연결 수락 시 `SET user:{uid}:conn <WORKER_ID>:<토큰> GET`. 이전 값이 있으면 사용자 범위 이벤트 `session_replaced`
(`EVENT_SCOPES` 에 `user` 추가, 채널 `{ns}:user:{uid}:events`)를 발행하고, 그 유저의 로컬 연결 id 가 다른 워커는 옛 소켓을 4000 으로
닫으며 `replaced` 표시를 한다. **옛 소켓의 끊김은 기록하지 않는다** — 이중 방어: ① 핸들러가 `replaced` 면 건너뛴다 ② 서비스
`mark_disconnected(worker_id=…)` 가 좌석 owner 가 다른 워커면 무시한다(새 연결의 `mark_connected` 가 먼저 owner 를 옮긴 경우).

### 5. 끊김 배선 — 순서·소급·재시도·소유

| 항목 | 설계 |
| :--- | :--- |
| 연결 수락 | 인증 → 핸드셰이크 리밋 → 연결 맵 등록 → 세션 키(판단 4) → `connected` → 활동이 game 이면 `mark_connected(worker_id=WORKER_ID)` **후** `resync` |
| 게임 시작 | 버스가 `game_started` 를 로컬 수신자에게 전달할 때 `mark_connected(worker_id)` 로 owner 를 기록한다 — 시작 직후 크래시도 스위퍼가 찾는다(조사 사실의 H4 공백) |
| 소켓 종료 | `replaced` 가 아니고 활동이 game 이면 `mark_disconnected(game, uid, worker_id, at_ms)` 를 **추적되는 태스크**로. 성공하면 `RecentDisconnects` 에 기록 |
| 재시도 (H4) | `GameBusy`·`StoreUnavailable` 이면 워커 로컬 재시도 큐에 **원래 at_ms** 로 넣고 1 s 주기로 `disconnect_retry_max_sec`(120) 까지. 종료 시 남은 항목은 한 번 더 시도하고, 그래도 남으면 그 워커의 하트비트가 끊긴 뒤 다른 워커 스위퍼가 `drop_seat` 로 처리한다(owner 가 그대로이므로) |
| 소급 (L19) | ping 타임아웃 종료면 `at_ms = max(종료 − (ping_interval + ping_timeout), 마지막 수신 메시지, 연결 수락)`. 다른 종료 코드는 소급 없음. **close code 가 ping 타임아웃을 구분하는지는 B2 첫 단계 파일럿으로 실측**(판정 규칙: 타임아웃 = 1011 이고 RST·정상 종료가 1011 이 아니면 채택, 아니면 멈추고 질문). 클라이언트가 1011 을 직접 보내면 **자기에게 불리**하게 소급되므로 악용 경로가 아니다 |
| 서비스 변경 | `mark_disconnected(…, *, worker_id=None, at_ms=None)` — at 은 `max(at_ms, clocks.latest_ms())` 로 클램프(`drop_seat` 와 같은 규칙), owner 불일치면 None. **시계 규칙은 바꾸지 않는다**(기록 시각의 출처만) |
| ping 설정 | `ws_ping_interval_sec`(10)·`ws_ping_timeout_sec`(10)·`ws_max_size_bytes`(4096) 를 config 에 두고 Dockerfile prod CMD 에 같은 값. **값 일치 가드 테스트**(Dockerfile 파싱)로 어긋남을 잡는다. 최대 무료 구간 40 s → 소급 후 ≈ RTT |

### 6. lifespan · 런타임 (M9 포함)

`app/ws/runtime.py` 의 `Realtime` 하나가 버스·스위퍼·큐 티커·`RecentDisconnects`·끊김 태스크 집합·재시도 큐·draining 시각을 갖는다.

```
startup : init_db → init_redis → (Redis 있으면) bus.start → sweeper.start → queue_ticker.start → SIGTERM/SIGINT 훅
shutdown: (uvicorn 이 이미 1012 로 닫음) → 끊김 태스크·재시도 마무리 대기(상한 server_grace_window_ms)
          → apply_on_shutdown(since = draining_at − window) → queue_ticker.stop → sweeper.stop → bus.stop → close_redis → close_db
```

- **M9:** 시작 시 uvicorn 이 설치한 SIGTERM/SIGINT 처리기를 감싸 먼저 `draining_at` 을 찍는다(단조 시계 → 첫 Redis TIME 으로 환산).
  `apply_on_shutdown` 은 그 시각 이후(− 창)의 끊김 전부를 본다 — lifespan 이 늦거나 E4 처럼 두 번 끊겨도 유예가 남는다. 신호를 못
  봤으면(테스트·reload) 지금처럼 lifespan 시각
- Redis 가 기동 시 없으면 실시간 구성요소를 띄우지 않고, WS 엔드포인트는 인증 후 1013 으로 닫는다
- `/health` 에 `realtime: {worker_id, bus: {subscribed, resubscribes}, sweeper: {running, last_tick_ok, last_tick_at_ms}, connections}`
- `connected.worker` 는 `ws_expose_worker`(기본 false) 일 때만 — 하네스 전용. 운영은 기본값

### 8. 보안·누설 원칙 (판단 기준 3·4)

- `user_id` 는 토큰 `sub` 에서만. 페이로드는 타입별 pydantic 모델로 받고 **정의되지 않은 필드는 버린다**(`seat_no`·`user_id`·시각을 넣어도
  무시) — 좌석은 `meta.seat_of`, 시각은 서버
- 좌표 범위 검사는 엔진 몫(§7 "범위 밖은 세지 않는다"를 지키려면 pydantic 이 먼저 거르면 안 된다) — 모델은 **타입만**(StrictInt·Literal)
- `error.message` 는 코드별 **고정 문구 표**에서만. 예외는 서버 로그로만, 소켓에는 `internal_error`. `ActionOutcome.state` 를 직렬화하는 경로 없음
- 로그 필터가 `token=` 쿼리 값을 `***` 로 바꾼다(uvicorn·앱 로거). 토큰·좌표를 앱 로그에 남기지 않는다
- 탈락자: 행동·`chat` → `not_in_game`(chat 은 생존자도 `feature_disabled`). `leave_room` → 탈락 좌석이면 activity 해제(결과는 종료 시
  그대로 기록), 생존 좌석이면 항복(§9)

## C — 실제 다중 워커 하네스 (판정 기준을 먼저 못박는다)

**형태:** pytest 가 아니라 독립 compose 프로젝트 `server/harness/multiworker/`(`-p m3s7`) — 이미지는 `server/Dockerfile` **prod 타깃**
그대로 + `--workers 2`, Redis(개발과 같은 다이제스트·인자), Postgres. 클라이언트는 `websockets`(고정 의존성)로 쓴 시나리오 스크립트.
이유: 실제 프로세스·신호·`CLIENT KILL`·컨테이너 pause 는 pytest 안에서 재현할 수 없고, 기본 테스트 시간에 넣으면 안 된다.
하네스 환경값: 짧은 시계(`CLOCK_INITIAL_MS=3000`, `CONNECTION_BUDGET_MS=8000`), `WS_EXPOSE_WORKER=true`, `JWT_SECRET`(하네스 전용),
users 행은 하네스가 SQL 로 심는다. 워커 분포가 치우치므로 좌석이 두 워커에 갈릴 때까지 재접속(상한 50회, 넘으면 실패).

| S5 | (a) 앱 연결 전체 `CLIENT KILL TYPE normal` (b) Redis 재시작 (c) Redis `pause` 10 s (d) `pause` 125 s — d 만 1회 | a·b: 2 s 안 행동 성공, 무효·시간패 0, b 는 장애 미기록 · c: 장애 1건 기록, 현재 좌석 잔량 변화 ≤ 1.5 s · d: 진행 중 전원 `game_end server_fault` + `full_board`, DB `void` |
| S6 | 좌석 연결 중 `docker compose stop -t 30`(SIGTERM) → 재기동 → 5 s 뒤 재접속 | 접속 시계 감소 ≤ 1 s(유예 없으면 ≈5 s — 대조군 1회), 게임 시계는 8 s 상한 안 정지. 로그에 `token=` 원문 0 |
| S7 | 반개방 — 원시 소켓이 ping 에 답하지 않고 침묵 | 서버 종료 ≤ interval+timeout+1 s, 기록된 끊김 시각이 침묵 시작 ±(interval+0.5 s) 안 |
| S8 | 같은 계정을 A 에서 B 로 다시 접속 | 1 s 안 A 소켓 4000, 상대에게 `player_left` 0, 시계 `connected` 내내 true |
| S9 | 차례 아닌 좌석이 500 메시지 연타 + 분당 30회 재접속 | `rate_limit_exceeded` → 1008, 재접속 1013. 그동안 상대 행동 왕복 p99 ≤ 50 ms(평시 대조), 상대 시계 차감 = 실제 사고 시간 ±200 ms |

**시간 추정:** 이미지 빌드 3~5 분(캐시 있으면 1 분) / 파일럿 1회(전 시나리오, d 제외) ≈4 분 / 본 실행 3회 ≈12 분 / S5d 1회 ≈2.5 분 →
