## 판단 1 — `game_sessions` 는 "시작·종료 기록"만 담는다

platform.md §5 는 `current_turn → current_seat_no` 로 **이름만 바꾸라고** 적었지만, 이는
0단계(Redis 권위) **이전**에 쓴 문장이다. 진행 중 상태는 Redis `game:<id>:state` 가
권위이므로 DB 에 진행 상태를 두면 이중 기록이 된다. 그래서:

| 컬럼 | 처리 | 이유 |
| :--- | :--- | :--- |
| `game_id` `String(36)` PK | 유지 | |
| **`game`** `String(32)` | 신규 | `maze_1p`… (platform.md §4.2 `(game, mode)`) |
| **`mode`** `String(16)` | `game_mode` ENUM 대체 | 문자열 — 값 추가에 마이그레이션 불필요 (§5 확장성 원칙) |
| `is_ranked` | 유지 | |
| `status` `String(16)` | ENUM → 문자열 | `in_progress` \| `finished` \| `void`. §8 fail-safe 의 "진행 중으로 기록된 게임" 판별에 쓴다 |
| **`end_reason`** `String(16)` nullable | 신규 | `goal_reached` \| `last_standing` \| `server_fault` (maze.md §10) |
| **`winner_seat_no`** nullable | `winner` 대체 | |
| `turn_count` | 유지 | 종료 시 기록 |
| **`started_at`** / **`ended_at`** nullable | `created_at`/`updated_at` 대체 | 기록 테이블은 두 시점만 의미가 있다 |
| `player1_*`, `player2_*` | **삭제** | → `game_participants` |
| `current_turn`, `game_state` | **삭제** | 진행 상태 — Redis 권위 |
| `ai_difficulty` | **삭제** | 온라인 AI 좌석 착수 시 좌석 단위로 다시 정한다 |
| `is_deleted` | **삭제** | REST `DELETE` 전용이었다 (1단계 폐기) |

`status` 에 인덱스 — 6단계 fail-safe 가 진행 중 게임을 훑는다.

**`game_participants`** — platform.md §5 표 그대로:
`(game_id FK ondelete CASCADE, seat_no)` 복합 PK, `user_id` FK nullable(index), `display_name`
`String(50)`, `is_ai`, `result` nullable, `rank` nullable, `elimination_reason` nullable,
`mmr_before`/`mmr_after` nullable. `GameSession.participants` 관계는 `seat_no` 정렬 +
`lazy="selectin"`(async 에서 지연 로딩 불가).

**문자열 값 검증은 리포지토리에서** 튜플 상수로 한다 (`GAME_STATUSES`, `END_REASONS`,
`RESULTS`, `ELIMINATION_REASONS`). DB `CHECK`/`ENUM` 은 두지 않는다 — 값 추가 시 마이그레이션.

## 판단 2 — `GameSessionRepository` 를 3단계가 쓸 형태로 다시 쓴다

구 메서드(`update_game_state`, `get_active_sessions`, `get_recent_sessions`, `abandon_game`,
`hard_delete`)는 행동마다 상태를 쓰던 REST 전제라 **전부 삭제**한다. 새 API:

```python
@dataclass(frozen=True)
class ParticipantSeed:          # 게임 시작 시
    seat_no: int; user_id: int | None; display_name: str; is_ai: bool = False

@dataclass(frozen=True)
class SeatResult:               # 게임 종료 시
    seat_no: int; result: str; rank: int | None
    elimination_reason: str | None = None
    mmr_before: int | None = None; mmr_after: int | None = None

class GameSessionRepository:
    async def create(game_id, *, game, mode, is_ranked, participants: Sequence[ParticipantSeed]) -> GameSession
    async def get_by_id(game_id) -> GameSession | None          # participants 포함
    async def record_result(game_id, *, end_reason, winner_seat_no, turn_count,
                            results: Sequence[SeatResult]) -> GameSession | None
    async def void(game_id) -> GameSession | None               # server_fault — 전원 result=void
    async def list_in_progress(limit: int = 100) -> list[GameSession]
```

- `create`: `seat_no` 가 **1..N 연속·중복 없음**이 아니면 `ValueError`. N 을 가정하지 않는다
- `record_result`: **좌석 전원**의 결과가 있어야 한다(누락·초과 좌석 → `ValueError`). 이미
  끝난 게임이면 `ValueError` — 종료는 한 번이다
- 엔진 `standings()` → `SeatResult` 변환은 **3단계** 몫이다(서비스 계층). 여기서는 받은 값을 검증·저장만

## 판단 3 — 개발 DB 리셋 (사용자 결정 1)

구 `game_sessions` 가 남아 있으면 `create_all` 이 건너뛰어 새 코드와 충돌한다. 1회 실행:

```bash

  "DROP TABLE IF EXISTS game_participants, game_sessions, match_queue, game_rooms, daily_champions CASCADE;
   DROP TYPE IF EXISTS game_status, game_mode, match_queue_status, room_status;"
docker compose restart server     # create_all 이 새 스키마 생성
```

- `users` 는 건드리지 않는다 — 스키마 변경 없음
- 실행 전 `\dt` 로 대상을 확인한다. 스크립트 파일은 만들지 않는다(1회성). 명령은 커밋 메시지와 계획서에 남긴다
