# M3 착수 — 작업 순서 확정 + 0단계 실측 (워커·Redis 동작)

## Context

`docs/ROADMAP.md` M3 의 작업 1~7 을 착수한다. 순서를 정하는 과정에서 두 가지가
드러났다.

1. **작업 3(엔진 N인 일반화)이 작업 1·4 와 같은 자료구조를 건드린다.** 큐·방의
   현 구조(`GameRoom.host/guest`, `MatchResult.player1/player2`)와 DB 모델
   (`player1_*`/`player2_*`, `match_queue`·`game_rooms`)이 모두 2인 전제다.
2. **진행 중 게임 상태(`GameState`)의 위치가 어느 작업에도 속해 있지 않다.**
   지금은 `app/services/quoridor_service.py:40` `_games` — 프로세스 메모리다.
   작업 1 은 "큐·방"만 다룬다. `--workers ≥ 2`(M3 완료 판정)는 이것 없이 성립하지
   않는다. maze.md §8 fail-safe 는 "소유 워커 + 워커 사망 시 무효"를 전제하지만,
   이 전제는 **배포마다 진행 게임 전원 무효**를 뜻한다. 대안은 "Redis 권위 +
   재접속 이어받기"다.

사용자 결정(2026-10-01):
- 2번의 모델 선택은 **uvicorn 워커·Redis 동작을 실측한 뒤에** 한다 → **0단계 신설**
- 서버 원인 끊김을 접속 시계에서 깎을지는 상태 모델 결정 **뒤에** 정한다
- 구 REST `/api/v1/quoridor/*` 는 **M3 에서 폐기**한다 (platform.md §6 이미 결정)
- 이 계획서는 **전체 순서 + 0단계 상세**. 1단계 이후는 착수 시 계획서를 따로 만든다

## 0단계 상세 — 실측

### 목적

"워커가 죽는다"가 실제로 무엇이고, 그때 소켓·상태·Redis 가 어떻게 되는지를
**측정값으로** 확정한다. 그 위에서 게임 상태 모델(소유 워커+무효 vs Redis 권위+
이어받기)을 고른다.

### 대상 버전 (고정값 그대로)

`uvicorn[standard]==0.40.0`, `websockets==16.0`, `fastapi==0.128.0`,
`redis[hiredis]==8.1.0`, Redis 이미지 `redis:8-alpine@sha256:3811…`.
**전부 Docker 컨테이너 안에서** 측정한다 (로컬 툴체인 없음).

### 실험 목록

| # | 질문 | 방법 | 기록할 값 |
| :--- | :--- | :--- | :--- |
| E1 | `--workers 2` 에서 WS 연결은 워커에 어떻게 분배되나. 재접속은 같은 워커로 가나 | 최소 FastAPI 앱이 응답에 `os.getpid()` 를 실어 보낸다. 클라이언트 N 회 접속·재접속 | 워커별 분포, 재접속 시 PID 동일 비율 |
| E2 | 워커 하나가 `kill -9` 되면 그 위 소켓은? 마스터가 워커를 재기동하나? 다른 워커 소켓은? | 연결 유지 중 한 PID 를 SIGKILL | 클라이언트 close code, 재기동 여부·소요 시간, 타 워커 연결 생존 |
| E3 | 정상 종료(SIGTERM, `docker stop`)에서 열린 WS 는? lifespan shutdown 은 소켓이 닫히기 전에 도나 뒤에 도나 | 연결 유지 중 컨테이너 stop | close code(1001/1012?), lifespan 훅 실행 순서·남은 시간, `--timeout-graceful-shutdown` 영향 |
| E4 | **배포 = 컨테이너 교체.** 구 컨테이너 종료 ~ 신 컨테이너 수락까지 공백은 몇 초인가. 접속 시계 60초 안인가 | `docker compose up -d --force-recreate server` 동안 클라이언트가 재접속 루프 | 공백(ms), 재접속 성공까지 시간 |
| E5 | Pub/Sub 은 워커 간 실제로 전달되나. 구독자 재연결 중 발행된 메시지는? | 워커 A 발행 → 워커 B 구독. B 의 Redis 연결을 끊었다 붙임 | 지연 p50/p99, 유실 건수 |
| E6 | 게임별 락 + 상태 읽기/쓰기 비용 | `SET NX PX` 락 → `GET` JSON → 적용 → `SET` → 해제. 동시 행동 경합 | 행동 1건 왕복 p50/p99, 경합 시 직렬화 정확성 |
| E7 | Redis 가 재시작되면 (AOF `--appendonly yes`) 앱은? 상태는 남나 | 상태 기록 중 `docker restart gamemoa-redis` | redis-py 재연결 동작, 데이터 보존 여부, `is_redis_available()` 전이 |

> E4 가 가장 중요하다. 이어받기 모델의 성립 여부가 "배포 공백 < 접속 시계"에
> 달려 있고, 이 값은 배포 방식(단일 컨테이너 교체 vs 롤링)에 따라 달라진다.

### 판정 규칙 (측정 전에 못박는다)

- E4 공백이 접속 시계(60초)보다 **충분히 작고**(기준: 10초 이하) E6 p99 가 행동
  처리 예산 안(기준: 20ms 이하)이면 → **Redis 권위 + 이어받기**
- 그렇지 않으면 → **소유 워커 + 무효** 유지, 대신 배포 절차(드레인)를 설계 항목으로 추가
- 기준값 자체가 틀렸다고 판단되면 결정하지 않고 사용자에게 측정값을 들고 묻는다
- **측정 1회로 결론 내지 않는다.** 각 실험 최소 3회, 편차를 함께 기록한다
  (메모리 규칙: 측정값과 기록이 어긋날 때 교차 검증)
