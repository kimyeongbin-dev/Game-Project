# M3 5단계 — 시야 엔진 (Fog of War)

## Context

ROADMAP M3 실행 순서 5단계. 4단계에서 좌석별 화면의 자리(`app/services/maze_view.py` `vision_fields`)를 만들었지만
**빈 시야**를 돌려준다(남의 좌표·벽을 흘리지 않는 기본값). 그래서 지금 게임 화면에는 내 위치 말고 아무것도 없다.

5단계는 이 자리를 실제 값으로 채운다.

- **순수 시야 계산**(엔진, 프레임워크 무의존): 위치 + 벽 → 보이는 칸·변·말
- **좌석별 누적 상태**(`discovered_edges`·`last_seen_players`)를 Redis 에 게임 수명 동안 보관
- 수락된 행동마다 좌석 전원의 누적 상태를 **state 와 같은 락·같은 펜싱 쓰기 한 번**으로 갱신
- `vision_fields` 를 저장된 누적 상태를 받는 서명으로 바꾼다. 재접속·재구독 재동기화는 `game_view` 를 거치므로 자동 복원

**전제 (ROADMAP 2.5단계 보류 인용문):** 검증 없이 진행하고, 문제가 생기면 교체·수정으로 대응한다. 단계마다 테스트 전체 통과는 지킨다.

## 판단 1 — 시야 모델: 반지름 1.25 원 + 벽 차폐 (사용자 답, 2026-10-02)

> 사용자: "각 칸을 1×1 정사각형이라 했을 때, 시야는 가운데 칸의 중심을 기준으로 지름 2.5 정도의 원.
> 12시 방향에 벽이 있다면 11시~1시 90도 정도가 차폐되고, 11시·1시 칸에 말이 있다면 말의 일부가 보여
> 거기 말이 있구나를 인식할 수 있다."

이 기하 모델이 정본이고, 설계서의 이산 규칙은 그 정확한 이산화다. 기하로 유도하면:

| 대상 | 보이는 조건 (P = 내 칸) | 기하 근거 |
| :--- | :--- | :--- |
| 직교 칸 X (b d e g) | 보드 안이고 `P｜X` 에 벽이 없다 | X 로 가는 모든 시선이 `P｜X` 를 지난다 |
| 대각 칸 D (a c f h) | 두 직교 이웃 X 중 하나라도 **X 가 보이고 `X｜D` 에 벽이 없다** | D 로 가는 시선은 (모서리 한 점을 빼면) `P｜X₁→X₁｜D` 또는 `P｜X₂→X₂｜D` 를 지난다 |
| `P` 의 4면 | 보드 안이면 **항상** (벽이든 아니든) | 반지름 0.5 안 |
| 바깥 고리 변 8개 (`X｜D`) | **그 변이 붙은 직교 칸 X 가 보일 때만** | 시선이 `P｜X` 를 지나야 닿는다. 대각 D 쪽에서는 닿지 않는다 |
| 3×3 외곽 테두리 | **절대 아니다** | 거리 1.5 > 반지름 1.25 |
| 말 | 그 칸이 보이면 보인다 (일부만 보여도) | 사용자 답 |

**설계서 표의 "보이는 칸에 접한 내부 변" 은 "보이는 *직교* 칸(또는 P)에 접한 내부 변" 으로 정밀화한다.** 예시 1·2 는
이 규칙과 정확히 일치한다(a｜b: a 는 보이지만 b 가 안 보여 전송 안 함 / e｜h: h 는 보이지만 e 가 안 보여 전송 안 함).
규칙 변경이 아니라 예시와 표의 어긋남을 바로잡는 것이다.

**검증 방법 (사용자 지적 반영 — 전수는 과하다, P 기준 5×5 만):** 3×3 내부 변에 걸칠 수 있는 벽은 **P 를 중심으로 한
5×5 안의 벽 자리 32개**(교차점 4×4 × 방향 2)뿐이다. 테스트에 원 모델을 그대로 구현한 **독립 오라클**(시선 표본 + 선분 교차)을
두고, 내부 칸 P 하나에 대해 그 32자리의 **실제로 놓을 수 있는 벽 1개·2개 조합**(≈ 500)에서 이산 규칙과 같은지 확인한다.
예시 2 처럼 대각이 완전히 막히는 경우도 벽 2개 안에 들어온다. 보드 가장자리·꼭짓점은 손으로 쓴 사례로 덮는다.

## 판단 2 — 변 원소: 보이는 변 전부 + `wall` 여부

원 모델에서 플레이어는 변을 **본다** — 벽이 있으면 벽을, 없으면 열린 통로를. 열린 변을 본 것도 관측이다.

- `visible_edges`·`discovered_edges` 의 원소를 `{row, col, orientation, wall: bool}` 로 한다(필드 1개 추가 — maze.md §6 개정)
- 예시 1 의 "전송하는 변 / 전송 안 함" 과 "내 4면은 언제나 전송된다" 를 문자 그대로 만족한다. 벽만 보내면 "내 4면" 중
  열린 면은 *전송되지 않는* 셈이다
- **열린 통로도 발견 맵에 남는다** — 재접속해도 탐사한 지도가 그대로 복원된다(§9 "재접속 시 시야"). 벽만 저장하면
  재접속 후 "가 본 길" 과 "모르는 곳" 을 구분할 수 없다
- 누적의 단조성: 변 하나의 상태는 `미발견 → 열림 → 벽` 으로만 바뀐다(벽은 사라지지 않는다). 열림으로 본 변에 나중에
  시야 밖에서 벽이 서면 **다시 볼 때까지 열림으로 남는다** — `last_seen_players` 처럼 낡은 정보이고, 서버가 채워 넣지 않는다
- 정보량: 보이는 변 ≤ 12, 발견 변 ≤ 144(9×8×2). 패킷 크기 문제 없음

> 이 판단은 질문의 두 선택지 중 하나를 사용자가 고른 것이 아니라, 사용자의 원 모델에서 유도했다. 계획 승인으로 확정한다.

## 판단 3 — 탈락 좌석: 말은 못 하고 구경만 한다 (사용자 결정, 2026-10-02)

탈락자는 게임에 남아 **끝까지 진행을 받고, 종료 시 순위를 받는다.** 아무것도 보낼 수 없다(행동은 이미 `not_in_game`,
`chat` 은 §12 에서 유보 — 추가될 때 탈락자 발신은 막는다). 구경하지 않고 나가도 결과는 종료 시 DB 에 그대로 기록된다
(`_finalize` 가 좌석 전원을 기록한다 — 이미 그렇다). 무엇을 구경하는지는 방 설정이 정한다.

| 게임 | 탈락자 화면 |
| :--- | :--- |
| **랭크전**, 또는 친구 방에서 관전 전환 **끔**(기본) | **눈을 감는다.** 탈락한 행동 직전까지의 발견 맵을 동결(탈락 행동에서 그 좌석을 갱신하지 않는다). `visible_edges = []`, `visible_players = []`. 공개 정보(턴·`last_action`·남은 벽·탈락)는 계속 받는다 |
| 친구 방에서 관전 전환 **켬** | **관전 패킷**: `spectator: { walls: [2칸 벽 전부], positions: [{seat_no, position} 전원], views: [{seat_no, visible_edges, visible_players, discovered_edges, last_seen_players} 생존자마다] }`. 클라이언트가 "전체 판" 과 "생존자 한 명 따라가기" 를 **서버 상태 없이** 고른다(누구를 보는지 서버가 기억하지 않는다) |

- 근거(랭크): 3인 이상에서 **일부러 항복해 길목의 와드가 되는 담합 경로**를 막는다
- 근거(친구): 방장이 켠 친선전이라 담합 위험을 감수한다. 랭크는 **항상 끔**이다 — 매칭 경로는 이 값을 받지 않는다
- 설정은 **방 생성 옵션 `allow_spectate`**(기본 false)이고, 게임 시작 시 `GameMeta.spectate_on_elimination` 에 복사된다(불변).
  화면 분기는 meta 만 본다 — 방이 사라져도 게임은 같은 규칙으로 끝난다
- 탈락자의 **말**은 남들에게 계속 보인다(§9) — `visible_players`·`last_seen_players` 에 그대로 나온다
- 탈락자의 메시지 차단·"구경 안 하고 나가기"(activity 해제) 는 핸들러 몫이라 **7단계**다(경계 표)

## 판단 4 — 같은 칸의 여러 말

설계서가 이미 정했다(§5 "같은 좌표가 복수 등장할 수 있다"). 원소는 **좌석당 하나**, 묶지 않는다.
`visible_players: [{seat_no, position}]` 를 seat_no 오름차순으로. 내 칸 P 는 항상 보이므로 내 칸에 겹친 말은 항상 보인다.
`others[].visible` 은 `visible_players` 의 seat_no 집합에서 정한다(4단계 그대로).

## 판단 5 — 순수 모듈 `app/games/maze/core/vision.py`

```python
@dataclass(frozen=True, order=True)
class UnitEdge:              # 관측 단위 (칸 기준) — §6 좌표 규약
    row: int; col: int; orientation: Orientation

def unit_edges(wall: Wall) -> tuple[UnitEdge, UnitEdge]   # 2칸 벽 → 단위 변 2개
def edge_between(a: Position, b: Position) -> UnitEdge     # 직교 인접 두 칸의 경계

@dataclass(frozen=True)
class Sight:                 # 지금 이 순간 보이는 것
    cells: frozenset[Position]
    edges: dict[UnitEdge, bool]          # 변 → 벽 여부
    players: tuple[tuple[int, Position], ...]

def sight(origin: Position, blocked: AbstractSet[UnitEdge],
          others: Iterable[tuple[int, Position]]) -> Sight
def game_sight(state: GameState, seat_no: int) -> Sight    # 벽 → blocked 집합, 다른 좌석 전원(탈락 포함)

@dataclass(frozen=True)
class SeatMemory:            # 누적 — Redis game:{id}:vision:{seat_no}
    edges: dict[UnitEdge, bool]
    last_seen: dict[int, tuple[Position, int]]   # seat_no → (위치, 목격 턴)
    def observe(self, s: Sight, turn: int) -> "SeatMemory"   # 새 객체. 변은 덮어쓰기(벽이면 계속 벽), 보인 좌석만 덮어쓰기
    def to_dict / from_dict   # VISION_SCHEMA_VERSION = 1
```

- `sight` 는 **단위 변 집합**을 받는다(엔진 상태와 분리돼 테스트가 단순해진다). 운영 경로는 `game_sight` 가
  `unit_edges` 로 집합을 만든다 — `WallManager` 를 고치지 않는다
- `unit_edges` 와 엔진의 이동 차단이 어긋나지 않음을 모든 벽 자리(8×8×2=128)에서 `is_move_blocked` 와 대조한다
  (시야와 이동 판정이 다른 벽을 보는 일이 없게)
- 인원 수를 쓰지 않는다. `others` 는 좌석 목록에서 나온다
- 엔진 검증 로직(`move_validator`·`pathfinder`·`game_state` 의 move/place_wall)은 건드리지 않는다

## 판단 6 — 저장: 좌석별 STRING, state 와 한 번의 펜싱 쓰기

| 키 | 타입 | 값 | TTL | 쓰는 쪽 | 읽는 쪽 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `game:{id}:vision:{seat_no}` | STRING | `SeatMemory.to_dict()` JSON `{v, edges:[[row,col,"h"\|"v",wall]…], last_seen:[{seat_no,row,col,turn}…]}` | state 와 같다(진행 중 없음 / 종료 후 `game_finished_ttl_sec`) | 게임 서비스 — 생성 시 MULTI, 행동 시 state 와 같은 Lua | `game_view`(자기 좌석 키만), 게임 서비스 |

- **좌석별 키**(예약 행 그대로): 화면을 만들 때 **자기 좌석 키만** 읽는다. 남의 발견 맵을 읽는 코드 경로가 화면 쪽에 생기지 않는다
- **원자성:** `redis_lock.py` 에 `fenced_mset(redis, lock_key, token, {key: value}, ex)` 를 추가한다 — Lua 한 번이 토큰을
  확인하고 state + 좌석 전원의 vision 을 같은 EX 로 SET 한다. `fenced_set` 은 1키 경우로 위임한다(동작 동일).
  나눠 쓰면 그 사이 장애에서 state 는 다음 턴인데 발견 맵은 이전 턴이 되고, 그 턴의 목격(`last_seen`)은 **영구히** 사라진다
- **`_act` 순서:** 락 → MGET(state, meta) → 판정 → 수락이면 MGET(vision × 좌석 수) → 생존 좌석만 `observe` → `fenced_mset`(state +
  **모든** 좌석 vision — 동결된 좌석도 다시 써서 종료 TTL 을 같이 받는다) → 종료 처리 → 발행. 거절이면 지금처럼 state 만
- **생성:** `create_game` 의 MULTI 에 좌석 전원의 초기 관측(turn 0)을 함께 SET 한다
- **`void_lost_game`:** meta 의 좌석 수만큼 vision 키도 지운다
- **읽기(`game_view`):** meta(불변) → `MGET state, vision:{seat}` — 한 명령이라 찢어진 읽기가 없다. 저장된 기억에
  현재 시야를 메모리 안에서 한 번 더 `observe` 해서 화면을 만든다(쓰지 않는다). 키가 없거나 버전이 달라도
  `discovered ⊇ visible` 이 항상 성립한다. 버전 불일치는 `StateVersionMismatch`
- 워커가 2개여도: 상태는 전부 Redis, 쓰기는 게임 락 + 펜싱, 읽기는 MGET 스냅샷 → 깨지는 것 없음

## 판단 7 — `vision_fields` 서명과 화면

```python
def vision_fields(state: GameState, seat_no: int, memory: SeatMemory) -> dict
def build_view(state, meta, seat_no, memory) -> dict
```

- 탈락 좌석: `visible_* = []`, 발견 맵은 `memory` 그대로(판단 3)
- 생존 좌석: `s = game_sight(state, seat_no)`, `m = memory.observe(s, state.turn_count)` → 4개 필드
- 탈락 좌석 + `meta.spectate_on_elimination`: 위에 더해 `spectator` 필드(판단 3). 생존자 vision 키를 MGET 으로 함께 읽는다.
  **다른 좌석의 vision 키를 읽는 경로는 이것 하나**이고, 플래그와 탈락 두 조건을 모두 확인한 뒤에만 읽는다
- 그 외 모든 화면에는 `spectator` 키 자체가 없다
- 정렬: 변은 `(row, col, orientation)`, 말은 seat_no — 결정적 출력
- `delivery.py` 는 바꾸지 않는다(`game_view` 를 거친다). 재접속·재구독 재동기화는 자동으로 저장된 발견 맵을 복원한다
- **종료 후에도 화면은 안개를 유지한다.** `full_board` 는 7단계 `game_end` 몫이다

## 판단 8 — 벽은 2칸으로 설치하고 단위 변으로 점유한다 (사용자 지적 확인)

> 사용자: "벽은 변 2개 길이로 설치되고, 저장은 변 각각으로 되어서, 변 하나만 남았으면 설치가 안 되도록."

**엔진이 이미 그렇게 동작한다 — 규칙 변경 없음.** `WallManager._occupied_slots` 가 벽마다 단위 변 슬롯 2개
(`(r,c,"h")`·`(r,c+1,"h")` 또는 `(r,c,"v")`·`(r+1,c,"v")`) + 가운데 교차점 `(r,c,"center")` 를 점유하고, 하나라도 겹치면
거절한다(`invalid_wall_position`, §7 카운터 대상). 보드 끝에서 변이 하나만 남는 자리는 좌표 범위 0–7 이 막는다.

- 가운데 교차점 슬롯이 필요한 이유: 가로 `(3,3)` 과 세로 `(3,3)` 은 단위 변을 하나도 공유하지 않지만 서로 X 자로 가로지른다.
  **단위 변만 저장하면 이 교차를 잡지 못한다.** 그래서 state JSON 은 2칸 벽을 그대로 저장하고, 단위 변은 엔진이 파생한다
- 5단계는 이것을 **테스트로 고정**만 한다: ① 기존 벽 옆에 변 하나만 비었을 때 한 칸 어긋난 벽이 거절된다(가로·세로)
  ② 보드 끝 ③ 시야의 `unit_edges(wall)` 가 엔진의 `h`/`v` 슬롯과 같은 변이다(시야와 설치 판정이 다른 변을 보지 않는다)

## 판단 9 — 좌석 번호 위조 (사용자 질문)

> "악의적 사용자가 좌석 번호를 속여서 보내면?"

**좌석 번호는 어디에서도 클라이언트 입력이 아니다.** 서버가 인증된 `user_id` 로 `meta.seat_of(user_id)` 를 찾는다.

| 경로 | 좌석을 정하는 것 |
| :--- | :--- |
| 행동 `move`·`place_wall`·`surrender` | `_act` 가 `meta.seat_of(user_id)`. 서명에 seat 인자가 없다 |
| 화면 `game_view(game_id, user_id)` | 같다. 그 게임의 좌석이 아니면 `None` — 남의 `game_id` 를 넣어도 남의 화면은 없다 |
| 재동기화 `resync(user_id)` | `user:{uid}:activity` → `game_view` |
| `eliminate(game_id, seat_no, reason)` | 유일하게 seat 를 받는다. **서버 행위(6단계 스위퍼) 전용** — 소켓 메시지에 연결하지 않는다 |

남는 신뢰 지점은 `user_id` 하나이고, 그것은 **7단계 핸들러가 인증된 연결(JWT)에서만 꺼내고 페이로드에서 읽지 않는다**(경계 표).
5단계 테스트: 행동·화면 메서드 서명에 seat 인자가 없다 / 좌석 1 유저가 어떤 인자로도 좌석 2 의 화면(`me`·발견 맵)을 받지 못한다 /
비참가자는 `None`.

## 실행 비용

장시간 연산은 없다. 시야는 칸 8개·변 12개 상수 시간이다. 대량 검증 2건만 추정을 먼저 적는다. **DB 픽스처는 쓰지 않는다.**

| 검증 | 규모 | 판당/건당 | 추정 |
| :--- | :--- | :--- | :--- |
| 오라클 (5×5) | 벽 1개 32 + 2개 ≈ 450 ≈ 500 배치 | 시선 표본 ~200개의 교차 변 비트마스크를 **한 번 미리 계산** → 배치당 ~200 AND + 시야 1회 ≈ 50 µs | ≈ 0.05 s |
| 무작위 대국 | 3 모드 × 10판 × ≤60수 = ≤1.8k 수 | 벽 설치 BFS(생존자 수만큼) ≈ 0.5 ms + 시야 ≤4회 | ≈ 1–2 s |
| 서비스·화면 | ≈ 25건 × Redis 왕복 수십 회 | ≈ 30 ms | ≈ 1 s |

- **추정 합계 +3~5 s → 전체 ≈ 120 s** (기준선 ≈ 115 s / 429건). 추가 ≈ 45건
- **기준선:** 커밋 1 전에 `server-test` 를 한 번 재서 커밋 메시지에 적는다
- **중단 조건:** 새 엔진 테스트 파일 단독이 10 s 를 넘거나 전체가 기준선 + 30 s 를 넘으면 멈춘다 → 판 수를 줄이고(10 → 3) 오라클 표본을 줄인다.
  그래도 넘으면 원인을 보고하고 묻는다
- 엔진 테스트는 Redis·DB 없이 돈다

## MUST / MUST NOT

- MUST: 커밋마다 `docker compose run --rm server-test` 전체 통과
- MUST: §6 예시 1·2, MUST NOT 표 4행을 테스트로 고정. duel·trio·quad 파라미터화(quad 는 배치 테이블 행 추가만으로 통과)
- MUST: Redis 진입은 `require_redis()`, 호출은 `store_errors()`. 시야 쓰기는 게임 락 + state 와 같은 토큰의 펜싱 쓰기 한 번
- MUST: 키 문자열은 `redis_keys.py`, 설정값은 `config.py` 에만(새 설정은 없다 — TTL 은 `game_finished_ttl_sec` 재사용)
- MUST: 이벤트 hint 에 좌표·벽·시야 필드를 싣지 않는다
- MUST NOT: 이동·벽 설치 규칙과 엔진 검증 로직 변경(`move_validator`·`pathfinder`·`GameState.move/place_wall/eliminate`·`WallManager`)
- MUST NOT: 시계·스위퍼·서버 유예(6단계), WS 라우터·`main.py`·§12 와이어 확정·`full_board`(7단계)
- MUST NOT: 의존성 추가(hypothesis 등). 필요해지면 멈추고 승인을 받는다
- MUST NOT: 플레이어 화면 경로에서 다른 좌석의 vision 키를 읽는다(예외는 판단 3 의 관전 패킷 — 친구 방 + 켬 + 탈락)
- MUST NOT: 좌석 번호를 클라이언트 입력으로 받는 서비스 메서드(서버 행위 `eliminate` 제외, 판단 9)
