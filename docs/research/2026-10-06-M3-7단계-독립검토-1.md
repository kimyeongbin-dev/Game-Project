### [심각도: 높음] 끊김 재시도가 그 사이 같은 워커로 재접속한 좌석을 다시 "끊김"으로 만든다
- **근거 위치:** `app/ws/runtime.py:221-248` (`retry_pending`), `app/services/maze_game.py:469-486` (`_disconnect`의 owner 검사)
- **확인 수준:** 테스트로 확인 (재현 테스트 `test_retry_after_same_worker_reconnect_marks_live_seat_disconnected` 실패. 재시도 뒤 `connected=False`, `disconnected_at`은 원래 시각)
- **재현 시나리오:**
  1. 좌석 2의 연결이 워커 w1에서 끊긴다. `mark_disconnected`가 GameBusy로 실패해 `pending`에 들어간다.
  2. 0.5 s 뒤 같은 유저가 같은 w1으로 다시 붙는다(E1에서 85~97%가 이 경로다). `_welcome`이 `mark_connected(owner=w1)`을 부른다.
  3. 1 s 뒤 `retry_pending`이 `redo_disconnect(worker_id=w1, at_ms=t0)`을 부른다. owner가 w1이므로 검사를 통과하고, 살아 있는 연결이 t0 기준 "끊김"으로 기록된다.

- **제안:**
  - 재접속(`_welcome`, 그리고 같은 유저의 `connect`) 시 그 유저의 pending 항목을 버린다.
  - 더 근본적으로는 owner를 워커 id가 아니라 연결 id(`user_conn` 값)로 기록한다. 그리고 `_disconnect`/`redo_disconnect`는 "좌석의 현재 연결 id == 끊긴 연결 id"일 때만 기록한다.

### [심각도: 중간] 접속 처리 중 Redis·락 오류가 나면 `connected` 없이 열린 소켓이 남고, 그 밖의 예외는 연결 맵에 좀비 항목을 남긴다
- **근거 위치:** `app/ws/maze_handler.py:155-160`, `:117-127` (`_open`이 try/finally 밖)
- **확인 수준:** 코드로 확인
- **재현 시나리오:**
  - (a) 런타임 Redis 장애 중에 접속한다. E7에서 봤듯 `get_redis()`는 클라이언트를 그대로 돌려주므로 1013 검사를 통과한다. 이어서 `_claim_session`이 StoreUnavailable을 내고, 이것이 삼켜진 채 세션이 반환된다. 클라이언트는 `connected`도 재동기화도 못 받은 채 열린 소켓을 쥐게 된다. §2에 따르면 1013이어야 한다. `mark_connected`의 GameBusy도 같다.
  - (b) `_welcome`에서 StateVersionMismatch(스키마 버전을 올리는 배포 직후의 재접속)나 `resync`의 기타 예외가 나면, `serve`의 finally 밖에서 전파된다. `manager.connect`로 등록된 항목은 지워지지 않고, `on_disconnect`도 불리지 않는다.
- **왜 문제인가:** 프로토콜이 깨진다(첫 메시지 계약). 그리고 끊김 기록이 빠진다.
- **제안:** `_open` 전체를 try로 감싼다. 실패하면 `manager.disconnect`를 부르고 1013(또는 1011)으로 닫는다.

- **제안:** 수신자별 전송 큐와 태스크(유계 큐, 넘치면 연결 종료)를 둔다. `_claim_seat`은 버스 밖 태스크로 뺀다. 게임별 스냅샷 읽기는 수신자 간에 공유한다.

  - 탈락 후 나간 유저에게 이벤트가 0건인지

### [심각도: 낮음] `session_replaced` 처리가 이벤트 payload만 비교해 경합에 약하고, 이벤트 유실에 대비가 없다
- **근거 위치:** `app/ws/connection_manager.py:162-173`, `app/ws/bus.py:344-348`
- **확인 수준:** 코드로 확인 (경합 발생 빈도는 추측)
- **재현 시나리오:**
  - C1(wA) → C2(wB) → C3(wA)를 수 ms 안에 연달아 연결한다. wA의 버스가 `replaced(C2)`를 C3 등록 뒤에 처리하면 C3를 닫는다. 그다음 `replaced(C3)`가 C2를 닫는다. 결국 유저의 연결이 0개가 된다.
  - 이벤트가 유실되면(E5) 같은 계정의 연결 두 개가 서로 다른 워커에 동시에 살아 있다. 재구독 뒤에도 다시 점검하지 않는다.
- **제안:** 닫기 전에 `GET user:{uid}:conn`으로 현재 값을 확인한다(권위는 Redis). 재구독 때 로컬 연결 전원의 `conn_id`를 대조한다.

### [심각도: 낮음] WS 접속 리미터 — INCR/EXPIRE가 원자적이지 않고, DB 조회 뒤에 검사한다
- **근거 위치:** `app/ws/rate_limit.py:73-75`, `app/ws/maze_handler.py:137-150`
- **확인 수준:** 코드로 확인
- **재현 시나리오:**
  - INCR 성공 직후 EXPIRE가 실패(연결 끊김)하면 키에 TTL이 없다. 그 유저는 20회 뒤로 영구히 1013을 받는다.
  - 유효 토큰으로 접속을 연타하면 리미터에 걸리기 전에 매번 `identity.lookup`(DB 쿼리)을 수행한다.
  - 무효 토큰 연타에는 IP 단위 제한이 없다(slowapi는 WS에 적용되지 않는다).
- **제안:** INCR과 EXPIRE를 Lua나 MULTI로 묶는다(또는 `SET NX EX`를 먼저). 리미터를 토큰 검증 직후, DB 조회 전으로 옮긴다. 핸드셰이크에 IP 단위 리미트를 둘지 검토한다.

### [심각도: 낮음] `full_board`의 함수 수준 가드를 호출자가 우회한다
- **근거 위치:** `app/ws/delivery.py:124-132` (`voided=True` 고정 전달), `app/ws/wire.py:320-323`
- **확인 수준:** 코드로 확인. 실제 발생은 추측이다(`lost_game_min_age_sec` 덕분에 생성 경합이 거의 막힘).
- **재현 시나리오:** `game_voided` 이벤트가 왔는데 다시 읽은 스냅샷이 진행 중이고 무효가 아닌 상태라고 하자. 예를 들어 `_void_lost`와 `create_game`의 DB→Redis 쓰기가 경합한 경우다. 그러면 `full_board(state, voided=True)`가 진행 중인 판 전체를 만든다. trio의 무작위 시작 꼭짓점이 포함되므로 §6·§10 위반이다.
- **제안:** `voided=snap.voided`로 넘긴다. 스냅샷이 진행 중이고 무효가 아니면 `full_board=None`.

### [심각도: 낮음] 효과 없는 설정과 개발 환경의 플래그 누락
- **근거 위치:** `app/core/config.py` `ws_ping_interval_sec`·`ws_ping_timeout_sec`·`ws_max_size_bytes` (앱 코드에서 쓰는 곳 0건), `server/Dockerfile:85` (dev CMD에 WS 플래그 없음)
- **확인 수준:** 코드로 확인
- **재현 시나리오:** 환경변수로 `WS_MAX_SIZE_BYTES`를 바꿔도 서버 동작은 그대로다. dev 서버는 16 MiB 프레임과 ping 20/20 s로 돈다. 그래서 §1 "4 KiB 초과 시 1009"와 L19 감지 한계가 개발 환경에서 재현되지 않는다.
- **제안:** 설정값을 실제로 uvicorn에 넘기는 진입점을 둔다. 아니면 설정에서 지우고 Dockerfile을 유일한 출처로 둔다.

### [심각도: 낮음] 자잘한 불일치와 누수
- **확인 수준:** 코드로 확인 (1번 순서는 추측)
1. **`join_queue` 응답 순서:** 매치가 성사되면 `matched`(버스)가 `queue_joined`(핸들러 응답)보다 먼저 도착할 수 있다. §3은 "이어서 matched"라고 순서를 약속한다.
2. **`_leave_room`의 `seat_no`:** 락 밖에서 읽은 `before`로 계산한다(`maze_handler.py:329-331`). 동시에 다른 사람이 퇴장해 좌석이 당겨지면 틀린다.
3. **`user:{uid}:conn` 누수:** TTL이 없고 지우는 곳도 없다. 접속한 적 있는 모든 유저마다 키 하나가 영구히 남는다.
4. **`/health` 노출:** 공개 엔드포인트로 `worker_id`와 연결 수를 내보낸다.
5. **로그 마스킹 범위:** 레코드의 `getMessage()`만 가린다. `exc_info` 트레이스백이나 `websockets.*` 로거는 대상이 아니다(누설 경로가 실재하는지는 확인 못 함).
6. **위반 누적:** `violations`가 줄지 않는다. 오래 유지된 정상 연결도 누적되면 1008로 닫힌다.

## 관점별 추가 판정

1. **인원이 4명이 되면?** 실질적인 하드코딩은 없다. 핸들러·전달·와이어는 좌석 목록과 배치 테이블만 쓴다. 라이브 핸들러 테스트도 `seat_mode`(quad)로 돈다. 걸리는 것은 `room_dissolved`의 `seat_no: 1` 상수 정도인데, 이는 "호스트 = 1번 좌석"이라는 설계서 규칙에서 나온 값이다. hint에서 받도록 하면 더 안전하다. 판정: **통과.**

2. **워커가 2개면?** 이번 검토에서 가장 약한 부분이다.
   - 좌석 소유를 **워커 id 단위**로 기록하는 탓에, 같은 워커의 옛·새 연결을 구분하지 못한다(높음 1). 반대로 교체 뒤 소유가 옮겨지지 않으면 끊김을 영영 기록하지 못한다(높음 3).
   - E1(재접속은 대개 같은 워커)과 E5(이벤트 유실)를 겹치면 재시도·교체·재동기화가 각각 틀린 상태를 만든다(높음 1, 낮음 session_replaced, 중간 재동기화).
   - E3 종료 순서와 E4 두 번 끊김은 신호 시각 기준 소급과 원래 시각 재시도로 대체로 맞게 처리됐다. 다만 그 재시도 자체가 높음 1의 원인이다.
   - 크래시한 워커의 좌석은 스위퍼가 처리하지만, **살아 있는 워커**가 기록을 잃은 좌석에는 아무 안전망이 없다(높음 2·3, 중간 시작 전 끊김).

3. **클라이언트가 좌석·시계·턴을 조작할 수 있는가?**
   - 직접 조작 경로는 찾지 못했다. user_id는 HS256 토큰 `sub`에서만 나온다. `typ`/`auth`/`exp`/`sub` 검사가 있고, `alg none`은 거부된다. 페이로드의 미정의 필드는 버려지고, 시각은 Redis TIME이며, 좌석은 `meta.seat_of`가 정한다. 위조 좌석 테스트도 판별력이 있다.
   - 간접 경로는 있다. 연결 상태가 틀리게 기록되는 결함(높음 1~3, 중간 시작 전 끊김) 때문에, **상대가 일부러 끊고 붙는 타이밍**으로 내 좌석을 끊김 상태로 만들 수는 없다. 하지만 **자기 좌석의 끊김 기록을 피하는 것**은 가능하다. 시작 직전에 끊으면 접속 시계 60 s 대신 300 s를 쓰는 셈이 되고, 그만큼 상대를 붙잡아 둘 수 있다.
   - 레이트 리밋 우회는 다른 워커 재접속(분당 20 × 버스트 20)으로 제한적이다. DB 조회는 리밋보다 먼저 일어난다(낮음).

4. **시야 밖 정보가 새는가?**
   - 경기 중 패킷에서는 누설을 찾지 못했다. `game_state`는 `build_view` 그대로이고, `last_action`은 좌석과 종류뿐이다. 에러는 고정 문구 표에서만 나오고, 예외 문구는 로그 수준으로만 간다. hint에는 좌표가 없다. 끝나지 않은 게임의 `full_board`는 빌더가 거부한다.
   - 남은 위험:
     - (a) `_voided_end`가 `voided=True`를 고정으로 넘겨 그 가드를 우회한다(낮음, 경합이 필요).
     - (b) 나간 탈락자에게 관전 데이터를 포함한 옛 게임 패킷이 계속 간다(중간). 새는 대상이 이미 그 정보를 볼 수 있던 사람이라 FoW 위반은 아니고 프로토콜 위반이다.
     - (c) 로그 마스킹은 `token=`의 메시지 본문만 가린다.
