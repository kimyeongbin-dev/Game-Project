# 프록시(Caddy) 경유 다중 워커 실측 (M4-1)

> 계획서: [`../plans/2026-10-07-M4-1-프록시.md`](../plans/2026-10-07-M4-1-프록시.md) "판단 5"·수락 기준 C1~C7.
>
> 목적: M3 의 다중 워커 보장(S1~S9)이 **실제 클라이언트 경로(엣지 → Caddy → uvicorn 워커 2개)** 에서도 성립하는지, 그리고
> 프록시가 들어오면서 생긴 새 보장 — 실제 클라이언트 IP 식별(위조 불가), IP 접속 리밋, 운영 오리진 제한, 토큰 로그 누설 없음 — 을 잰다.

## 환경

| 항목 | 값 |
| :--- | :--- |
| 측정일 | 2026-10-07 |
| 하네스 | [`server/harness/multiworker/`](../../server/harness/multiworker/) — M3 하네스에 `proxy`(개발 compose 와 **같은 Caddyfile·같은 이미지** `caddy:2.11-alpine@sha256:d8542f48…`)와 `edge` 추가 |
| 경로 | 클라이언트 → `proxy:8080` → `server:8000`(prod 이미지, `--workers 2`, `FORWARDED_ALLOW_IPS` = proxy 고정 주소). 서버 직결은 진단(워커별 `/health`)과 P1 의 "직결" 항목뿐 |
| 엣지 흉내 | `edge` 컨테이너(고정 주소). Caddy 는 이 주소만 신뢰(`CADDY_TRUSTED_PROXIES`) — edge 가 붙인 `X-Forwarded-For` 가 배포의 엣지가 알려 주는 클라이언트 주소에 해당한다. `edge_probe.py` 를 Docker exec 로 돌려 클라이언트 IP 를 마음대로 정한다 |
| 설정 | M3 하네스와 같다(`ENVIRONMENT=production`, 짧은 시계) + `RATE_LIMIT_ENABLED=true`·분당 1000, `WS_CONNECT_PER_MINUTE_IP=600`(시나리오가 한 컨테이너에서 많이 접속한다). 오리진은 production 기본(없음) |
| CPU | 합 4 — redis 0.5, db 0.5, server **1.75**, proxy **0.5**, edge 0.25, client 0.5 (아래 "S9 — 프록시 CPU" 참조) |

```bash
C="docker compose -p m3s7 -f server/harness/multiworker/compose.yml"
$C up -d --build server proxy edge
$C run --rm client python scenarios.py all --runs 3 --with-long
```

## 발견 — 고치지 않고 기록 (사용자 결정 또는 운영 지침)

### Redis 재시작 뒤 워커의 Redis 클라이언트가 늦게 되살아난다 (M3 검토 #3 높음 2 — 재판단 → **Y9 로 수정**)

장애 중 들어와 붙잡힌 행동, 복구 직후의 새 접속 모두 복구 뒤 **최대 ≈1.3 s** 늦었다(아래 표). 이미 다시 연결된 소켓의 행동은
즉시(≤ 15 ms) 처리된다. 원인: Redis 가 꺼진 동안 이름 조회 하나가 3.3 s(Docker 내장 DNS NXDOMAIN) 걸리고, 워커의 재접속들이
asyncio 기본 스레드 풀을 채운다 — 하트비트 연결은 M3 에서 이미 피했다(`HeartbeatConnection`), 앱 풀·리미터 클라이언트는 그대로다.
그 사이 행동은 면제 없이 차감된다(재시작 공백이 하한 3 s 미만이면 장애로도 기록되지 않는다).

M3 검토 #3 때 사용자에게 제시한 "0.19~0.40 s"(재시작 3회)는 **과소 표본**이었다 — 다시 물었고 사용자 결정(2026-10-07): **기록하고
M4-2 에서 앱 풀 주소 고정으로 수정**(ROADMAP M4 항목 9). 그 뒤 짧은 재시작에서 복구 뒤 2~3 s 까지 감을 확인해(아래 Y9) 다시 물었고
**M4-1 에서 수정**(사용자 결정, `1ca8bf2`) — 하네스 S5 상한도 1 s 로 되돌렸다. 아래 표는 수정 **전** 값이다.

| 실행 | 장애 중 붙잡힌 행동 처리(복구 뒤) | 복구 뒤 새 접속 첫 성공 |
| :--- | :--- | :--- |
| S5 진단 3회(`results/m41-s5diag/`) | 14 · 8 · 797 ms | 1196 · 77 · 1241 ms |
| 본 실행 2묶음째(`m41-official2/`) | 881 · 1250 · 809 ms | 241 · 1302 · 785 ms |
| 최종(`m41-official3/`) | 8 · 177 · 770 ms | 935 · 527 · 765 ms |

### S9 — 한 소켓의 연타가 공유 프록시의 CPU 를 먹는다

| proxy CPU | 연타 중 상대 이동 왕복 |
| :--- | :--- |
| 0.25 (`m41-official1`·`2`) | 11.5 · 24.4 · **54.6** ms (상한 50 ms 초과 1회) |
| 1.0 (진단 3회, server 1.5·edge 정지로 합 4) | 12.6 · 11.9 · 8.2 ms |
| 0.5 (최종) | 7.8 · 7.5 · 10.2 ms |

서버의 메시지 리밋(버킷 → 1008)은 **서버**를 보호한다. 연타 프레임 500 개는 그 전에 Caddy 가 모두 중계한다 — 프록시 CPU 가 빠듯하면
같은 프록시를 쓰는 다른 플레이어가 늦어진다. **운영 지침:** 프록시에 CPU 여유를 둔다(하네스 기준 0.5 이상). 프록시 단의 연결별 리밋은
Caddy 기본 바이너리에 없다(플러그인 빌드 금지 — 2026-10-07 결정) — 필요해지면 M4-2 부하 측정과 함께 다시 본다.

### S4 kill — 간헐 실패 1회 (원인 가설 Y5 로 수정 — 판별은 못 함)

최종 1회차에서 20게임 중 **한 좌석**의 클라이언트가 `game_end`·탈락 통지를 받지 못했다. Redis 상태로는 20게임 모두 정상 종료(`last_standing`,
탈락 1건)라 **판정은 맞았고 통지 한 건이 닿지 않았다.** 그 회차 서버 로그는 이후 S6 의 서버 재기동으로 남지 않았다. 계측(빠진 좌석의
워커·마지막 수신 메시지·close 코드)을 넣고 5회 더 돌렸으나 전부 통과. M3·M4 전체에서 S4 kill 약 20회 중 1회. 설계상 이벤트는
at-most-once·권위 없음이고 재접속하면 재동기화가 결과를 준다(§8·§9) — 그래도 구독이 유지된 채 통지가 사라질 경로는 모른다.
독립 검토가 원인 가설을 냈고(쓰기 직후·발행 전 워커 사망 — 관측과 맞는다) 고쳤다(Y5). "재현 안 됨" 은 정확하지 않았다 —
확률 사건이라 5회로는 판별할 수 없었다(검토 지적). 수정 뒤 3회 통과도 같은 이유로 원인 확정의 근거는 아니다. 계측은 남겨 둔다.
