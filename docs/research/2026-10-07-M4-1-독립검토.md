### [심각도: 치명] 배포 엣지가 XFF 를 덧붙이는 형식이면 클라이언트가 IP 를 마음대로 위조한다 — Caddy 비엄격 모드는 맨 왼쪽 값을 고른다
- **근거:** `infra/caddy/Caddyfile:19` (`trusted_proxies static …` 에 `trusted_proxies_strict` 없음), `:30` (`header_up X-Forwarded-For {client_ip}`)
- **실측:** 신뢰 대역에서 `X-Forwarded-For: 6.6.6.6, 1.2.3.4` 를 보냈더니 `client_ip` = **`6.6.6.6`**. 같은 설정에 `trusted_proxies_strict` 를 더한 사본은 `1.2.3.4`. `garbage, 1.2.3.4` 는 무효 항목을 건너뛰어 `1.2.3.4`.
- **재현:** Fly·ALB·Cloudflare 류 엣지는 받은 XFF 에 접속 주소를 **덧붙인다**. 공격자가 `X-Forwarded-For: <임의 IP>` 를 보내면 엣지가 `임의, 실제` 로 넘기고, Caddy(엣지를 신뢰)가 맨 왼쪽 `임의` 를 `{client_ip}` 로 골라 그 값 하나로 XFF 를 다시 쓴다 → uvicorn 도 `임의` 를 클라이언트로 본다. REST 리밋과 WS IP 리밋을 요청마다 새 창으로 우회하거나, 남의 IP 를 써서 그 사람을 잠근다. `platform.md:72-74` 의 "클라이언트가 보낸 X-Forwarded-For 는 어느 단에서도 쓰이지 않는다" 는 거짓이 된다.
- **판별력 공백:** `edge_probe.py` 는 XFF 를 **단일 값**으로 보낸다 — 실제 엣지의 "클라이언트 값 + 접속 주소" 형태를 만들지 않아 하네스 P1·E2E·가드 모두 이 결함을 못 잡는다. 실측 보고서는 이 부분을 "측정하지 않은 것" 에 넣었지만 판정 문구는 위조 경로가 없다고 단정한다.
- **제안:** `servers { trusted_proxies static …; trusted_proxies_strict }`. 가드 검사 2 에 `trusted_proxies_strict` 추가. `edge_probe` 가 `"<위조>, <클라이언트>"` 형태도 보내게 하고 P1 판정에 "위조 값이 키가 되지 않는다" 추가. 엣지가 `Fly-Client-IP`·`CF-Connecting-IP` 같은 전용 헤더를 준다면 `client_ip_headers` 를 그 헤더로 고정하는 방안을 배포 작업의 조건으로 적어 둘 것.

### [심각도: 높음] Caddy 기본 오류 로그(`http.log.error`)가 5xx 마다 URI 를 통째로 남긴다 — `?token=` 원문 누설
- **근거:** `infra/caddy/Caddyfile` 전체 — 접속 로그를 끄는 것만으로는 막히지 않는다. `scripts/check-proxy-config.sh:26-31` 은 `log` 지시어만 본다. `maze.md §2`(128-129행) "Caddy 는 접속 로그를 남기지 않는다 — 가드가 막는다".
- **실측:** 업스트림이 죽은 상태에서 `GET /api/v1/ws/maze?token=SECRETTOKEN123` → stderr 에
  `{"level":"error","logger":"http.log.error","msg":"dial tcp …","request":{…,"uri":"/api/v1/ws/maze?token=SECRETTOKEN123",…},"status":502}`
- **재현:** 배포 SIGTERM 으로 1012 가 나가면 클라이언트는 즉시 재접속을 시도한다. 서버가 내려간 몇 초 동안 Caddy 는 502 를 내며 그 재접속들의 토큰 원문을 로그에 남긴다(워커 재기동·업스트림 keep-alive 경합·프록시 재시작 직후도 같다). 즉 **배포 때마다 확정적으로** 샌다.
- **하네스 판별력 없음:** S6 은 `wait_server()` 뒤에만 재접속하고, P4 는 502 를 유발하지 않는다. 보고서 C5 "충족" 은 실제 위험 경로를 재지 않은 판정이다.
- **제안:** 전역 `log default` 에 `format filter` 로 `request>uri` 의 쿼리를 지운다(`query token delete` 또는 uri 통째 삭제) — `http.log.error` 도 그 기본 로거로 나가는지 실측 확인. 가드를 "`log` 금지" 에서 "쿼리 필터 필수" 로 바꾸고, 하네스 P4 앞에 "서버 정지 중 토큰 실은 WS 접속" 을 일부러 만든다.

### [심각도: 높음] (S4 kill 간헐 실패의 가설 — 확인 필요) 커밋 직후·발행 전에 워커가 죽으면 `game_end` 가 영구히 사라진다
- **근거:** `server/app/services/maze_game.py:821-826` — `_commit`(펜싱 쓰기) **다음에** `for event in tx.outbox: await self._publisher.publish(event)`. 원자적이지 않다. 재처리 경로는 `was_closed=True` 가 되어 쓰기·outbox 를 모두 건너뛰므로 다시 발행하지 않는다(`expire()` 696행 재호출도 빈 목록). 버스의 재동기화(`bus.py _resync_all`)는 **그 워커의 구독이 끊겼을 때만** 돈다 — 살아남은 워커는 구독이 그대로라 재동기화하지 않는다.
- **관측과의 정합:** Redis 상태는 `last_standing`·탈락 1건으로 정상 종료인데 그 좌석은 `player_left(eliminated)` 도 `game_end` 도 0건(0 eliminations seen) — 같은 outbox 의 이벤트가 **전부** 빠졌다 = "커밋 → 발행 전 사망" 과 맞는다. `s4` 의 `t_start` 는 20게임을 `gather` 로 다 만든 **뒤**에 찍히므로(`scenarios.py:365-366`), 일찍 만들어진 게임의 기한은 kill 시각(`t_start + initial − 0.2`)보다 **앞선다** — kill 순간 죽는 워커의 스위퍼가 만료 처리 중일 수 있다. 창은 게임당 Redis 왕복 1~2회(수 ms)지만 20게임 × 두 스위퍼 분담이라 회당 수 % 확률 → "약 20회 중 1회" 관측, 5회 재시도 전부 통과(그 확률이면 ≈77% 기대)와 모순되지 않는다.
- **차순위 가설:** (b) `bus._dispatch` 에서 `deliver` 예외 시 그 유저를 건너뛴다(`bus.py` "다음 이벤트·재동기화가 메운다") — 종료 이벤트에는 "다음" 이 없다. 서버 로그에 `deliver … failed` 가 남았을 것. (c) `ws_send_timeout_sec`(2 s) 초과로 서버가 그 소켓을 닫음 — 프록시 CPU 0.5 에서 kill + 20게임 종료가 겹침. 이 경우 close 코드가 남았어야 한다. (d) 처리 지연으로 45 s 초과 — 계산상 리스 10 s 를 더해도 ≈41 s 라 가능성 낮음.
- **보고서 정직성:** "그 회차 서버 로그는 S6 의 서버 재기동으로 남지 않았다" 는 확인 필요 — `docker stop/start` 는 같은 컨테이너의 로그를 유지한다. 로그가 없었다면 컨테이너가 재생성됐거나 앱 로그 레벨 때문에 애초에 남지 않았을 것이다(다음 계측에서 확인할 것).
- **제안:** 발행을 펜싱 Lua 안의 `PUBLISH` 로 옮겨 쓰기와 원자화하거나, outbox 를 같은 쓰기로 Redis 에 남기고 스위퍼가 미발행분을 재발행. 차선책: 죽은 워커 판정(`_reap_dead_workers`) 때 그 워커가 관여한 게임의 살아 있는 좌석에 재동기화. 하네스: 만료를 처리한 워커 id 기록, kill 시각을 Redis 의 가장 이른 `turn_started_at` 기준으로, "커밋 후 발행 전 사망" 을 결함 주입 단위 테스트로 고정.

### [심각도: 중간] IP 접속 리밋이 정상 NAT 사용자를 막고(테스트가 그걸 요구한다), 명분·키 공간이 약하다
- **근거:** `server/app/ws/rate_limit.py:84-102`, `maze_handler.py:146-147`, `tests/ws/test_rate_limit_ws.py:177,194`(유효 토큰도 같은 IP 면 1013 을 단언)
- **재현:**
  1. 같은 통신사 CGNAT·사내 IP 뒤에서 공격자가 무효 토큰 접속을 분당 120회(초당 2회)만 보내면 그 IP 의 **유효 토큰** 사용자 전원이 1013. 성공 접속도 세므로 배포 1012 대량 재접속 순간 큰 NAT 는 정상 접속만으로도 한도에 닿는다 — 판단 기준 4 정면 위반.
  2. IPv6: `/128` 마다 키 — `/64` 하나로 무한 우회, 리미터 DB 키 증가.
  3. 명분 약함: "서명 검증·로그를 태우지 못하게" — HS256 검증(µs)보다 그 앞의 Redis INCR 왕복이 더 비싸다. uvicorn 접속 로그(마스킹된 `WebSocket …?token=*** [accepted]`)는 시도마다 그대로 찍히므로 로그도 줄지 않는다.
  4. Origin 거절은 IP 리밋보다 앞이라 세지 않는다 — 시도마다 `logger.info("WS rejected: origin not allowed")`, 무제한.
  5. 고정 창(`expire nx`) 경계에서 2배 버스트(경미).
- **제안:** IP 카운터는 **인증 실패만** 센다(검증 먼저, 실패 시 INCR, 차단 판정만 검증 전) — 유효 토큰은 계정 리밋에 맡긴다. IPv6 는 `/64` 로 묶은 키. Origin 검사 앞에서 IP 를 센다. 테스트 194행의 기대를 반대로.

- **근거:** CI `proxy-e2e` 는 dev 타깃(`--reload`, 워커 1, `ENVIRONMENT=local`, CORS `*`, `JWT_SECRET_KEY` 빈 값)으로 돈다. E2E 가 운영 설정의 반대(ACAO `*`)를 단언한다(`server/e2e/test_proxy.py:47`). ### [심각도: 중간] 실측 보고서 판정 중 근거가 부족한 것
- "M3 때의 0.19~0.40 s 는 과소 표본" 재판단은 교란 미정리: M4-1 에서 경로(Caddy), CPU 배분(server 2 → 1.75, proxy 0.5), **접속 경로에 리미터 Redis 호출(`allow_ip`) 이 하나 더 생겼다** — 보고서가 원인으로 지목한 "늦게 되살아나는 리미터 클라이언트" 가 바로 이것이다. 같은 하네스로 프록시 없이(직결) S5 를 3회 이상 돌린 대조 없이 과거 측정을 깎았다(내 변경이 원인인지 배제 안 함).
- P4 "원문 토큰 0" 은 정상 경로만(위 높음 항목).
- S4 kill "재현 안 됨" → "확률 사건이라 5회로는 판별 불가" 로 써야 정직하다.

### [심각도: 낮음] CORS 와 WS 오리진 판정이 "같은 판정" 이 아니다
- **근거:** `origins.py:29` 는 끝 `/` 를 정규화하지만 Starlette `CORSMiddleware` 는 정확 일치. `test_origins.py:30-32` 는 WS 쪽 정규화만 고정.
- **재현:** `CORS_ALLOWED_ORIGINS='["https://b.example/"]'` → WS 는 허용, REST 프리플라이트는 거부. 대소문자·기본 포트(`:443`) 혼용도 양쪽에서 조용히 거부(fail-closed 이긴 하다).
- **제안:** 설정 검증 단계에서 오리진을 정규화(소문자, 끝 `/` 제거, 기본 포트 제거)해 두 곳에 같은 목록을 넘긴다.

### [심각도: 낮음] Caddy 업스트림 연결 재사용 — 워커 분배 쏠림, keep-alive 경합 (확인 필요)
- **근거:** Caddyfile `reverse_proxy` 에 `transport` 설정 없음(Go 기본 keep-alive 풀), uvicorn `--timeout-keep-alive` 기본 5 s.
- **영향:** REST·WS 업그레이드 요청이 한가한 연결을 재사용해 처음 열린 워커로 쏠린다(보고서가 "/health 가 한 워커만 보인다" 고 인정). M3 E1 의 쏠림이 더 심해질 수 있다. uvicorn 이 5 s 에 연결을 닫는 순간 Caddy 가 그 연결을 재사용하면 경합 — 멱등 아닌 POST(향후 인증 API)는 Go 가 재시도하지 않아 간헐 502, 그 502 는 위 오류 로그 경로로 URI 를 남긴다.
- **제안:** `transport http { keepalive 4s }`(uvicorn 보다 짧게) 또는 uvicorn `--timeout-keep-alive` 증가, 하네스에서 POST 연타 502 측정.

### [심각도: 낮음] 고정 서브넷·CI 세부
- `docker-compose.yml:244-246`(172.30.0.0/24)·하네스(172.31.7.0/24)는 Docker 기본 주소 풀(172.17–172.31 의 /16)과 겹친다 — 오래 쓴 개발 호스트에서 자동 할당 네트워크가 172.30/16·172.31/16 을 이미 잡았다면 `Pool overlaps` 로 기동 실패. 기존 `gamemoa` 네트워크는 IPAM 변경으로 재생성 필요. GitHub 러너는 새 환경이라 충돌 가능성 낮음. 192.168·10 대역 등 기본 풀 밖 값 권장.
- `--wait` 는 proxy 헬스체크(업스트림 `/health`)에만 의존 — server 에 헬스체크가 없지만 proxy 헬스가 사실상 server 를 대신 본다(동작상 문제 없음).
- E2E 를 로컬에서 돌리면 **개발 스택**(앱 DB 0, 리미터 DB 2)의 리미터 카운터를 오염시킨다 — 1분 안에 다시 돌리면 `/health` 가 429 를 받아 `KeyError` 가능.
- `admin off` 라 Caddy 설정 변경 = 재시작 = 전원 1001 끊김. 운영 절차에 적을 것.
- S9 지적(연타 프레임을 서버 리밋 전에 Caddy 가 다 중계해 공유 프록시 CPU 잠식)은 보고서에 기록돼 있으나 완화책이 없다 — 연결당 리밋이 없어 프록시 CPU 를 겨냥한 DoS 표면이 된다.
