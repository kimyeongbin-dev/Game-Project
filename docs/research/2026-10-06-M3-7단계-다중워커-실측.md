## 파일럿이 찾은 서버 결함 (본 실행 전에 고쳤다)

파일럿은 "실패하면 맹목적으로 다시 돌리지 않고 원인부터"(계획서 중단 조건)로 돌렸다. 하네스 결함과 서버 결함을 가려,
서버 결함은 각각 회귀 테스트·반증과 함께 고쳤다.

| # | 결함 | 드러난 시나리오 | 수정 커밋 |
| :-- | :--- | :--- | :--- |
| X1 | 빈 DB 에 워커 2개가 동시에 `create_all` → 한 워커가 유일키 충돌로 **DB 없이** 떴다(그 워커의 접속은 신원 조회 실패로 1013) | 첫 기동 | `feda244` — advisory lock 으로 스키마 생성 직렬화 |
| X2 | redis-py 기본 재시도가 **0회** — Redis 재시작·`CLIENT KILL` 뒤 풀에 남은 죽은 연결을 쓰는 명령이 하나씩 실패. 상태 쓰기는 `server_busy` 로 재시도되지만 **발행·전달 읽기는 조용히 유실**돼 `game_start`·`turn_change` 가 오지 않았다 | S5·S6 | `7bc9508` — 새 연결로 즉시 1회 재시도 |
| X3 | 전역 Redis 장애 동안 **모든** 워커의 하트비트가 멈춘다. 복구 직후 먼저 돈 스위퍼가 살아 있는 다른 워커를 죽었다고 판정해 그 좌석을 장애 시작부터 끊김으로 만들었다 — 접속 예산보다 긴 장애면 **살아 있는 플레이어가 기권패** | S5 (10 s 정지) | `7bc9508` — 장애가 끝난 뒤 하트비트 타임아웃 동안 사망 판정 유예 |
| X4 | 장애 시작을 마지막 하트비트로 추정하는데 하트비트가 1 s 주기라, **정지 0.7 s 전에 생긴 게임**이 126 s 장애에도 무효가 되지 않았다 | S5d (본 실행 1회차) | `a9f2f9d` — 경계를 마지막 하트비트 + `store_outage_min_ms` 로 |

X2 의 남는 위험: 명령이 실행된 뒤 응답만 잃으면 재시도가 한 번 더 실행한다. 상태 쓰기(펜싱 SET·NX)는 같은 값이라 무해하고,
매칭 Lua(`ZPOPMIN`)만 두 번 꺼낼 수 있다 — 응답 유실 순간에만이라 수용한다(`app/db/redis.py` docstring).

같은 이유로 `server_busy` 는 **행동이 이미 반영됐을 수도 있다**(maze.md §13 에 명시). 실측에서 Redis 재시작 순간의 이동이
반영됐는데 응답을 잃어 `server_busy` 가 갔고, 재구독 재동기화가 최신 화면으로 수렴시켰다.
