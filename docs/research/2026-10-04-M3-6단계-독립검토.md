- 제안: 항목별로 예외를 격리하고 실패 항목을 재시도한다. 처리는 게임 단위로 묶어 병렬화한다. 실패 항목은 Redis에 "유예 후보" 키로 남겨, 다음에 그 게임을 처리하는 아무 워커가 적용하게 한다. 그러면 소급이 프로세스 수명에 묶이지 않는다.

### [심각도: 높음] 행동 시각이 "서버 수신 시각"이 아니라 "락 획득 뒤 시각"이다. 상대가 락을 독점해 내 시계를 태울 수 있다

- 확인 수준: 코드로 확인. 효과의 크기는 추측(WS 레이트 리밋이 아직 없다. slowapi는 HTTP 전용)
- 재현 시나리오: 좌석 2(상대)가 자기 차례가 아닌데 `move` 를 초당 수백 회 보낸다. 또는 재접속을 반복한다. 요청마다 `_run` 이 락을 잡고 state·clocks를 다시 쓴다. 좌석 1의 정상 행동은 공정하지 않은 스핀 락을 경쟁해야 하므로 획득이 늦어지고, 그동안의 경과가 좌석 1의 게임 시계에서 빠진다. 2 s를 넘기면 `GameBusy` 로 행동 자체가 실패하고 시계는 계속 흐른다.
- 왜 문제인가: 클라이언트가 **상대의** 시계를 조작하는 경로다. 설계서의 "수신 시각" 문장과 구현도 다르다.
- 제안: 수신 시각을 락 밖에서 Redis TIME으로 찍어 `_run` 에 넘긴다. 단 `turn_started_at` 이전이면 그 값으로 클램프하고 단조성을 보장한다. 차례가 아닌 행동과 무변경 거절은 쓰지 않고 락 없이 빠르게 거절한다(state 스냅샷 읽기만). WS 메시지 레이트 리밋을 설계 항목으로 추가한다.

  1. "장애"는 `FlakyClock.now_ms` 만 실패시킨 것이다. claim·ZSET·락 같은 실제 Redis 호출은 모두 성공한다. 부분 실패, 기록 후 실패(위 구간 연장), 풀 고갈은 재현되지 않는다.
  2. 모든 "워커"가 FakeClock 하나와 이벤트 루프 하나를 공유한다. 락 TTL 초과, 리스 만료 중 처리 지연, 프로세스별 관측 상태(재기동)는 검증되지 않는다. `test_claim_then_crash_is_retried_after_lease` 는 `claim()` 만 부를 뿐 크래시나 락 보유 중 사망을 다루지 않는다.
  3. 복구 직후 스위퍼 회차 **전에** 들어오는 행동이라는 경쟁 사례가 없다(첫 항목).
  4. 유실 테스트는 state 키만 지운다. 전체 유실(meta·ZSET 동시 소실) 사례가 없다.
  5. `test_crash_gets_no_grace` 는 크래시 때 실제로는 호출되지 않는 `mark_disconnected` 를 직접 부른다.
  6. 서버 유예·장애 테스트는 전부 2좌석이다. N≥3에서 한 번의 정산으로 여러 좌석이 탈락하는 경우(시간패 + 접속 소진 동시)의 서비스 수준 순번·턴 인계 테스트가 없다(`maze_clock` 순수 테스트만 있다).
  7. `session_factory=lambda: None` 이라 DB 경로(`db_in_progress`, limit 100, `_finalize` 실패 → void 전환)가 한 번도 실행되지 않는다.
  8. `apply_server_grace` 의 부분 실패나 대량 항목 사례가 없다.
- 제안: 실제 Redis 연결을 끊는 장애 하네스(toxiproxy 또는 `CLIENT KILL`/`DEBUG SLEEP`)와 2프로세스 통합 테스트를 둔다. 위 결함마다 반증 테스트를 추가한다.

### [심각도: 낮음] 하트비트 감지 지연만큼 끊김마다 접속 시계가 무료다
