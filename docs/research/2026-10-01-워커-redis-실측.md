# uvicorn 워커 · Redis 동작 실측 (M3 0단계)

> 계획서: [`../plans/2026-10-01-M3-착수순서.md`](../plans/2026-10-01-M3-착수순서.md) 0단계
>
> 목적: 진행 중 게임 상태를 **소유 워커 + 무효**로 둘지 **Redis 권위 + 이어받기**로
> 둘지 정하기 위해, "워커가 죽는다"가 실제로 무엇인지 측정한다.

## 환경

| 항목 | 값 |
| :--- | :--- |
| 측정일 | 2026-10-01 |
| 서버 | `uvicorn[standard]==0.40.0`, `fastapi==0.128.0`, `websockets==16.0`, `redis[hiredis]==8.1.0` — `server/Dockerfile` `deps` 스테이지 (고정 의존성 그대로) |
| 서버 플래그 | prod CMD 와 동일 + `--workers 2` |
| Redis | `redis:8-alpine@sha256:3811…` + `--appendonly yes --save 60 1` (개발 compose 와 동일) |
| Redis 연결 계층 | `app.db.redis` **그대로** 사용 (운영과 같은 풀 설정: `socket_timeout=5`, `max_connections=50`) |
| 호스트 | Windows 10 + Docker Desktop (WSL2), 클라이언트·서버·Redis 모두 같은 Docker 네트워크 |
| 하네스 | [`server/spikes/m3_worker_redis/`](../../server/spikes/m3_worker_redis/) — `spike_app.py` / `client.py` / `compose.yml` (독립 compose 프로젝트 `m3spike`) |

```bash
C="docker compose -f server/spikes/m3_worker_redis/compose.yml"
$C up -d --build
$C run --rm -T spike-client python client.py <실험> ...
$C down -v
```

각 실험 3회. 아래 수치는 3회 값을 모두 적는다.

## 결과

### E1 — 워커 분배와 재접속

`client.py e1 100` — 순차 100회 접속 + 동시 100 연결.

| 회 | 순차 분포 | 직전과 같은 워커 | 동시 분포 |
| :-- | :-- | :-- | :-- |
| 1 | 89 / 11 | 85 / 99 | 85 / 15 |
| 2 | 88 / 12 | 91 / 99 | 92 / 8 |
| 3 | 99 / 1 | 97 / 99 | 89 / 11 |

- 분배가 **심하게 치우친다** (85~99%가 한 워커). uvicorn 은 마스터가 연 소켓을
  자식들이 공유해 `accept()` 하므로 커널이 깨운 쪽이 가져간다. 균등 분배가 아니다
- 재접속은 **대개** 같은 워커로 가지만 **보장되지 않는다** (3~15%가 다른 워커)

**함의:** 재접속한 플레이어가 다른 워커에 붙는 일은 정상 경로다. 어떤 모델이든
게임 상태를 워커 메모리에만 두면 재접속 경로가 성립하지 않는다.

### E2 — 워커 SIGKILL (크래시 모사)

`client.py hold 10 25` 중 첫 연결의 워커 PID 에 `kill -9`.

| 회 | 죽인 워커 연결 | 다른 워커 연결 | 클라이언트가 본 종료 | 재기동 (died → Started) |
| :-- | :-- | :-- | :-- | :-- |
| 1 | 3 끊김 | 7 생존 | close frame 없음 (1006) | 재기동됨, ≈3.8 s |
| 2 | 10 끊김 | — (전부 한 워커) | 1006 | ≈3.6 s (로그 `11:33:45.06 → 48.64`) |
| 3 | 10 끊김 | — | 1006 | ≈3.4 s (`11:33:53.90 → 57.33`) |

- uvicorn 0.40 마스터가 **죽은 워커를 자동 재기동한다** (`Child process [N] died` → `Started server process`)
- 죽은 워커의 소켓만 끊기고 **다른 워커의 소켓은 영향 없다**
- 크래시는 close frame 이 없다 (1006)

> 무효 측정 기록: 첫 6회는 측정 오류로 버렸다. PID 탐색 셸이 자기 자신을 잡았고
> (`kill: No such process`), 다음엔 slim 이미지에 `kill` 바이너리가 없었다.
> 최종 명령은 `exec -T spike-server sh -c 'kill -9 "$1"' _ <pid>`.

### E3 — 정상 종료 (`docker compose stop`, SIGTERM)

`client.py hold 10 30` 중 서버 컨테이너 stop.

| 회 | 클라이언트 종료 코드 | lifespan `shutdown_begin` 시점 열린 소켓 |
| :-- | :-- | :-- |
| 1 | 10/10 **1012** | 0 |
| 2 | 10/10 **1012** | 0 |
| 3 | 10/10 **1012** | 0 |

- uvicorn 은 SIGTERM 에서 열린 WS 를 **1012 (Service Restart)** 로 닫는다
- **lifespan shutdown 은 소켓이 모두 닫힌 뒤에 돈다.** shutdown 훅에서 플레이어에게
  메시지를 보낼 수 없다. Redis 쓰기는 가능하다 (Redis 를 닫기 전이면)
- 종료 전체가 0.1 s 안에 끝났다 (WS 를 기다리지 않는다)

**함의:** 클라이언트는 1012(배포)와 1006(크래시·네트워크)을 **구분할 수 있다**.
서버는 shutdown 훅에서 자기 게임에 "서버 사유 유예" 표시를 Redis 에 남길 수 있다.

### E4 — 배포 = 컨테이너 교체 공백

`client.py reconnect 35` 중 `compose up -d --force-recreate spike-server` (이미지 사전 빌드).

| 회 | 종료 코드 | 재접속까지 공백 | 시도 횟수 (50 ms 간격) |
| :-- | :-- | :-- | :-- |
| 1 | 1012 → 1012 | 11 ms → **6 744 ms** | 1 → 73 |
| 2 | 1012 | **6 973 ms** | 77 |
| 3 | 1012 | **6 827 ms** | 74 |

- 단일 컨테이너 교체 공백 **≈ 6.7~7.0 s**
- 1회차: 1012 직후 **아직 살아 있던 구 컨테이너의 다른 워커**에 11 ms 만에 붙었다가
  다시 1012 로 끊겼다. 종료 중인 인스턴스로 재접속하는 경로가 실재한다

> **이 수치의 한계:** 로컬 Docker 단일 컨테이너 교체다. 배포처(Fly.io / ECS)가
> 롤링 교체면 공백은 0에 가까워지고, 콜드 스타트·헬스체크 대기가 붙으면 커진다.
> 배포처가 정해지면 같은 하네스로 재측정한다.

### E5 — Pub/Sub 워커 간 전달

`client.py e5` — 서로 다른 워커에 붙은 송신자·수신자, 10 ms 간격 발행.

| 조건 | 회 | 송신 | 수신 | 유실 | 중복 | p50 | p99 |
| :-- | :-- | --: | --: | --: | --: | --: | --: |
| 기준 (10 s) | 1 | 863 | 863 | 0 | 0 | 1.30 ms | 2.09 ms |
| | 2 | 865 | 865 | 0 | 0 | 1.31 ms | 2.06 ms |
| | 3 | 863 | 863 | 0 | 0 | 1.34 ms | 2.05 ms |
| 구독 연결 강제 종료 (`CLIENT KILL TYPE pubsub`) | 1 | 1728 | 1708 | **20** (557–576) | 0 | 1.32 ms | 2.16 ms |
| | 2 | 1728 | 1708 | **20** (558–577) | 0 | 1.32 ms | 2.08 ms |
| | 3 | 1726 | 1706 | **20** (555–574) | 0 | 1.33 ms | 2.04 ms |

- 구독이 끊기면 redis-py 는 `ConnectionError` 를 던진다 (조용한 재연결이 아니다)
- 재구독까지 발행된 메시지는 **영구 유실**된다. 유실량 = 재구독 지연(하네스 0.2 s) × 발행률
- idle 상태로 수 분 두어도 `socket_timeout=5` 때문에 구독이 끊기지는 않았다

**함의:** Pub/Sub 은 **at-most-once** 다(maze.md §8 이 이미 전제한 것과 일치). Pub/Sub
메시지에 권위를 싣지 않는다. 재구독 직후에는 Redis 의 상태에서 **재동기화**해야 한다.

### E6 — 게임별 락 + 상태 RMW

`client.py e6 GAMES ACTORS ACTIONS PAYLOAD` — `SET NX PX` 락 → `GET` → JSON 갱신 →
`SET` → Lua 비교 삭제. 참고: 현재 `GameState.to_dict()` 는 벽 4개 기준 **668 B**.

| 조건 | 회 | 정확성 | p50 | p99 | max |
| :-- | :-- | :-- | --: | --: | --: |
| 1게임 · 1행위자 · 2 KB | 1 | ✅ | 0.94 ms | 2.42 ms | 3.2 ms |
| | 2 | ✅ | 1.22 ms | 2.36 ms | 12.6 ms |
| | 3 | ✅ | 1.10 ms | 1.73 ms | 2.2 ms |
| 1게임 · 1행위자 · 16 KB | 1 | ✅ | 1.25 ms | 2.30 ms | 2.7 ms |
| | 2 | ✅ | 1.06 ms | 1.90 ms | 2.8 ms |
| | 3 | ✅ | 1.15 ms | 2.08 ms | 3.1 ms |
| 1게임 · **3행위자 경합** · 16 KB | 1 | ✅ 600/600 | 1.30 ms | 32.9 ms | 55 ms |
| | 2 | ✅ 600/600 | 1.32 ms | 39.1 ms | 66 ms |
| | 3 | ✅ 600/600 | 1.31 ms | 47.4 ms | 61 ms |

- 경합 없는 행동 1건 **p99 ≈ 2 ms**
- 경합 조건은 **최악 가정**이다 — 3행위자가 생각 시간 없이 같은 게임을 두드린다.
  실제 턴제에서는 현재 좌석 1명 + 드물게 항복·스위퍼뿐이다. 그래도 직렬화는 정확했다
- **무효 측정 기록:** 처음에는 100게임을 한 클라이언트 프로세스에서 동시에 돌렸다.
  그 결과 경합이 없는데도 p50 70 ms, 락 대기 p99 200 ms 가 나왔다. 이는 Redis 비용이
  아니라 **벤치마크 프로세스 안의 큐잉**이다. 100×3 은 `MaxConnectionsError` 로
  실패했다. 버렸다
- 부수 관찰: 락을 쥔 채 대기하는 코루틴이 많으면 풀(`max_connections`)이 먼저
  고갈된다. 운영 풀 50 은 워커당 동시 행동 수 상한이 된다

### E7 — Redis 재시작 (`compose restart spike-redis`)

`client.py e7 25` — 100 ms 간격 `INCR`.

| 회 | 장애 구간 | 오류 순서 | 실패 쓰기 | 자동 복구 | 데이터 |
| :-- | :-- | :-- | --: | :-- | :-- |
| 1 | ≈2.0 s | `ConnectionError` → `BusyLoadingError` | 6 | ✅ | 유실 0 (복구 후 값 36 = 35+1) |
| 2 | ≈1.9 s | 동일 | 6 | ✅ | 유실 0 |
| 3 | ≈2.2 s | `ConnectionError` | 2 | ✅ | 유실 0 (누적 671 = 225+225+221) |

- 풀이 **스스로 재연결**한다. 앱 재시작이 필요 없다
- AOF 로 데이터가 남는다 (정상 종료 재시작 기준. `kill -9` 크래시는 측정하지 않았다 —
  `appendfsync everysec` 기본값이면 최대 1 s 유실 가능)
- ⚠️ **`is_redis_available()` 는 장애 내내 `true` 였다.** 기동 시 한 번 정해지는
  플래그이지 실시간 상태가 아니다. 이 가드만으로는 런타임 장애를 막지 못하고,
  Redis 호출부는 예외 처리를 따로 해야 한다

## 판정

계획서의 판정 규칙(측정 전에 고정):

| 기준 | 측정 | 판정 |
| :--- | :--- | :--- |
| E4 배포 공백 ≤ 10 s | 6.7~7.0 s | ✅ |
| E6 행동 처리 p99 ≤ 20 ms | ≈2 ms (경합 없음) | ✅ |

→ **Redis 권위 + 이어받기** 가 규칙상 채택된다. **사용자 확인 전이다.**

### 결정에 딸려 오는 설계 사항 (측정이 드러낸 것)

| # | 사항 | 근거 |
| :-- | :--- | :--- |
| 1 | 게임 상태를 Redis 에 두고 행동마다 게임별 락으로 직렬화한다 | E1, E6 |
| 2 | Pub/Sub 은 통지 수단일 뿐이다. 재구독 직후 해당 워커의 소켓 전원에게 Redis 상태로 재동기화를 보낸다 | E5 |
| 3 | 1012(배포)와 1006(크래시)을 구분할 수 있다. shutdown 훅은 소켓이 닫힌 **뒤에** 돌기 때문에 Redis 표시만 할 수 있다 | E3 |
| 4 | `is_redis_available()` 를 런타임 가드로 믿지 않는다. 멀티 경로는 Redis 예외를 직접 처리한다 | E7 |
| 5 | 종료 중인 인스턴스로 재접속하는 경로가 있다. 재접속 흐름은 "두 번 끊김"을 견뎌야 한다 | E4 1회차 |
| 6 | 워커 분배가 고르지 않다. 용량 산정 시 워커 수 × 균등 분배를 가정하지 않는다 | E1 |

### 측정하지 않은 것

- 배포처의 실제 교체 방식(롤링 여부)과 공백 — 배포처 결정 후 재측정
- Redis `kill -9` 크래시 시 AOF 유실량
- Caddy 프록시를 거친 WS 동작 — M4 범위
