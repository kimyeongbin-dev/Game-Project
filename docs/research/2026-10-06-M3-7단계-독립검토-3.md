### [심각도: 높음] 장애 끝을 "Redis 가 PING 에 답한 시각"으로 찍게 되어, 플레이어가 실제로 행동할 수 있게 된 시각과 어긋난다 — 재시작 장애에서 과소 면제
- 근거: `app/services/sweeper.py` `_alive_loop` 가 전용 연결로 장애를 닫는다. 보고서 "알려진 한계"(실측 문서 177행) 스스로 "앱 풀 재접속도 기본 스레드 풀에서 줄을 선다 … 복구 뒤 행동 재개가 ≈1.4 s 늦을 수 있다(측정은 하트비트로만)"를 인정한다. X7 분석에 따르면 복구 뒤 1.4 s 동안 두 워커가 Redis 에 쓰지 못했다 — 앱 풀도 같은 원인으로 막혀 있었다는 뜻이다.

- 제안: (a) 앱 풀의 이름 조회 지연을 같이 고치거나(전용 resolver/주소 고정), (b) 장애 끝을 "앱 풀 첫 성공"으로 찍는 경로를 남기거나(예: `_run` 첫 성공 처리·회차 하트비트의 실패→성공 시각), (c) 최소한 설계서 §8 에 "장애 = 하트비트 전용 연결 기준" 정의와 과소 면제 한계를 명시. 하네스 S5 재시작 구간에 "첫 행동 성공 시각 − 기록된 장애 끝"을 재는 지표를 추가.

- `mark_connected(only_if_current=True, owner=None)` 은 `user_conn` 이 없을 때 `None == None` 으로 대조를 통과한다(`maze_game.py:566`) — 현 호출자는 없지만 API 함정. `owner is None` 이면 거부하도록.

### 확인했으나 문제 없음
- `extra_keys` 가 다른 `_run` 호출자에 주는 영향: 기본 `()` 이면 MGET 이 이전과 동일. 클러스터 CROSSSLOT 은 이미 `store:alive` 가 섞여 있어 새 제약 아님.
- 회차 `_heartbeat` 와 전용 루프의 중복·경합: Lua 의 `if now > last then SET` 로 단조 유지 — 걸려 있던 회차 eval 이 낡은 `now` 로 늦게 실행돼도 `alive` 를 되감지 않고, 공백 기록은 원자적 1회. 무효 훑기는 기록자와 무관하게 `store:outages` 를 읽으므로 누락 없음.
- 주입 시계 테스트 분기: `self._clock is redis_clock` 일 때만 전용 루프 — `Realtime` 기본 sweeper 는 redis_clock 이라 운영에서는 돈다.
- claim 경로 자체의 수정: 새 연결이 "SET → 자기 소유 기록" 순서를 지키는 한 락 안 대조가 X6 순서를 막는다(남은 문제는 위 "높음"의 다른 경로).
- 공격자 관점: 클라이언트가 `owner`/`user_conn` 값을 직접 넣을 경로는 없다. 동시 재접속으로 소유를 엇갈리게 하는 것은 가능(첫 항목)하나 무료 면제를 얻는 경로는 찾지 못했다 — 엇갈려도 결국 끊김이 기록되는 쪽(연결된 좌석의 과다 과금)이다.
