## §1 개요와 전송 방식

| 항목 | 값 |
| :--- | :--- |
| 게임 ID | `maze_1p` |
| 보드 | 9×9. 벽은 교차점 2칸 길이 (0-7) |
| 인원 | 1:1 (2인) 또는 1:1:1 (3인) |
| 전송 | **WebSocket 단일 채널** |
| 엔드포인트 | `wss://<host>/api/v1/ws/maze` |

### 왜 REST가 아니라 WebSocket인가

구 Quoridor는 턴마다 REST를 호출했다(`POST /games/{id}/move`). 1인칭 미로는
그 방식으로 구현할 수 없다.

1. **시야가 상대 행동에 따라 바뀐다.** 상대가 이동하면 내 시야에 들어오거나
   나갈 수 있다. 서버가 능동적으로 알려야 한다 — 폴링으로는 즉시성이 없다.
2. **턴 타이머가 서버에 있다.** 시간 초과를 서버가 통보해야 한다.
3. §4.1이 "120fps 유지"를 요구한다. 매 프레임 폴링은 불가능하다.

### AI는 두 경로로 나뉜다

[`../platform.md`](../platform.md) §6에서 확정했다. 둘은 **다른 경로**이며 섞이지
않는다.

| 경로 | 로그인 | 네트워크 | AI 실행 | MMR |
| :--- | :--- | :--- | :--- | :--- |
| **오프라인 솔로** | 불필요 | **100% 오프라인** | 클라이언트 **Dart Isolate** | — |
| **온라인 AI 좌석** | 필수 | 이 문서의 WS 프로토콜 **그대로** | 서버 `simple_ai.py` | **미반영** |

- **오프라인 솔로**는 §1.1에 따라 로컬 AI·판정·렌더링을 클라이언트가 전부
  수행하며 이 문서의 API를 전혀 호출하지 않는다
- **온라인 AI 좌석**은 `game_participants.is_ai = true` 로 좌석을 표현한다.
  멀티 프로토콜을 그대로 재사용하므로 **메시지 타입·좌석 구조에 변경이 없다**.
  랭크전이 아니므로 MMR에 반영하지 않는다
- **AI 좌석도 §6 시야 필터를 거친 상태만 입력으로 받는다.** 서버 엔진이 전체
  상태에 접근할 수 있다는 이유로 전지(全知) AI가 되면 안 된다
- 둘 다 멀티플레이 상호작용 검증 이후 착수한다. **Phase 1 미노출**이며
  `simple_ai.py` 는 온라인 AI 좌석의 기반으로 보존한다
- 구 `POST /games/{id}/ai-move` 는 **폐기**다 — 어느 경로도 그 엔드포인트를
  필요로 하지 않는다

### 메시지 봉투

REST의 `data` 봉투와 달리 WebSocket은 `type`으로 분기한다.

```json
{ "type": "move", "seq": 12, "payload": { } }
```

| 필드 | 설명 |
| :--- | :--- |
| `type` | `WSMessageType` 값 (§12) |
| `seq` | 클라이언트 → 서버에만. 요청 일련번호. 서버 응답·에러에 `ack_seq`로 되돌려 준다 |
| `payload` | 타입별 본문 |

서버 → 클라이언트 에러는 공통 규약의 필드명을 유지한다.

```json
{ "type": "error", "ack_seq": 12,
  "payload": { "error": "not_your_turn", "message": "내 차례가 아닙니다." } }
```

## §2 접속과 인증

```
wss://<host>/api/v1/ws/maze?token=<access_token>
```

- 인증은 **연결 수립 시 1회**. 쿼리 파라미터로 access token을 보낸다.
  WebSocket 핸드셰이크는 커스텀 헤더를 브라우저에서 설정할 수 없어 쿼리를 쓴다.
  **access token만** 허용한다 (`typ=access` 검증). 리프레시 토큰은 거부한다.
- 토큰이 없거나 무효면 핸드셰이크를 수락하지 않고 close code로 끊는다 (§13).
- **익명 계정은 거부한다.** 멀티플레이는 카카오 로그인 필수(§1.1)이므로
  `auth=anonymous` 토큰은 `login_required`로 끊는다.
- **닉네임이 없으면 거부한다.** 상대에게 표시할 이름이 필요하다
  → `nickname_required`.

연결 성공 시 서버가 먼저 보낸다.

```json
{ "type": "connected",
  "payload": {
    "user_id": 2210,
    "nickname": "미로장인",
    "mmr": 1042,
    "reconnect": { "game_id": "…", "seat_no": 2 }
  } }
```

`reconnect`는 진행 중인 게임이 있을 때만 포함된다 (§9).

> 같은 계정으로 새 연결이 들어오면 **기존 연결을 끊는다** (close code 4000).
> 현행 `ConnectionManager.connect`가 이미 이 동작을 한다
> (`server/app/ws/connection_manager.py:48`) — 재사용한다.

## §3 매치메이킹

### 큐 참가

```json
{ "type": "join_queue", "seq": 1, "payload": { "mode": "duel" } }
```

| `mode` | 인원 | 비고 |
| :--- | :--- | :--- |
| `duel` | 2 | 1:1 |
| `trio` | 3 | 1:1:1 |

모드별로 큐가 분리된다. 한 사용자는 동시에 하나의 큐에만 들어간다.

```json
{ "type": "queue_joined", "ack_seq": 1,
  "payload": { "mode": "duel", "position": 3, "waiting_count": 7,
               "estimated_wait_sec": 20 } }
```

대기 중 주기적으로 `queue_status`가 온다.

### MMR 범위 — Phase 1 은 제한하지 않는다

**매칭에 MMR 필터를 걸지 않는다.** 큐에 들어온 순서대로 성사시킨다.

MMR 자체는 정상적으로 계산·기록하고 리더보드에 쓴다([`../platform.md`](../platform.md)
§4.2). 끄는 것은 **매칭 필터뿐**이다.

> 출시 직후에는 동시 접속자가 적다. 이때 MMR 범위를 걸면 **매칭이 아예 성사되지
> 않는다.** 상대를 못 만나는 것보다 실력 차 나는 상대를 만나는 편이 낫다 —
> 품질보다 성사가 우선인 구간이다.

**큐 인구가 확보되면 범위 제한을 도입한다.** 그때 쓸 설계는 아래와 같다.
허용 범위를 서버 설정값으로 두고, 설정이 비어 있으면 무제한으로 동작시킨다.

| 경과 | 허용 MMR 차 (도입 시) |
| :--- | :--- |
| 0~10초 | ±100 |
| 10~30초 | ±200 |
| 30~60초 | ±350 |
| 60초 이상 | ±500 (상한) |

`trio`는 3명이 모두 범위 안에 들어와야 성사되어 난이도가 높으므로 상한을
±700로 완화한다. 모드별 상한은 **설정 테이블의 행**이므로 모드가 늘어도
스키마가 바뀌지 않는다.

> 확장 규칙은 `server/app/services/matchmaking.py` 의 `mmr_window`(구간 표
> `MMR_WINDOW_STEPS`, 모드별 상한 `MMR_WINDOW_CAP`)로 보존돼 있다(M3 3단계). **로직을 지우지 말고
> 비활성화만 한다.** 도입 시점에 기준을 점수(`score`)에서 MMR로 바꿔 되살린다.

### 매칭 성사

```json
{ "type": "matched",
  "payload": {
    "game_id": "8f14e45f-ceea-467a-9a0b-1c2d3e4f5a6b",
    "mode": "duel",
    "my_seat_no": 1,
    "players": [
      { "seat_no": 1, "nickname": "미로장인", "mmr": 1042 },
      { "seat_no": 2, "nickname": "길잃은양", "mmr": 998 }
    ],
    "ready_deadline_sec": 10
  } }
```

양측이 `ready`를 보내야 시작한다. 기한 내 응답하지 않으면 매칭이 취소되고
**응답한 쪽만 큐로 복귀**한다.

### 큐 이탈

```json
{ "type": "leave_queue", "seq": 2 }
```

## §4 친구 대전 방

MMR에 반영되지 않는 비랭크 경기다.

### 방 생성

```json
{ "type": "create_room", "seq": 1, "payload": { "mode": "trio" } }
```

```json
{ "type": "room_created", "ack_seq": 1,
  "payload": { "room_code": "K7QX2M", "mode": "trio", "capacity": 3,
               "players": [ { "seat_no": 1, "nickname": "미로장인", "is_host": true } ] } }
```

방 코드는 6자다 (`server/app/services/rooms.py` `ROOM_CODE_LENGTH = 6`).

### 방 참가

```json
{ "type": "join_room", "seq": 1, "payload": { "room_code": "K7QX2M" } }
```

참가자에게 `room_joined`, 기존 인원에게 `player_joined`가 간다.
정원 초과 시 `room_full`.

### 준비와 시작

각자 `ready` → 서로에게 `player_ready` → 전원 준비되면 `game_start`.
호스트가 이탈하면 방이 해산되고 남은 인원에게 `player_left` 후 방이 닫힌다.

> **랭크와 친구 대전의 차이:** 친구 대전은 `is_ranked=false`로 기록되며
> MMR이 변하지 않는다. 결과는 `game_sessions`에 남는다 (전적 표시용).

## §5 게임 진행

### 좌표계

`PLATFORM_ARCHITECTURE.md`의 Quoridor 좌표 규약을 유지한다 — 보드 9×9 (0-8),
벽은 교차점 (0-7). 기존 엔진(`app/games/maze/core/`)이 이 규약으로 구현되어 있다.

**단, 1인칭 뷰에서도 서버 프로토콜은 그리드 좌표를 쓴다.** 1인칭 렌더링은
클라이언트의 표현 방식이며, 서버는 논리 좌표만 다룬다.

> **카메라 방향은 클라이언트 전용 상태다.** 시야가 방향에 의존하지 않으므로(§6)
> 서버는 플레이어가 어디를 보는지 알지 못하며, 알 필요도 없다. 프로토콜 어디에도
> 방향 필드가 없다.

### 이동

```json
{ "type": "move", "seq": 10,
  "payload": { "row": 7, "col": 4 } }
```

| 필드 | 설명 |
| :--- | :--- |
| `row`, `col` | 목표 칸 |

#### 합법 이동

| 조건 | 내용 |
| :--- | :--- |
| **거리** | 현재 칸과 **직교 인접**한 1칸 (상·하·좌·우) |
| **보드** | `0 ≤ row ≤ 8`, `0 ≤ col ≤ 8` |
| **벽** | 두 칸 사이의 변에 벽이 없을 것 |

이 셋이 전부다. **말의 위치는 이동 제약에 전혀 관여하지 않는다**(아래).

- **대각 이동은 없다.** 어떤 경우에도 발생하지 않는다
- **패스는 없다.** 매 턴 이동 또는 벽 설치 중 하나를 반드시 한다
- 생존 플레이어에게 **합법 이동은 항상 최소 1칸 존재한다** — §7이 모든 생존자의
  목표 도달 경로를 보장하고 말이 길을 막지 않으므로, 그 경로의 첫 칸이 언제나
  합법이다

#### 말은 서로를 막지 않는다

**여러 말이 같은 칸에 겹칠 수 있다.** 다른 말이 있는 칸으로 그냥 들어간다.

| 대상 | 취급 |
| :--- | :--- |
| 생존자의 말 | 통과·중첩 가능 |
| **탈락자의 말** | **동일하다.** 장애물이 아니다 (§9) |
| **목표 칸** | 동일하다. 다른 말이 서 있어도 들어가 도달한다 — **목표 봉쇄가 불가능하다** |

- 같은 칸의 인원에 **상한을 두지 않는다.** 모드 정원이 유일한 한계다
- 같은 칸에서 조우해도 **특별 효과가 없다** — 전투·밀어내기 같은 상호작용을
  넣지 않는다
- `visible_players`·`last_seen_players` 에 **같은 좌표가 복수 등장할 수 있다**(§6)

#### 점프 규칙은 두지 않는다

구 Quoridor의 "인접 상대를 뛰어넘고, 뒤가 막히면 대각으로 우회한다"를 **승계하지
않는다.** 근거 4개:

1. **Fog of War와 구조적으로 충돌한다.** 직선 점프 가능 여부는 상대 **뒤쪽 변**과
   **착지점 점유**로 결정되는데, 전자는 3×3의 **외곽 변**이라 §6이 전송하지 않고
   후자는 2칸 거리로 **3×3 밖**이다. 클라이언트가 자기 합법 수를 계산할 수 없게
   되고, 메우려면 §6의 외곽 변 규칙이나 §7의 "유효 수 목록을 주지 않는다"에
   **예외**를 내야 한다
2. **§4.1에 없다.** SSOT가 규정한 행동은 "**이동 및 벽 설치**" 둘뿐이고, 점프도
   말 충돌 규칙도 언급이 없다
3. **몸으로 길막기가 성립하지 않는다.** 폰 충돌의 전략적 의미는 상대의 길을 막는
   것인데, **상대가 어디 있는지 모르는 게임에서는 막을 대상을 특정할 수 없다.**
   잃는 전술이 애초에 작동하지 않는다
4. **교착이 사라진다.** 점프+충돌 규칙에서는 3인전에서 두 면이 벽, 두 면이 말이고
   대각까지 막히면 **합법 수가 0개**가 될 수 있었다. 처리 규칙이 없던 구멍이며,
   §7이 거절 3회째에 "반드시 말을 이동해야 한다"고 적은 전제도 여기서야 성립한다

> 제거는 §4.1의 "`Quoridor` 상표권 배제 및 Trade Dress 완전 해소" 방향과도 맞다.
> 변(edge) 단위 시야에는 정착된 표준이 없으므로, **판정에 필요한 정보가 시야 규칙
> 안에서 자족하도록 규칙을 맞춘다** — 시야에 예외를 내는 것보다 안전하다.

#### 검증 순서 (서버에서만 수행)

§7의 벽 설치 검증과 같은 형식으로 판정하고, **2~4 중 어디서 걸려도
`invalid_move`** 를 반환한다.

1. 내 턴인가 → 아니면 `not_your_turn`
2. 목표 칸이 보드 범위(0-8) 안인가
3. 현재 칸과 **직교 인접**한 1칸인가
4. 두 칸 사이의 변에 **벽이 없는가**
5. **도달 판정** — 아래 승리 판정에 걸리면 `goal_reached` 로 종료(§9·§10),
   아니면 턴을 넘긴다

#### 승리 판정

`me.goals` 는 `{축, 값}` 의 **목록**이다(§11). **원소 중 하나라도 만족하면
도달**이다.

```
도달 = goals 중 어느 g 에 대해
       (g.axis == "row" ? position.row : position.col) == g.value
```

- 2인전은 원소 1개(`row 0` 또는 `row 8`), 3인전은 2개(§11의 L자 17칸)
- 꼭짓점 `(8,8)` 처럼 **두 원소를 동시에 만족**해도 도달은 한 번이다
- 도달하면 `goal_reached` 로 **즉시 게임이 끝난다**(§9)

> **클라이언트가 합법 수를 자족적으로 계산한다.** 판정에 필요한 변은 내 4면뿐이고,
> §6이 *"`P` 는 항상 보이므로 내 4면은 언제나 전송된다"* 를 이미 보장한다. 그래서
> 서버는 유효 수 목록을 주지 않아도 되고(§7), **정상 플레이에서 `invalid_move` 는
> 발생하지 않는다** — 버그·조작 시에만 나온다.

> **M3 1단계에서 구현 완료 — 새로 만들지 않고 걷어냈다.**
> `server/app/games/maze/core/move_validator.py` 의 `_get_jump_moves()` 와
> `opponent` 인자, `pathfinder.find_shortest_path()` 의 `other_player_pos` 인자를
> 삭제했다. 상대 **목록**으로 확장한 것이 아니라 인자 자체가 불필요해졌다.
> 점프 테스트(`TestJumpMoves`·`TestJumpScenarios`)도 함께 삭제했다.

### 방향 전환은 행동이 아니다

제자리에서 시점만 돌리는 것은 **서버 상태를 전혀 바꾸지 않는다.** 시야가 360°
전방향이라(§6) 어느 쪽을 보든 받는 정보가 같기 때문이다.

- 회전 전용 메시지 타입을 두지 않는다
- 턴을 소모하지 않는다 — 소모 여부를 따질 대상 자체가 없다
- 회전해도 서버에 아무것도 보내지 않으므로 **시야 패킷 트래픽이 늘지 않는다**

> 1인칭 카메라는 클라이언트가 자유롭게 보간해 돌린다. 서버에게 미로는 끝까지
> 그리드일 뿐이다.

### 벽 설치

```json
{ "type": "wall", "seq": 11,
  "payload": { "row": 3, "col": 5, "orientation": "horizontal" } }
```

서버는 행동이 수락될 때마다 **각 플레이어에게 서로 다른** `game_state`를 보낸다.
스키마는 §6에 있다.

### 턴 전환

```json
{ "type": "turn_change",
  "payload": {
    "current_seat_no": 2,
    "turn_count": 13,
```

| :--- | :--- |

## §6 시야 필터링 (Fog of War)

> **이 절이 이 문서의 핵심이다.** §4.1의 안티치트 요구가 여기서 결정된다.

### 원칙

**서버는 플레이어별로 시야를 계산하고, 플레이어마다 내용이 다른 상태 패킷을
전송한다.** 같은 게임의 두 플레이어가 동시에 받는 `game_state`는 내용이 다르다.

§4.1의 문구를 그대로 구현한다 — "백엔드(FastAPI + Redis)에서 플레이어 좌표 기준
인접 3×3 가시성과 벽 차폐를 연산한 후, **시야에 노출된 벽과 상대 말 좌표만**
WebSocket 패킷으로 전송".

### MUST NOT — 이 방식들은 요구를 무효화한다

| 금지 | 이유 |
| :--- | :--- |
| 전체 맵·전체 벽 목록을 보낸 뒤 클라이언트가 가리기 | 패킷을 감청하면 맵핵이 그대로 가능하다. 안티치트 목적이 완전히 사라진다 |
| 시야 밖 상대 말의 정확 좌표를 어떤 필드로든 포함 | 위와 동일 |
| 클라이언트가 계산한 시야를 받아 신뢰 | 조작 가능하다. 서버가 독립적으로 계산한다 |
| 전체 상태를 보내고 "클라이언트가 안 보여주면 된다"고 가정 | 클라이언트는 신뢰 경계 밖이다 |

### 상태 패킷 스키마

```json
{ "type": "game_state",
  "payload": {
    "game_id": "8f14e45f-…",
    "turn_count": 13,
    "current_seat_no": 2,
    "me": {
      "seat_no": 1,
      "position": { "row": 7, "col": 4 },
      "walls_remaining": 8,
      "goals": [ { "axis": "row", "value": 0 } ]
    },
    "discovered_edges": [
      { "row": 3, "col": 5, "orientation": "horizontal" },
      { "row": 6, "col": 2, "orientation": "vertical" }
    ],
    "visible_edges": [
      { "row": 3, "col": 5, "orientation": "horizontal" }
    ],
    "visible_players": [
      { "seat_no": 2, "position": { "row": 5, "col": 4 } }
    ],
    "last_seen_players": [
      { "seat_no": 3, "position": { "row": 2, "col": 6 }, "seen_at_turn": 9 }
    ],
    "others": [
      { "seat_no": 2, "nickname": "길잃은양", "walls_remaining": 9, "visible": true, "eliminated": false },
      { "seat_no": 3, "nickname": "돌쇠", "walls_remaining": 10, "visible": false, "eliminated": false }
    ]
  } }
```

필드별 공개 범위:

| 필드 | 내용 | 시야 밖일 때 |
| :--- | :--- | :--- |
| `me` | 내 정보 전체 | — (항상 전체) |
| `me.goals` | 내 목표 **목록**. 원소는 `{축, 값}` (§11) | — |
| `discovered_edges` | **이 플레이어가 지금까지 직접 본 변의 누적** | 유지된다 (아래) |
| `visible_edges` | **지금 시야 안에 있는 변** | 배열에서 제외 |
| `visible_players` | **시야 내 상대 말 좌표만.** 같은 좌표가 복수 등장할 수 있다 (§5 중첩 허용) | 배열에서 제외 |
| `last_seen_players` | **마지막으로 목격한 위치와 그 턴 번호** | 유지된다 (아래) |
| `others[].walls_remaining` | 상대의 남은 벽 개수 | **공개한다** (아래 근거) |
| `others[].eliminated` | 탈락 여부 (§9) | **공개한다** |
| `others[].position` | — | **필드 자체가 없다** |

> 전체 벽 목록 필드는 **존재하지 않는다.** 모든 배열이 이 플레이어가 **실제로
> 본** 것만 담는다.

#### 관측 단위는 *벽* 이 아니라 *단위 변* 이다

벽은 **2칸 길이**다(§7). 벽의 절반만 시야에 들어왔는데 벽 전체를 보내면
**보이지 않아야 할 절반이 드러난다** — 아래 MUST NOT 을 그대로 위반한다.
그래서 설치 단위와 관측 단위를 분리한다.

| 용도 | 단위 | 표현 |
| :--- | :--- | :--- |
| **설치·검증** (§7) | 벽 (2칸) | `{row, col, orientation}` — 교차점 기준 |
| **관측** (§6) | **단위 변** (1칸 경계) | `{row, col, orientation}` — **칸 기준** |

관측용 변 좌표 규약:

| `orientation` | 의미 | 범위 |
| :--- | :--- | :--- |
| `horizontal` | 칸 `(row, col)` 의 **북쪽** 변 | `1 ≤ row ≤ 8`, `0 ≤ col ≤ 8` |
| `vertical` | 칸 `(row, col)` 의 **서쪽** 변 | `0 ≤ row ≤ 8`, `1 ≤ col ≤ 8` |

보드 바깥 테두리는 변으로 표현하지 않는다 — 벽을 놓을 수 없는 자리이고
클라이언트가 이미 안다.

#### 발견 맵 — 플레이어가 직접 확인한 것만 쌓인다

각 플레이어는 **자신이 탐사하며 직접 확인한 것**으로 이루어진 지도를 갖는다.
서버는 이 지도를 플레이어별로 따로 들고 있다가 상태 패킷에 실어 보낸다.

| | 의미 | 시야를 벗어나면 |
| :--- | :--- | :--- |
| `visible_edges` | **지금 이 순간** 시야 안에 있는 변 | 사라진다 |
| `discovered_edges` | 게임 시작 이후 **한 번이라도 직접 본** 변의 누적 | **남는다** |
| `visible_players` | **지금** 시야 안에 있는 상대 말 | 사라진다 |
| `last_seen_players` | 좌석별 **마지막으로 목격한 위치 + 그 턴 번호**. 좌석이 달라도 좌표는 같을 수 있다 (§5 중첩 허용) | **남는다** |

`discovered_edges ⊇ visible_edges` 와 `last_seen_players ⊇ visible_players`
(좌석 기준)가 항상 성립한다.

클라이언트는 둘을 구분해 렌더링한다 — 발견했지만 지금 안 보이는 것은 흐리게,
지금 보이는 것은 선명하게. 목격 위치에는 턴 번호를 함께 띄워 **언제 적 정보인지**
알 수 있게 한다. **탐사한 지도가 누적**되는 것이 이 게임의 핵심 경험이다.
한 번 확인한 벽을 매번 다시 찾게 만들면 1인칭 미로가 아니라 기억력 테스트가 된다.

> **MUST NOT: 서버가 목격하지 않은 것을 채워 넣지 않는다.**
> 상대가 시야 밖에서 이동해도 `last_seen_players` 는 **그대로 둔다.** 갱신하면
> 시야 밖 좌표를 흘리는 것이다. 그 정보가 낡았다는 사실 자체가 게임성이며,
> 플레이어는 `turn_change.last_action` 으로 "그 좌석이 움직였다"까지만 안다.

**저장:** 플레이어별 발견 상태를 **Redis에 게임 수명 동안 보관**한다 (§2.2).
게임이 끝나면 폐기한다. 워커가 바뀌어도, 재접속해도 유지되어야 하므로 프로세스
메모리에 두지 않는다 — 인프라 마일스톤 M3 의존이다.

> 벽은 한 번 설치되면 사라지지 않으므로 `discovered_edges` 는 **단조 증가**한다.
> 무효화 로직이 필요 없다. `last_seen_players` 는 좌석당 1개를 덮어쓴다.

### 시야 밖 상대 정보 — 명시적 결정

암묵적으로 남기지 않고 항목별로 정한다.

| 정보 | 공개 | 근거 |
| :--- | :--- | :--- |
| 정확 좌표 | **비공개** | 맵핵의 핵심. 어떤 형태로도 주지 않는다 |
| 대략 방향·거리 힌트 | **비공개** | 삼각측량으로 좌표를 역산할 수 있다. 여러 턴에 걸쳐 수집하면 정확도가 올라간다 |
| 남은 벽 개수 | **공개** | 전략 판단의 기본 정보이고 위치를 드러내지 않는다. 벽을 설치할 때마다 1 줄어드는 것은 어차피 관측 가능하다 |
| 목표까지 남은 거리 | **비공개** | 위치를 강하게 시사한다 |
| 생존·탈락 여부 | **공개** | 게임 진행에 필수 (3인전에서 한 명이 빠지면 알아야 한다) |
| 턴을 썼다는 사실 | **공개** | `turn_change`로 이미 드러난다 |
| **누가 무엇을 했는가** | **공개** | `turn_change.last_action` 의 `seat_no` + `kind`(`move`\|`wall`). 아래 근거 |
| 그 행동의 **좌표** | **비공개** | 벽 위치·이동 목적지는 어떤 형태로도 담지 않는다 |

#### 행동 사실은 알리되 위치는 감춘다

상대가 내 시야 밖에서 벽을 설치하거나 이동하면, **누가 어느 종류의 행동을
했는지**까지만 알린다(`turn_change.last_action`). 좌표는 담지 않는다.

근거: 남은 벽 개수가 이미 공개되므로(위 표) "저 좌석이 벽을 놓았다"는 사실은
**어차피 개수 변화로 추론된다.** 추론 가능한 것을 숨기면 정보 우위는 생기지
않고 UI 만 일관성을 잃는다. 반면 **좌표는 추론 불가능**하므로 끝까지 감춘다.

`move` 와 `wall` 을 구분해 알리는 것도 같은 이유다 — 벽 개수가 줄지 않았다는
사실로 "이동했구나"가 이미 드러난다.

### 시야 계산 — 인접 3×3 과 벽 차폐

**플레이어는 칸 내부에 서 있고, 자기 칸을 중심으로 한 3×3 블록을 본다.**
시야는 **방향에 의존하지 않는다** — 360° 전방향이다. 각도(FOV)도 사거리도 없다.

```
   +---+---+---+   ← 3×3 의 바깥 테두리: 전송하지 않는다
   | a | b | c |
   +---#---#---+   ← # = 3×3 의 내부 변 12개
   | d | P | e |      (가로 2줄 × 3칸 + 세로 2줄 × 3칸)
   +---#---#---+
   | f | g | h |
   +---+---+---+
```

| 규칙 | 내용 |
| :--- | :--- |
| **범위** | 자기 칸 `P` 를 중심으로 한 **3×3**. 차폐 전 후보는 `a`~`h` 8칸 |
| **직교 차폐** | `P` 와 직교 인접 칸(`b` `d` `e` `g`) 사이에 벽이 있으면 **그 칸은 보이지 않는다.** 벽 자체는 보인다 — 막혔다는 사실은 안다 |
| **대각 차폐** | 대각 칸(`a` `c` `f` `h`)은 두 우회 경로 중 **하나라도 열려 있으면** 보인다. 예: `c` 는 `P→b→c` 와 `P→e→c` 가 **둘 다** 막혀야 안 보인다 |
| **보이는 변** | **보이는 칸에 접한 내부 변만** 전송한다. `P` 는 항상 보이므로 **내 4면은 언제나 전송된다** |
| **바깥 테두리** | 3×3 의 외곽 변은 **어떤 경우에도 전송하지 않는다** |

경로가 "열려 있다"는 것은 그 경로를 이루는 **두 변에 모두 벽이 없고, 경유하는
칸이 보인다**는 뜻이다. 즉 차폐는 `P` 에서 바깥으로 전파된다.

**예시 1 — 직교 한 면이 막힌 경우**

```
   +---+---+---+       P 의 북쪽(P｜b)에만 벽(===)이 있다
   | a | b | c |
   +---#===#---+       보이는 칸 : P  d e f g h
   | d | P | e |                   a (d 경유로 열림)
   +---#---#---+                   c (e 경유로 열림)
   | f | g | h |       안 보이는 칸: b
   +---+---+---+
                       전송하는 변 : P 의 4면(P｜b 벽 포함)
                                     + a d e f g h 에 접한 내부 변
                       전송 안 함  : a｜b, b｜c  (b 가 안 보인다)
```

**예시 2 — 대각이 완전히 차단되는 경우**

```
   +---+---+---+       P｜b 와 P｜e 가 둘 다 막혔다
   | a | b | c |
   +---#===#---+       보이는 칸 : P  d f g
   | d | P ‖ e |                   a (d 경유)
   +---#---#---+       안 보이는 칸: b, e, c
   | f | g | h |                   h 는 g 경유로 보인다
   +---+---+---+
                       c 는 P→b, P→e 두 경로가 모두 막혀 보이지 않는다
```

> **클라이언트가 시야를 보내지 않는다.** 보낼 값 자체가 없다 — 시야는 서버가
> 아는 `position` 하나와 벽 배치만으로 결정된다. 조작할 입력이 없다는 것이
> 이 규칙의 부수적인 이점이다.

### 성능

차폐 판정은 **칸 8개와 변 12개를 보는 상수 시간 연산**이다. 각도 레이캐스팅이
아니므로 보드가 커져도 플레이어당 비용이 변하지 않는다.

비용은 연산이 아니라 **전송**에 있다. **상태 패킷을 플레이어별로 따로 만들어야**
하므로 브로드캐스트를 재사용할 수 없다. `connection_manager`의 일괄
전송(`broadcast`)을 그대로 쓸 수 없고, **플레이어별 개별 전송**이 필요하다.

> M3 구현 시 주의: 현행 `ConnectionManager`에 게임 단위 브로드캐스트가 있다
> (`server/app/ws/connection_manager.py:36` `_game_players`). Fog of War에서는
> 같은 페이로드를 여러 명에게 보내는 경로를 **쓰지 않는다.**

## §7 벽 설치 검증

§4.1은 "벽 설치 시 **모든 플레이어**가 목표 지점까지 도달할 수 있는 경로가 최소
1개 이상 존재하는지 즉시 검증"을 요구한다.

검증 순서 (서버에서만 수행):

1. 내 턴인가 → 아니면 `not_your_turn`
2. 남은 벽이 있는가 → 없으면 `no_walls_remaining`
3. 좌표가 유효 범위(0-7)인가, 기존 벽과 겹치거나 교차하지 않는가
   → `invalid_wall_position`
4. **가상으로 설치한 뒤 모든 _생존_ 플레이어의 목표 도달 경로를 확인**
   → 한 명이라도 막히면 `wall_blocks_path`

3인전에서는 생존자 전부를 확인한다. 2인전 로직을 그대로 쓰면 3번째 플레이어가
갇힐 수 있다.

> **탈락자는 검증 대상에서 제외한다**(§9). 탈락한 좌석의 말은 보드에 남아
> 있더라도 더 이상 목표로 이동하지 않는다. 포함하면 그 말이 갇힌 순간부터
> **모든 벽 설치가 영구히 거절**된다.

> **구현:** `server/app/games/maze/core/pathfinder.py` 의 `can_place_wall_safely()`
> 가 **좌석 목록**을 받아 전원의 경로를 확인한다(M3 1단계에서 2인 서명을 일반화).
> 생존자만 넘기는 것은 호출자(`GameState.place_wall`)의 몫이다.

### 유효 수 목록을 서버가 주지 않는다

구 API에는 `GET /games/{id}/valid-moves`가 있었다. **이 설계에서는 제공하지
않는다** — 유효한 벽 위치 목록은 기존 벽 배치를 드러내므로 Fog of War가 무너진다.

클라이언트는 **자신이 발견한 정보(`discovered_edges`)로만** 후보를 계산해
표시한다. 발견하지 못한 벽 때문에 실제로는 놓을 수 없는 자리가 후보에 섞일 수
있으며, 그것이 아래의 설계 의도다.

> **이동에는 이 문제가 없다.** 합법 이동은 내 4면의 벽만으로 결정되고 §6이 그
> 4면을 항상 전송하므로, 클라이언트가 **합법 이동을 전부 스스로 계산한다**(§5).
> 서버 판정이 필요한 것은 **벽 설치뿐**이며, 이 절의 원칙에 예외를 두지 않는다.

### 거절 피드백은 의도된 게임 정보다

발견하지 못한 벽 때문에 경로가 막히는 자리에 벽을 놓으려 하면, 플레이어는
**"여기 놓으면 누군가의 길이 완전히 막히는구나"** 를 알게 된다. 이는 누출이
아니라 **추리 요소**다 — 보이지 않는 벽의 존재를 간접적으로 추론하는 수단이다.

단, 그 정보는 **플레이어가 스스로 기억해야 한다.** 서버는 기억해 주지 않는다.

| MUST | MUST NOT |
| :--- | :--- |
| 거절 시 `wall_blocks_path` 를 반환한다 | 거절된 좌표를 **누적·저장하지 않는다** |
| "이번 턴에 놓을 수 없음"만 전달한다 | 거절 이력을 조회하는 API를 만들지 않는다 |
| **턴당 거절 시도 횟수를 제한**한다 | 상태 패킷에 "놓을 수 없는 칸" 필드를 넣지 않는다 |
| 한도 초과 시 `probe_limit_exceeded` | **어느 벽이 원인인지, 누구의 경로가 막히는지 알리지 않는다** |

에러 본문에 좌표·경로·플레이어 식별자를 담지 않는다. 전달되는 것은 "이 자리는
지금 놓을 수 없다"는 사실 하나뿐이다.

#### 턴당 시도 제한

| 항목 | 값 |
| :--- | :--- |
| 턴당 허용 거절 횟수 | **2회** |
| **3회째 거절 시** | 이번 턴 **벽 설치가 잠긴다.** 반드시 말을 이동해야 한다 — **이동 가능한 칸은 항상 존재한다**(§5) |
| 잠긴 뒤 벽 시도 | `probe_limit_exceeded` |
| 시간 페널티 | **없다** (아래) |
| 리셋 시점 | **턴이 바뀔 때** |
| 세는 거절 | `wall_blocks_path` **와** 기존 벽과의 겹침·교차로 인한 `invalid_wall_position` — **같은 카운터** |
| 세지 않는 거절 | 좌표 범위(0-7) 밖, 방향값 무효, `no_walls_remaining` |
| 카운터 저장 | 게임 상태(`wall_rejections`)에 포함 — Redis `game:<id>:state` (§8) |

2회까지는 단순 오조작과 가벼운 탐색을 보장한다. 3회째 시도가 또 거절되면 그
턴에는 더 이상 벽을 놓을 수 없고 이동만 남는다. 3회째 거절은 원래 사유 코드를
그대로 반환하고, 그 뒤의 벽 시도부터 `probe_limit_exceeded` 다.

**겹침·교차도 같은 카운터로 센다 (2026-10-01 확정).** 겹침·교차는 경로 차단과
똑같이 정보를 흘린다 — 클라이언트는 **발견한 벽만** 알기 때문에, 발견하지 못한 벽과
겹친다는 거절은 *"그 자리에 보이지 않는 벽이 있다"* 를 직접 알려 준다. 경로 차단만
세면 겹침 판정으로는 126개 후보를 무제한 찔러 **벽 배치를 그대로 복원**할 수 있어
이 절의 상한이 무의미해진다. 두 사유를 하나의 카운터에 묶어 어느 쪽으로든 탐색
총량이 같게 한다. 범위 밖 좌표는 보드 크기만으로 판정되어 숨은 정보가 없으므로
세지 않는다.

**거절에는 시간 페널티를 주지 않는다.** 게임 시계는 자기 턴이 흐르는 만큼만
줄어들 뿐이고(§8), 거절했다고 추가로 깎지 않는다.

#### 왜 이 정도로 충분한가 — 탐색은 스스로 억제된다

횟수 제한보다 강한 억제 장치가 이미 규칙 안에 있다. **허공에 찔렀는데 벽이
정상적으로 설치되어 버리면 턴이 끝나고 벽 1개를 잃는다.** 그 손실이 크기 때문에
플레이어는 알아서 확신이 있을 때만 찌른다. 횟수 제한은 그 위에 얹는 상한이다.

상한이 여전히 필요한 이유: 제한이 없으면 한 턴에 전 좌표를 훑어 **벽 그래프를
사실상 복원**할 수 있다. 9×7×2 = 126개 후보를 모두 시도하면 어느 자리가 경로를
끊는지 전부 알게 되고, 그로부터 보이지 않는 벽의 배치를 역산할 수 있다.
Fog of War가 무너진다.

"기억해야 할 정보"라는 성격은 **얻는 데 비용이 있을 때만** 성립한다. 공짜로
무한히 조회할 수 있으면 기억할 이유가 없다.

> 거절이 턴을 소모하지는 **않는다.** 오조작·오해로 턴을 날리는 벌이 지나치게
> 크기 때문이다. 대신 횟수로 제한하고, 넘으면 그 턴의 벽 설치만 막는다.

## §8 시간 체계

**턴당 제한 시간을 두지 않는다.** 체스처럼 플레이어마다 전체 시간을 주고
수마다 증분을 더하는 **Fischer 방식**을 쓴다.

### 두 개의 시계를 완전히 분리한다

| | **게임 시계** | **접속 시계** |
| :--- | :--- | :--- |
| 측정 대상 | 그 플레이어의 누적 사고 시간 | 그 플레이어가 **끊겨 있던** 누적 시간 |
| 방식 | Fischer — 초기 `300초`, 수마다 `+5초` | 총량 `60초`에서 차감 |
| 흐르는 조건 | **자기 차례일 때만** | **연결이 끊긴 동안만** (차례와 무관) |
| 소진 시 | 시간패 → 탈락 (`time_forfeit`) | 기권패 → 탈락 (`disconnect_forfeit`) |
| 재접속하면 | 영향 없음 | **리셋하지 않는다 — 절대 누적값** (§9) |

> **왜 분리하는가.** 하나로 합치면 "끊고 생각하기"가 성립한다. 고의로 네트워크를
> 끊은 뒤 천천히 수를 고르고 돌아오면 되기 때문이다. 분리하면 끊은 동안
> **자기 차례라면 게임 시계가 계속 줄고, 동시에 접속 시계도 준다** — 양쪽에서
> 손해를 본다. 어느 쪽도 끊김으로 이득을 볼 수 없다.

두 시계의 남은 값은 `turn_change.clocks` 와 `game_state` 로 전원에게 공개한다.
숨길 이유가 없고, 상대의 시간 압박을 읽는 것은 정상적인 전략 요소다.

### Fischer 산정 — 서버 권위

```
턴 시작      : turn_started_at ← 서버 시각
행동 수락 시 : remaining -= (서버 수신 시각 - turn_started_at)
               remaining += increment
               remaining <= 0  →  시간패 (§9 탈락 처리)
```

- **클라이언트가 보낸 시각을 쓰지 않는다.** 서버 수신 시각만 쓴다
  (`PLATFORM_ARCHITECTURE.md` §3.3 원칙 2)
- **상행 지연 보정식을 두지 않는다.** 보정하려면 클라이언트가 주장하는 시각을
  신뢰해야 하므로 Zero-Trust 를 깬다. `increment 5초`가 왕복 지연보다 훨씬 커서
  실질적으로 그 역할을 한다

거절된 벽 시도(§7)는 행동이 아니므로 `remaining` 을 추가로 깎지 않는다. 다만
그 사이에도 자기 턴은 흐르므로 경과분만큼은 자연히 줄어든다.

### 하트비트 — 끊김을 즉시 인지한다

**WebSocket 프로토콜 레벨의 ping/pong 을 쓴다** (uvicorn `--ws-ping-interval` /
`--ws-ping-timeout`). 응답이 끊기면 서버가 그 시점부터 접속 시계를 돌린다.

앱 레벨 하트비트 메시지를 만들지 않는다 — §12 어휘를 늘리지 않고 같은 일을
할 수 있다.

### 만료 감지 — Redis ZSET + 스위퍼

감지해야 할 데드라인은 두 종류다. 하나의 정렬 집합에 담고 전용 루프가 훑는다.

| 요소 | 설계 |
| :--- | :--- |
| 색인 | ZSET `maze:deadlines` — score = 만료 시각(epoch ms) |
| member | `clock:<game_id>` — 현재 차례 좌석의 게임 시계 소진 예정 시각<br>`grace:<game_id>:<seat_no>` — 접속 시계 소진 예정 시각 |
| 갱신 | 턴이 바뀌면 `ZADD` 로 덮어쓴다. 끊기면 `grace:` 를 추가하고 재접속하면 지운다 |
| 감지 | 각 워커가 1초 주기로 `ZRANGEBYSCORE key -inf <now> LIMIT 0 N` |
| 중복 방지 | 후보마다 `ZREM` 을 호출해 **반환값이 1인 워커만** 처리한다. 원자적 선점이라 **리더 선출이 필요 없다** |
| 지연 보정 | 행동 수신 시에도 데드라인을 비교해 이미 지났으면 만료를 먼저 처리한다 |
| 통보 | 처리 결과를 Redis Pub/Sub 으로 방 채널에 발행하고, 연결을 가진 워커가 **플레이어별 개별 전송**(§6)한다 |

게임 시계는 자기 차례에만 흐르므로 `clock:` 은 게임당 **항상 하나**다.
접속 시계는 좌석마다 독립이라 `grace:` 는 여러 개가 동시에 존재할 수 있다.

**기각한 대안**

| 대안 | 기각 이유 |
| :--- | :--- |
| 키 TTL + keyspace notification `Ex` | ① `notify-keyspace-events` 를 Redis 설정에 켜야 한다 — 현재 `docker-compose.yml` 의 `redis-server` 인자에 없다 ② Pub/Sub 은 **at-most-once** 다. 구독자가 재연결 중이면 만료 이벤트가 영구히 소실되고 **그 게임은 영원히 멈춘다** ③ 통지 시점이 키 접근·능동 만료 사이클에 의존해 비결정적이다. 결국 복구용 폴링을 또 만들어야 한다 |
| 전체 게임 주기 폴링 | 게임 수에 비례하는 스캔. ZSET 은 같은 일을 `O(log N + k)` 로 한다 |
| APScheduler 에 턴마다 잡 등록 | 기본 잡 저장소가 프로세스 메모리라 워커가 죽으면 소실된다. Redis 저장소를 붙이면 위 설계를 더 무겁게 재구현한 것이 된다 |
| `asyncio.call_later` | 워커에 종속된다. `PLATFORM_ARCHITECTURE.md` §2.2 위반 |

> 게임이 늘어도 키를 `<game>:deadlines` 로 두고 member 접두어에 핸들러를
> 등록하면 된다. **인원 수와는 무관**한 구조다.

### 워커 장애와 배포 — 게임은 이어진다

**게임 상태의 권위는 Redis 다.** 워커는 상태를 소유하지 않는다. 어느 워커든
행동을 받으면 게임별 락을 잡고 Redis 에서 상태를 읽어 판정·기록한다. 그래서
워커가 죽거나 배포로 교체되어도 **게임은 끝나지 않는다** — 끊긴 플레이어가
재접속하면 아무 워커에 붙어 그대로 이어간다.

> **근거는 실측이다** ([`../../research/2026-10-01-워커-redis-실측.md`](../../research/2026-10-01-워커-redis-실측.md)).
> 재접속의 3~15% 가 다른 워커에 붙으므로(E1) 상태를 워커 메모리에 두면
> 재접속 자체가 성립하지 않는다. 락 + 상태 읽기·쓰기는 행동당 p99 ≈ 2 ms 다(E6).
> 이전 설계(소유 워커 기록 + 워커 사망 시 무효)는 **배포마다 진행 중인 게임 전원을
> 무효로 만드는** 설계였으므로 폐기했다.

| 요소 | 설계 |
| :--- | :--- |
| 상태 위치 | Redis `game:<id>:state`. 프로세스 메모리에 권위 있는 사본을 두지 않는다 |
| 직렬화 | 게임별 락 (`SET NX PX` + 토큰 비교 해제). 행동·스위퍼 만료 처리·항복이 모두 같은 락을 쓴다 |
| 워커 크래시 | 그 워커의 소켓만 끊긴다(1006). uvicorn 마스터가 워커를 재기동한다(실측 ≈3.6 s). 끊긴 플레이어는 **일반 끊김**으로 처리한다 — 접속 시계가 흐른다 |
| 배포 (정상 종료) | 소켓이 1012 로 끊긴다. **서버 유예**를 적용한다 (아래) |
| Pub/Sub | 통지 수단일 뿐 권위가 없다. at-most-once 라 재구독 사이의 메시지는 유실된다(E5). 워커는 **재구독 직후 자기 소켓 전원에게 Redis 상태로 재동기화**를 보낸다. 워커마다 패턴 구독 하나로 모든 게임·방 채널을 받고, 이벤트의 수신자 중 자기에게 연결된 유저에게만 좌석별로 만든 패킷(§6)을 보낸다 — 채널 설계는 [`../platform.md`](../platform.md) "이벤트 채널" |
| 재접속 경로 | 종료 중인 인스턴스에 다시 붙었다가 한 번 더 끊길 수 있다(E4). 재접속 흐름은 연속 끊김을 정상 경로로 다룬다 |

#### 서버 유예 — 배포로 끊긴 시간은 플레이어에게 물리지 않는다

배포로 끊긴 좌석은 재접속할 때까지 **접속 시계와 게임 시계를 모두 멈춘다.**
배포는 플레이어 잘못이 아니다.

| 요소 | 설계 |
| :--- | :--- |
| 판별 | **서버 프로세스가 종료 단계에 들어갔는가**로만 판별한다 |
| 판별에 쓰지 않는 것 | **close code 1012.** 클라이언트가 직접 1012 로 닫아도 서버 핸들러에는 똑같이 1012 로 보인다(실측). 코드로 판별하면 누구나 접속 시계를 면제받는다 |
| 순서 제약 | uvicorn 은 소켓을 **먼저** 닫고 lifespan shutdown 을 **나중에** 돈다(E3). 끊김 핸들러가 실행되는 시점에는 lifespan 이 아직 종료를 알리지 않았다. 구현은 이 순서를 전제로 해야 한다 |
| 상한 | 서버 유예는 `server_grace_max`(초기 `30초`)까지만. 넘으면 일반 끊김으로 전환해 접속 시계가 흐른다. 신 인스턴스 기동 공백 실측은 ≈7 s 다(E4) |
| 크래시 | 면제하지 않는다. 크래시한 워커는 아무것도 남기지 못하고, 판별하려면 워커 하트비트·좌석별 소속 워커 기록이 추가로 필요하다. 드물고 재기동이 짧아 일반 끊김으로 처리한다 |

### Redis 장애 시 무효 처리 (Fail-safe)

무효 처리는 **게임 상태 자체를 잃었을 때**만 한다. 워커 장애나 배포는 해당하지 않는다(위).
플레이어 잘못이 아닌 것으로 MMR 이 움직이면 안 된다.

| 요소 | 설계 |
| :--- | :--- |
| 트리거 | 진행 중인 게임(`game_sessions` 에 진행 중으로 기록된 게임)의 Redis 상태가 **사라졌다** |
| 짧은 Redis 장애 | 무효가 아니다. 재시작 시 풀이 스스로 재연결하고 AOF 로 상태가 남는다(E7, 장애 ≈2 s, 유실 0). 장애 중 행동은 실패로 응답하고 클라이언트가 재시도한다 |
| 가드 | `is_redis_available()` 는 **기동 시 한 번 정해지는 값**이다. 장애 내내 `true` 였다(E7). 멀티 경로는 Redis 예외를 직접 처리한다 |
| 결과 | `game_end.reason = "server_fault"`, 전원 `result = "void"`.<br>**MMR 변동 0, 전적 미집계** (§10) |

무효 처리된 게임도 `full_board` 는 공개한다(§10). 복기 가치는 동일하고,
막는 것은 레이팅 반영뿐이다.

> **미결 — 긴 Redis 장애 중 시계:** 장애가 길어지면 스위퍼가 멈췄다가 복구 직후
> 한꺼번에 만료를 처리해 시간패가 쏟아질 수 있다. 장애 구간을 시계에서 빼는 방식과
> 장애가 얼마나 길면 무효로 돌릴지는 M3 시간 체계 단계에서 확정한다.

## §9 이탈·탈락·종료 조건

**이 절의 규칙은 모드와 무관하다.** 2인전·3인전이 다른 규칙을 쓰지 않는다.

> 과거 설계는 "항복하면 게임이 끝난다"처럼 **2인 전제**로 적혀 있었다.
> 3인 이상에서는 그 플레이어만 빠지고 게임이 계속되므로, **좌석의 탈락**과
> **게임의 종료**를 분리해 정의한다.

### 재접속

연결이 끊긴 뒤 다시 접속하면 `connected` 메시지에 `reconnect`가 포함된다(§2).
클라이언트는 이어서 `game_state`를 받아 현재 상황을 복원한다.

- **접속 시계는 게임당 누적 60초다**(§8). 끊긴 동안만 줄어들고, **재접속해도
  리셋되지 않는다**
- 유예 중 나머지에게 `player_left`가 `state: "reconnecting"` 으로 간다
- 접속 시계가 0이 되면 `disconnect_forfeit` 으로 **탈락**한다
- **배포로 끊긴 경우는 예외다.** 서버 유예 동안 접속 시계와 게임 시계가 멈춘다(§8)

> **리셋하지 않는 이유:** 접속할 때마다 60초가 되돌아오면 "끊었다 붙었다"를
> 반복하며 사실상 무한히 시간을 벌 수 있다. 한 게임 동안의 **절대 누적 상한**이다.

> **재접속 시 시야:** 서버가 현재 위치 기준으로 시야를 다시 계산해 보내고,
> Redis에 보관된 발견 맵(§6)을 그대로 복원한다. 끊긴 동안 상대가 움직인 경과는
> **전달하지 않는다** — 그 이력을 주면 시야 밖에서 일어난 일이 드러난다.

### 이탈

```json
{ "type": "leave_room", "seq": 5 }
```

게임 시작 전에만 유효하다. 시작 후 이탈은 항복과 동일하게 처리한다.

### 항복

```json
{ "type": "surrender", "seq": 20 }
```

즉시 **탈락**한다. 게임이 끝나는지는 아래 종료 조건이 따로 판정한다.

### 탈락 — 좌석 단위

| 사유 | 트리거 |
| :--- | :--- |
| `surrender` | 본인이 `surrender` 를 보냈다. 시작 후 방 이탈도 같다 |
| `time_forfeit` | **게임 시계 소진**(§8). 시계는 자기 차례에만 흐르므로 **항상 자기 차례에** 발생한다 |
| `disconnect_forfeit` | **접속 시계 소진**(위) |

탈락이 확정되면 서버는 다음을 수행한다.

1. 그 좌석을 탈락 표시하고 **탈락 순번**을 부여한다 (순위 산정에 쓴다)
2. **턴 순환에서 제외**한다
3. 그 좌석의 게임 시계·접속 시계 데드라인을 ZSET에서 **제거**한다(§8)
4. **§7 경로 보장 검증 대상에서 제외**한다 — 포함하면 그 말이 갇힌 순간부터
   모든 벽 설치가 영구히 거절된다
5. 탈락자가 현재 차례였다면 **즉시 다음 생존자로 턴을 넘기고** 새 게임 시계
   데드라인을 건다
6. 남은 전원에게 `player_left` 를 보낸다

```json
{ "type": "player_left",
  "payload": {
    "seat_no": 2,
    "state": "eliminated",
    "reason": "time_forfeit",
    "survivors": 2
  } }
```

| 필드 | 설명 |
| :--- | :--- |
| `state` | `reconnecting`(일시) \| `eliminated`(확정) |
| `reason` | 탈락 사유 3종. `state: "reconnecting"` 이면 `null` |
| `grace_remaining_ms` | `state: "reconnecting"` 일 때만. 남은 접속 시계 |
| `survivors` | 통보 시점의 생존자 수 |

탈락자의 말은 보드에 남지만 더 이상 움직이지 않는다. 다른 플레이어는 그 말을
여전히 볼 수 있다(§6). **이동 규칙상 장애물이 아니다** — 살아있는 말과 똑같이
통과·중첩 가능하다(§5).

> 장애물로 두면 1칸 통로에 선 순간 **영구 장벽**이 되는데, §7의 경로 보장 검증은
> 말을 통과 가능으로 보고 계산하므로 "검증은 통과했지만 실제로는 갈 수 없는"
> 상태가 생긴다. 중첩 허용으로 이 불일치가 애초에 발생하지 않는다.

### 게임 종료 — 셋뿐이다

| 조건 | `game_end.reason` | 결과 |
| :--- | :--- | :--- |
| 누군가 목표에 도달했다 | `goal_reached` | 도달자가 1위. 즉시 종료 |
| **생존자가 1명만 남았다** | `last_standing` | 그 1명이 1위. 즉시 종료 |
| Redis 상태 유실 (§8) | `server_fault` | 전원 `result: "void"`. MMR 변동 0 |

**2인전은 자동으로 성립한다** — 한 명이 탈락하면 생존자가 1명이 되어
`last_standing` 이다. 모드별 분기가 필요 없다.

> **게임 수준 사유와 좌석 수준 사유를 분리한다.** 왜 끝났는지는
> `game_end.reason` 이, 누가 왜 빠졌는지는 `results[].elimination_reason` 이
> 답한다. 과거의 `surrender`·`disconnect_timeout`·`turn_timeout` 은 **좌석 사유를
> 게임 사유 자리에 적던 것**이라 2인에서만 맞았다.

### 순위 산정 — 모드 무관

```
순위 = [목표 도달자]
     > [생존자]  남은 최단 거리가 짧은 순
                 → 같으면 사용한 턴 수가 적은 순
                 → 그래도 같으면 공동 순위
     > [탈락자]  탈락 순번의 역순 (나중에 탈락한 쪽이 상위)
```

> **탈락 역순인 이유:** 오래 버틴 것은 성과다. 탈락자를 전부 공동 최하위로 두면
> 10턴 만에 끊고 나간 사람과 25턴을 싸우다 항복한 사람의 MMR 변동이 같아지고,
> **조기 이탈에 아무 불이익이 없어진다.**

예 (3인전): `seat2` 가 10턴에 시간패, `seat1` 이 목표 도달
→ 1위 `seat1`(도달) / 2위 `seat3`(생존) / 3위 `seat2`(탈락)

공동 순위는 MMR 쌍별 분해에서 무승부(`S=0.5`)로 처리한다
([`../platform.md`](../platform.md) §4.2).

## §10 종료와 MMR 반영

```json
{ "type": "game_end",
  "payload": {
    "game_id": "8f14e45f-…",
    "reason": "goal_reached",
    "results": [
      { "seat_no": 1, "nickname": "미로장인", "rank": 1, "result": "win",
        "elimination_reason": null,
        "mmr_before": 1042, "mmr_after": 1058, "mmr_delta": 16 },
      { "seat_no": 2, "nickname": "길잃은양", "rank": 2, "result": "lose",
        "elimination_reason": "time_forfeit",
        "mmr_before": 998, "mmr_after": 982, "mmr_delta": -16 }
    ],
    "full_board": { }
  } }
```

| `reason` | 의미 |
| :--- | :--- |
| `goal_reached` | 누군가 목표에 도달했다 |
| `last_standing` | 생존자가 1명만 남았다 (§9) |
| `server_fault` | Redis 의 게임 상태를 잃어 무효 처리했다 (§8). 워커 장애·배포는 해당하지 않는다 |

| `results[]` 필드 | 의미 |
| :--- | :--- |
| `rank` | 최종 순위. 산정 규칙은 §9 |
| `result` | `win` \| `lose` \| `draw` \| **`void`**(서버 장애) |
| `elimination_reason` | `surrender` \| `time_forfeit` \| `disconnect_forfeit` \| `null`(탈락하지 않음) |

> **왜 사유가 두 곳에 나뉘는가:** `reason` 은 **게임이** 왜 끝났는지, 
> `elimination_reason` 은 **그 좌석이** 왜 빠졌는지를 답한다. 3인전에서 한 명이
> 항복해도 게임은 끝나지 않으므로 둘을 같은 필드에 담을 수 없다 (§9).

### MMR은 서버가 계산한다

산정식은 [`../platform.md`](../platform.md) §4.2를 따른다 (Elo, 초기 1000,
배치 10판 K=40 / 이후 K=24).

> **MUST:** 클라이언트는 결과를 **통보받을 뿐**이다. 승패를 주장하는 메시지
> 타입은 존재하지 않는다 (§3.3 원칙 2).

친구 대전(`is_ranked=false`)과 `server_fault` 무효 게임은 `mmr_*` 필드가 `null`이다.

### 종료 후 최종 상태를 공개한다

`full_board`는 **게임이 끝난 뒤에만** 채워진다. 경기 중에는 어떤 메시지에도
전체 맵이 포함되지 않는다.

```json
"full_board": {
  "walls": [ { "row": 3, "col": 5, "orientation": "horizontal" } ],
  "final_positions": [
    { "seat_no": 1, "row": 0, "col": 4 },
    { "seat_no": 2, "row": 5, "col": 4 }
  ]
}
```

| 담는다 | 담지 않는다 |
| :--- | :--- |
| 최종 **벽** 배치 (2칸 단위 — 전부 공개되므로 변으로 쪼갤 이유가 없다) | **이동 경로** |
| 좌석별 **최종 위치** | **수 기록 / 턴별 스냅샷** |

**경로와 수 기록을 담지 않는 것은 의도된 제한이다.** 리플레이는 2026-10-01에
폐기했고([`../platform.md`](../platform.md) §6), 여기에 경로를 넣으면
`full_board` 가 리플레이의 우회로가 된다. 복기 기능이 필요해지면 리플레이를
재도입할 때 **함께** 설계한다 ([`../../ROADMAP.md`](../../ROADMAP.md) 향후 확장).

랭크·친선·무효를 구분하지 않고 동일하게 공개한다. 모드마다 다르게 하면
클라이언트가 두 경로를 다뤄야 하고, 복기 가치가 가장 큰 쪽이 바로 랭크전이다.

> 연속 대전에서 상대의 벽 설치 성향이 누적된다는 우려가 있으나, 상대의 버릇을
> 읽는 것은 보드게임에서 정상적인 실력 요소다. 벽은 매 판 새로 놓이므로
> 고정된 정보도 아니다. 무엇보다 **공개 시점이 종료 후**라 경기 중
> Fog of War(§6)에는 영향이 없다.

## §11 1:1:1 전용 규칙

2인 규칙에서 자동으로 유도되지 않는 것들이다. 게임 엔진은 M3 1단계에서 좌석 수를
가정하지 않게 일반화했고(`app/games/maze/core/layouts.py` 배치 테이블), 매치메이킹·방도
M3 3단계에서 정원을 그 테이블에서 받는다(`app/services/matchmaking.py`·`rooms.py`).

### 좌석과 목표 — 네 꼭짓점 중 랜덤 3개

3인전은 보드의 **네 꼭짓점** `(0,0) (0,8) (8,0) (8,8)` 중 **랜덤하게 3개**를
골라 좌석에 배정한다. 목표는 그 꼭짓점의 **대각 반대편 두 변**이다.

| 시작 꼭짓점 | 목표 |
| :--- | :--- |
| (0, 0) | `row 8` ∪ `col 8` |
| (0, 8) | `row 8` ∪ `col 0` |
| (8, 0) | `row 0` ∪ `col 8` |
| (8, 8) | `row 0` ∪ `col 0` |

```
   시작 (0,0)                  목표: row 8  ∪  col 8   (L자 17칸)
     0 1 2 3 4 5 6 7 8
   0 S . . . . . . . G
   1 . . . . . . . . G
   …                   G
   8 G G G G G G G G G
```

네 꼭짓점 모두 목표가 17칸이고 최단 거리가 8로 **완전히 대칭**이다.
어느 꼭짓점을 받아도 불리하지 않다.

**목표는 `(축, 값)` 의 목록이다.**

```json
"goals": [ { "axis": "row", "value": 8 }, { "axis": "col", "value": 8 } ]
```

> 구 엔진의 `Player.goal_row` 는 단일 행만 표현했다. M3 1단계에서 `Player.goals`
> (`Goal(axis, value)` 의 튜플)로 일반화했다. 2인전은 원소 1개, 3·4인전은
> 2개이므로 **원소 수만 다르고 구조는 같다.**

- **목표를 꼭짓점 1칸으로 두지 않는 이유:** 벽 2개면 봉쇄된다. §7의 경로 보장
  검증이 상시 발동해 벽 설치가 자주 거절되고, §7의 거절 2회 제한과 충돌한다
- **목표를 3×3 영역으로 두지 않는 이유:** 목표가 `(축, 값)` 이 아니라 *영역*이
  되어 엔진이 일반화해야 할 범위가 불필요하게 커진다

### 왜 2인전은 꼭짓점이 아닌가

2인전은 **변 중앙을 유지한다** — `(8,4) → row 0`, `(0,4) → row 8`.

| 쟁점 | 판단 |
| :--- | :--- |
| **3인이 꼭짓점인 것은 취향인가** | 아니다. **제약**이다. 네 변 중 세 변에 배치하면 한 명만 마주보는 상대가 없어 비대칭이 된다. 꼭짓점이 유일한 대칭 해였다 |
| **모드마다 다르면 비일관 아닌가** | 데이터 구조는 이미 통일돼 있다 — `goals[]` 목록과 좌석별 시작 테이블. 시작 좌표는 **테이블의 값일 뿐**이고, "인원이 4명이 되면 무엇을 고쳐야 하는가"에 **행 추가**라고 답할 수 있다 |
| **밸런스** | 변 중앙은 목표가 9칸이라 **벽 10개의 가치가 높다.** 꼭짓점+두 변은 목표가 17칸이라 봉쇄가 어려워져 벽 가치가 떨어지고 재조정이 필요해진다 |
| **상호작용** | 변 중앙은 두 경로가 `col 4` 에서 **정면으로 만난다.** 3×3 시야(§6)에서 중앙에서 반드시 조우하므로 **조우 자체가 정보 획득**이 된다 — 상대 위치·진행도를 그때 처음 읽는다. 대각 출발은 서로 한 번도 못 만나고 끝날 수 있다 |

**모드별 배치 테이블** — 행 추가로 확장한다.

| `mode` | 시작 | 목표 | 인당 벽 |
| :--- | :--- | :--- | :--- |
| `duel` | 변 중앙 대향 2점 | 반대 변 1개 | 10 |
| `trio` | 네 꼭짓점 중 랜덤 3 | 대각 반대 두 변 | 7 |
| `quad` *(미래)* | 네 꼭짓점 전부 | 대각 반대 두 변 | — |

### 벽 배분

3인전은 **인당 7개**(총 21개)다. 2인전의 총 20개(인당 10)와 근사해 보드
포화도가 유지된다. 인당 10개면 총 30개가 되어 과포화된다.

### 턴 순서

`seat_no` 오름차순 순환. 탈락자는 건너뛴다(§9).

### 승패·순위·탈락은 §9를 따른다

탈락 사유, 탈락 처리 절차, 게임 종료 조건, 순위 산정은 **모드 무관 공통
규칙**이므로 [§9](#9-이탈탈락종료-조건)에 있다. 3인전 전용 규칙이 아니다.

3인전에서 확인해 둘 점만 적는다.

- 항복·시간패·접속 소진은 **그 좌석만 탈락**시키고 게임은 남은 2명으로 계속된다
- 2명이 탈락하면 남은 1명이 `last_standing` 으로 1위 종료
- 탈락자끼리의 순위는 **탈락 역순**이다 — 먼저 나간 쪽이 더 낮다

### MMR — `trio` 는 독립 풀이다

**`maze_1p:duel` 과 `maze_1p:trio` 는 서로 다른 MMR 풀이다**
([`../platform.md`](../platform.md) §4.2). 1:1은 상대 하나를 읽는 게임이고,
1:1:1은 두 상대의 상호작용과 어부지리가 개입하는 다른 게임이다. 한 풀에 두면
한쪽 실력이 다른 쪽 매칭 품질을 망친다.

3인 순위를 Elo에 반영하는 변환:

```
쌍: (1위,2위) (1위,3위) (2위,3위)
각 쌍에서 상위가 승(S=1), 하위가 패(S=0), 공동 순위는 무승부(S=0.5)
ΔR_x = Δ_쌍1 + Δ_쌍2                 # x 가 참여한 두 쌍의 합
```

**합산한다. 2로 나누지 않는다.** 초판은 duel과 변동폭을 맞추려고 2로 나눴으나,
풀이 분리된 지금은 맞출 대상이 없다. 변동폭 조절은 **모드별 K 계수**로 한다
(`trio`: 배치 중 32, 이후 16 — [`../platform.md`](../platform.md) §4.2).

> 풀 분리의 부수 효과: "3인전만 반복하는 편법"이 성립하지 않는다. trio MMR을
> 올려도 duel 리더보드·매칭에 전혀 영향이 없기 때문이다. 정규화로 막던 문제가
> 구조적으로 사라졌다.
