## §1 개요와 전송 방식

| 항목 | 값 |
| :--- | :--- |
| 게임 ID | `maze_1p` |
| 보드 | 9×9. 벽은 교차점 2칸 길이 (0-7) |
| 인원 | 1:1 (2인) 또는 1:1:1 (3인) |
| 전송 | **WebSocket 단일 채널** |
| 엔드포인트 | `wss://<host>/api/v1/ws/maze` |

### 왜 REST가 아니라 WebSocket인가

구 Quoridor는 턴마다 REST를 호출했다(`POST /games/{id}/move`). 1인칭 미로는
그 방식으로 구현할 수 없다.

1. **시야가 상대 행동에 따라 바뀐다.** 상대가 이동하면 내 시야에 들어오거나
   나갈 수 있다. 서버가 능동적으로 알려야 한다 — 폴링으로는 즉시성이 없다.
2. **턴 타이머가 서버에 있다.** 시간 초과를 서버가 통보해야 한다.
3. §4.1이 "120fps 유지"를 요구한다. 매 프레임 폴링은 불가능하다.

### 솔로 플레이는 서버를 쓰지 않는다

§1.1에 따라 솔로(AI 대전)는 **100% 오프라인**이다. 로컬 AI·판정·렌더링을
클라이언트가 수행하며 이 문서의 API를 전혀 호출하지 않는다.

> 서버의 `app/games/maze/ai/simple_ai.py`는 **서버 측 판정 보조**용으로만 남는다.
> 클라이언트 AI는 Dart로 별도 구현한다 (§2.1의 Dart Isolate).
> 관련 미결: [`../platform.md`](../platform.md) §6의 `ai-move` 항목.

### 메시지 봉투

REST의 `data` 봉투와 달리 WebSocket은 `type`으로 분기한다.

```json
{ "type": "move", "seq": 12, "payload": { } }
```

| 필드 | 설명 |
| :--- | :--- |
| `type` | `WSMessageType` 값 (§12) |
| `seq` | 클라이언트 → 서버에만. 요청 일련번호. 서버 응답·에러에 `ack_seq`로 되돌려 준다 |
| `payload` | 타입별 본문 |

서버 → 클라이언트 에러는 공통 규약의 필드명을 유지한다.

```json
{ "type": "error", "ack_seq": 12,
  "payload": { "error": "not_your_turn", "message": "내 차례가 아닙니다." } }
```

## §2 접속과 인증

```
wss://<host>/api/v1/ws/maze?token=<access_token>
```

- 인증은 **연결 수립 시 1회**. 쿼리 파라미터로 access token을 보낸다.
  WebSocket 핸드셰이크는 커스텀 헤더를 브라우저에서 설정할 수 없어 쿼리를 쓴다.
  **access token만** 허용한다 (`typ=access` 검증). 리프레시 토큰은 거부한다.
- 토큰이 없거나 무효면 핸드셰이크를 수락하지 않고 close code로 끊는다 (§13).
- **익명 계정은 거부한다.** 멀티플레이는 카카오 로그인 필수(§1.1)이므로
  `auth=anonymous` 토큰은 `login_required`로 끊는다.
- **닉네임이 없으면 거부한다.** 상대에게 표시할 이름이 필요하다
  → `nickname_required`.

연결 성공 시 서버가 먼저 보낸다.

```json
{ "type": "connected",
  "payload": {
    "user_id": 2210,
    "nickname": "미로장인",
    "mmr": 1042,
    "reconnect": { "game_id": "…", "seat_no": 2 }
  } }
```

`reconnect`는 진행 중인 게임이 있을 때만 포함된다 (§9).

> 같은 계정으로 새 연결이 들어오면 **기존 연결을 끊는다** (close code 4000).
> 현행 `ConnectionManager.connect`가 이미 이 동작을 한다
> (`server/app/ws/connection_manager.py:48`) — 재사용한다.

## §3 매치메이킹

### 큐 참가

```json
{ "type": "join_queue", "seq": 1, "payload": { "mode": "duel" } }
```

| `mode` | 인원 | 비고 |
| :--- | :--- | :--- |
| `duel` | 2 | 1:1 |
| `trio` | 3 | 1:1:1 |

모드별로 큐가 분리된다. 한 사용자는 동시에 하나의 큐에만 들어간다.

```json
{ "type": "queue_joined", "ack_seq": 1,
  "payload": { "mode": "duel", "position": 3, "waiting_count": 7,
               "estimated_wait_sec": 20 } }
```

대기 중 주기적으로 `queue_status`가 온다.

### MMR 범위 확장

기다린 시간에 따라 허용 MMR 차이를 넓힌다. 좁게 시작해 점점 완화한다.

| 경과 | 허용 MMR 차 |
| :--- | :--- |
| 0~10초 | ±100 |
| 10~30초 | ±200 |
| 30~60초 | ±350 |
| 60초 이상 | ±500 (상한) |

> 현행 `matchmaking.py`에 `SCORE_RANGE_MAX = 500`과 대기 시간 기반 확장 로직이
> 이미 있다 (`server/app/ws/matchmaking.py:41,164`). **로직을 재사용**하고
> 기준을 점수(`score`)에서 MMR로 바꾼다.

`trio`는 3명이 모두 범위 안에 들어와야 성사된다. 성사 난이도가 높으므로
**상한을 ±700로 완화**한다. 구체적 값은 운영 데이터로 조정한다.

### 매칭 성사

```json
{ "type": "matched",
  "payload": {
    "game_id": "8f14e45f-ceea-467a-9a0b-1c2d3e4f5a6b",
    "mode": "duel",
    "my_seat_no": 1,
    "players": [
      { "seat_no": 1, "nickname": "미로장인", "mmr": 1042 },
      { "seat_no": 2, "nickname": "길잃은양", "mmr": 998 }
    ],
    "ready_deadline_sec": 10
  } }
```

양측이 `ready`를 보내야 시작한다. 기한 내 응답하지 않으면 매칭이 취소되고
**응답한 쪽만 큐로 복귀**한다.

### 큐 이탈

```json
{ "type": "leave_queue", "seq": 2 }
```

## §4 친구 대전 방

MMR에 반영되지 않는 비랭크 경기다.

### 방 생성

```json
{ "type": "create_room", "seq": 1, "payload": { "mode": "trio" } }
```

```json
{ "type": "room_created", "ack_seq": 1,
  "payload": { "room_code": "K7QX2M", "mode": "trio", "capacity": 3,
               "players": [ { "seat_no": 1, "nickname": "미로장인", "is_host": true } ] } }
```

방 코드는 6자다 (현행 `room_manager.py:76` `ROOM_CODE_LENGTH = 6`).

### 방 참가

```json
{ "type": "join_room", "seq": 1, "payload": { "room_code": "K7QX2M" } }
```

참가자에게 `room_joined`, 기존 인원에게 `player_joined`가 간다.
정원 초과 시 `room_full`.

### 준비와 시작

각자 `ready` → 서로에게 `player_ready` → 전원 준비되면 `game_start`.
호스트가 이탈하면 방이 해산되고 남은 인원에게 `player_left` 후 방이 닫힌다.

> **랭크와 친구 대전의 차이:** 친구 대전은 `is_ranked=false`로 기록되며
> MMR이 변하지 않는다. 결과는 `game_sessions`에 남는다 (전적 표시용).

## §5 게임 진행

### 좌표계

`PLATFORM_ARCHITECTURE.md`의 Quoridor 좌표 규약을 유지한다 — 보드 9×9 (0-8),
벽은 교차점 (0-7). 기존 엔진(`app/games/maze/core/`)이 이 규약으로 구현되어 있다.

**단, 1인칭 뷰에서도 서버 프로토콜은 그리드 좌표를 쓴다.** 1인칭 렌더링은
클라이언트의 표현 방식이며, 서버는 논리 좌표만 다룬다. 시야각·카메라 방향을
서버가 알아야 하는 이유는 §6에 있다.

### 이동

```json
{ "type": "move", "seq": 10,
  "payload": { "row": 7, "col": 4, "facing": "north" } }
```

| 필드 | 설명 |
| :--- | :--- |
| `row`, `col` | 목표 칸 |
| `facing` | 이동 후 바라보는 방향 — `north` \| `south` \| `east` \| `west` |

`facing`이 필요한 이유: **시야가 방향에 의존**한다(§6). 서버가 시야를 계산하려면
플레이어가 어디를 보는지 알아야 한다.

> **판단 필요:** 이동 없이 방향만 바꾸는 행동(`turn`)을 턴으로 취급할지.
> 턴을 소모하지 않는 자유 회전이라면 별도 메시지가 필요하고, 그때마다 시야
> 패킷이 갱신되어 트래픽이 늘어난다. 회전 빈도를 고려해 결정한다.

### 벽 설치

```json
{ "type": "wall", "seq": 11,
  "payload": { "row": 3, "col": 5, "orientation": "horizontal" } }
```

검증은 §7.

### 상태 갱신

서버는 행동이 수락될 때마다 **각 플레이어에게 서로 다른** `game_state`를 보낸다.
스키마는 §6에 있다.

### 턴 전환

```json
{ "type": "turn_change",
  "payload": { "current_seat_no": 2, "turn_count": 13, "deadline_at": "2026-10-01T09:30:30Z" } }
```

## §6 시야 필터링 (Fog of War)

> **이 절이 이 문서의 핵심이다.** §4.1의 안티치트 요구가 여기서 결정된다.

### 원칙

**서버는 플레이어별로 시야를 계산하고, 플레이어마다 내용이 다른 상태 패킷을
전송한다.** 같은 게임의 두 플레이어가 동시에 받는 `game_state`는 내용이 다르다.

§4.1의 문구를 그대로 구현한다 — "백엔드(FastAPI + Redis)에서 플레이어 좌표·시선
방향 기준 Raycasting을 연산한 후, **시야에 노출된 벽과 상대 말 좌표만** WebSocket
패킷으로 전송".

### MUST NOT — 이 방식들은 요구를 무효화한다

| 금지 | 이유 |
| :--- | :--- |
| 전체 맵·전체 벽 목록을 보낸 뒤 클라이언트가 가리기 | 패킷을 감청하면 맵핵이 그대로 가능하다. 안티치트 목적이 완전히 사라진다 |
| 시야 밖 상대 말의 정확 좌표를 어떤 필드로든 포함 | 위와 동일 |
| 클라이언트가 계산한 시야를 받아 신뢰 | 조작 가능하다. 서버가 독립적으로 계산한다 |
| 전체 상태를 보내고 "클라이언트가 안 보여주면 된다"고 가정 | 클라이언트는 신뢰 경계 밖이다 |

### 상태 패킷 스키마

```json
{ "type": "game_state",
  "payload": {
    "game_id": "8f14e45f-…",
    "turn_count": 13,
    "current_seat_no": 2,
    "me": {
      "seat_no": 1,
      "position": { "row": 7, "col": 4 },
      "facing": "north",
      "walls_remaining": 8,
      "goal_row": 0
    },
    "visible_walls": [
      { "row": 3, "col": 5, "orientation": "horizontal" }
    ],
    "visible_players": [
      { "seat_no": 2, "position": { "row": 5, "col": 4 } }
    ],
    "others": [
      { "seat_no": 2, "nickname": "길잃은양", "walls_remaining": 9, "visible": true },
      { "seat_no": 3, "nickname": "돌쇠", "walls_remaining": 10, "visible": false }
    ]
  } }
```

필드별 공개 범위:

| 필드 | 내용 | 시야 밖일 때 |
| :--- | :--- | :--- |
| `me` | 내 정보 전체 | — (항상 전체) |
| `visible_walls` | **시야 내 벽만** | 배열에서 제외 |
| `visible_players` | **시야 내 상대 말 좌표만** | 배열에서 제외 |
| `others[].walls_remaining` | 상대의 남은 벽 개수 | **공개한다** (아래 근거) |
| `others[].position` | — | **필드 자체가 없다** |

> 전체 벽 목록 필드는 **존재하지 않는다.** `visible_walls`가 유일한 벽 정보원이다.

### 시야 밖 상대 정보 — 명시적 결정

암묵적으로 남기지 않고 항목별로 정한다.

| 정보 | 공개 | 근거 |
| :--- | :--- | :--- |
| 정확 좌표 | **비공개** | 맵핵의 핵심. 어떤 형태로도 주지 않는다 |
| 대략 방향·거리 힌트 | **비공개** | 삼각측량으로 좌표를 역산할 수 있다. 여러 턴에 걸쳐 수집하면 정확도가 올라간다 |
| 남은 벽 개수 | **공개** | 전략 판단의 기본 정보이고 위치를 드러내지 않는다. 벽을 설치할 때마다 1 줄어드는 것은 어차피 관측 가능하다 |
| 목표까지 남은 거리 | **비공개** | 위치를 강하게 시사한다 |
| 생존·항복 여부 | **공개** | 게임 진행에 필수 (3인전에서 한 명이 빠지면 알아야 한다) |
| 턴을 썼다는 사실 | **공개** | `turn_change`로 이미 드러난다 |

> **판단 필요:** 상대가 벽을 설치했을 때, 그 벽이 내 시야 밖이면 "누군가 벽을
> 설치했다"는 사실만 알리고 위치는 감춘다 — 이 이벤트를 보낼지 여부.
> 보내면 벽 개수 변화로 어차피 추론되므로 일관성이 있으나,
> 보내지 않으면 정보량이 더 적다. 게임 밸런스 문제이므로 플레이 테스트로 결정한다.

### 시야 계산

- 서버가 `position` + `facing`으로 Raycasting을 수행한다
- 시야각(FOV)과 최대 사거리는 **서버 설정값**이다. 클라이언트가 보내지 않는다
  — 보내면 조작된다
- 벽이 시선을 차단한다. 벽 뒤의 칸·말·벽은 보이지 않는다

> **판단 필요:** FOV 각도와 사거리의 구체적 값. 게임 난이도와 직결되므로
> 플레이 테스트로 정한다. 설계상으로는 "서버 설정값"이라는 점만 확정한다.

> **판단 필요:** 한 번 본 벽을 기억할지(탐사한 지도가 누적되는지), 시야를
> 벗어나면 잊는지. 누적이면 서버가 플레이어별 "발견한 벽" 집합을 Redis에
> 보관해야 하고 패킷에 `discovered_walls`가 추가된다. 게임성에 큰 영향을 주는
> 결정이다.

### 성능

플레이어 수 × 행동 수마다 Raycasting이 돌아간다. 9×9 보드에서는 연산량이 작지만,
**상태 패킷을 플레이어별로 따로 만들어야** 하므로 브로드캐스트를 재사용할 수 없다.
`connection_manager`의 일괄 전송(`broadcast`)을 그대로 쓸 수 없고,
**플레이어별 개별 전송**이 필요하다.

> M3 구현 시 주의: 현행 `ConnectionManager`에 게임 단위 브로드캐스트가 있다
> (`server/app/ws/connection_manager.py:36` `_game_players`). Fog of War에서는
> 같은 페이로드를 여러 명에게 보내는 경로를 **쓰지 않는다.**

## §7 벽 설치 검증

§4.1은 "벽 설치 시 **모든 플레이어**가 목표 지점까지 도달할 수 있는 경로가 최소
1개 이상 존재하는지 즉시 검증"을 요구한다.

검증 순서 (서버에서만 수행):

1. 내 턴인가 → 아니면 `not_your_turn`
2. 남은 벽이 있는가 → 없으면 `no_walls_remaining`
3. 좌표가 유효 범위(0-7)인가, 기존 벽과 겹치거나 교차하지 않는가
   → `invalid_wall_position`
4. **가상으로 설치한 뒤 모든 플레이어의 목표 도달 경로를 확인**
   → 한 명이라도 막히면 `wall_blocks_path`

3인전에서는 3명 전부를 확인한다. 2인전 로직을 그대로 쓰면 3번째 플레이어가
갇힐 수 있다.

> **재사용:** `server/app/games/maze/core/pathfinder.py`의
> `can_place_wall_safely()`와 `has_path_to_goal()`가 이미 이 검증을 한다.
> 3인 대응 여부를 확인하고 필요하면 확장한다.
> 새로 구현하지 않는다.

### 유효 수 목록을 서버가 주지 않는다

구 API에는 `GET /games/{id}/valid-moves`가 있었다. **이 설계에서는 제공하지
않는다** — 유효한 벽 위치 목록은 기존 벽 배치를 드러내므로 Fog of War가 무너진다.

클라이언트는 **자신의 시야 내 정보로만** 후보를 계산해 표시한다. 시야 밖 사정
때문에 거절될 수 있으며(`wall_blocks_path` 등), 그 거절 자체가 정보를 주지
않도록 에러 메시지에 위치 정보를 담지 않는다.

> **주의:** 거절 응답이 정보 누출 경로가 될 수 있다. 예컨대 특정 좌표에서만
> `wall_blocks_path`가 나온다면 그 근처 벽 배치를 추론할 수 있다.
> 완전 차단은 불가능하나, 에러에 **좌표나 경로를 절대 포함하지 않는다**.

## §8 턴 타이머

| 항목 | 값 |
| :--- | :--- |
| 턴 제한 | 30초 |
| 연속 시간 초과 | 2회 누적 시 패배 처리 |

타이머는 **Redis에 보관**한다(§2.2). 워커가 여러 개일 때 특정 워커의 메모리에
두면 그 워커가 죽으면 타이머가 사라진다.

시간 초과 시:

```json
{ "type": "turn_timeout",
  "payload": { "seat_no": 1, "consecutive": 1, "auto_action": "pass" } }
```

> **판단 필요:** 시간 초과 시 자동 행동. 선택지는 (a) 턴 넘김(pass),
> (b) 목표 방향으로 자동 1칸 이동, (c) 즉시 패배. 미로에서 pass는 상대에게
> 일방적으로 유리하고, 자동 이동은 원치 않는 위치로 끌려갈 수 있다.
> 게임 밸런스 문제다.

> M3 의존: 타이머 만료 감지 방식. Redis 키 TTL + 만료 이벤트, 또는 주기 폴링.
> 스케줄러 존속 여부와 연관된다 ([`../../ROADMAP.md`](../../ROADMAP.md) TODO).

## §9 재접속·이탈·항복

### 재접속

연결이 끊긴 뒤 다시 접속하면 `connected` 메시지에 `reconnect`가 포함된다(§2).
클라이언트는 이어서 `game_state`를 받아 현재 상황을 복원한다.

- 유예 시간: **60초.** 그 안에 재접속하면 게임이 유지된다
- 유예 중 상대에게 `player_left`가 가고 `reconnecting: true`로 표시된다
- 유예 초과 시 이탈자는 패배 처리되고 나머지에게 `game_end`가 간다

> **재접속 시 시야:** 서버가 현재 위치·방향으로 시야를 다시 계산해 보낸다.
> 끊긴 동안 상대가 움직인 경과는 **전달하지 않는다** — 그 이력을 주면
> 시야 밖에서 일어난 일이 드러난다.

### 이탈

```json
{ "type": "leave_room", "seq": 5 }
```

게임 시작 전에만 유효하다. 시작 후 이탈은 항복으로 처리한다.

### 항복

```json
{ "type": "surrender", "seq": 20 }
```

즉시 패배 처리. 3인전에서는 항복자만 탈락하고 남은 2명이 계속한다(§11).

## §10 종료와 MMR 반영

```json
{ "type": "game_end",
  "payload": {
    "game_id": "8f14e45f-…",
    "reason": "goal_reached",
    "results": [
      { "seat_no": 1, "nickname": "미로장인", "rank": 1, "result": "win",
        "mmr_before": 1042, "mmr_after": 1058, "mmr_delta": 16 },
      { "seat_no": 2, "nickname": "길잃은양", "rank": 2, "result": "lose",

  } }
```

| `reason` | 의미 |
| :--- | :--- |
| `goal_reached` | 목표 행 도달 |
| `surrender` | 항복 |
| `disconnect_timeout` | 재접속 유예 초과 |
| `turn_timeout` | 시간 초과 누적 |

### MMR은 서버가 계산한다

산정식은 [`../platform.md`](../platform.md) §4.2를 따른다 (Elo, 초기 1000,
배치 10판 K=40 / 이후 K=24).

> **MUST:** 클라이언트는 결과를 **통보받을 뿐**이다. 승패를 주장하는 메시지
> 타입은 존재하지 않는다 (§3.3 원칙 2).

친구 대전(`is_ranked=false`)은 `mmr_*` 필드가 `null`이다.

### 종료 후 전체 맵 공개

`full_board`는 **게임이 끝난 뒤에만** 전체 벽 배치를 담는다. 경기 중에는 어떤
메시지에도 전체 맵이 포함되지 않는다.

> **판단 필요:** 종료 후 전체 공개를 할지. 복기에는 유용하나, 연속 대전에서
> 같은 상대와 다시 만날 때 상대의 벽 설치 성향 정보가 누적된다.
> 리플레이 기능 존속 여부와 함께 결정한다
> ([`../platform.md`](../platform.md) §6).

## §11 1:1:1 전용 규칙

2인 규칙에서 자동으로 유도되지 않는 것들이다. 현행 구현은 1:1 전용이며
`matchmaking.py:145`가 `len(self._queue) < 2`로 하드코딩되어 있다.

### 좌석과 목표

| `seat_no` | 시작 위치 | 목표 |
| :--- | :--- | :--- |
| 1 | (8, 4) | row 0 |
| 2 | (0, 4) | row 8 |
| 3 | (4, 0) | col 8 |

> 3번 좌석의 목표가 **행이 아니라 열**이다. 기존 엔진의 `goal_row` 단일 개념으로
> 표현할 수 없다 — `Player.goal_row`(`app/games/maze/core/player.py`)를
> 목표 **축 + 값**으로 일반화해야 한다.
>
> **판단 필요:** 3인 배치의 대안으로 (4,0)·(4,8)·(0,4) 같은 대칭 구성도 가능하다.
> 공정성(목표까지 최단 거리가 동일한지)을 계산해 확정한다.

### 벽 배분

2인전은 각 10개다. 3인전에서 각 10개면 총 30개로 보드가 과포화된다.

> **판단 필요:** 3인전 벽 개수. 총량을 2인전과 맞추려면 각 7개(총 21개)가
> 근사치다. 플레이 테스트 필요.

### 턴 순서

`seat_no` 오름차순 순환. 탈락자는 건너뛴다.

### 승패와 순위

- 먼저 목표에 도달한 플레이어가 **1위이고 게임이 끝난다**
- 나머지 2명의 **2·3위를 가려야 한다.** 목표까지 남은 최단 거리가 짧은 쪽이 2위
- 거리가 같으면 사용한 턴 수가 적은 쪽이 2위
- 그래도 같으면 공동 2위 (MMR 변동 동일)

> 대안으로 "1위가 나오면 나머지는 모두 패배(동순위)"가 있다. 단순하지만
> 2·3위 구분이 없어 MMR이 거칠어진다. 위 방식을 권장한다.

### 탈락 처리

- 항복·이탈자는 **즉시 최하위**로 확정하고 게임은 남은 2명으로 계속한다
- 2명이 탈락하면 남은 1명이 1위로 즉시 종료한다

### 3자 MMR 반영 — 쌍별 분해

3인 결과를 **3개의 쌍별 대결로 분해**하고 각 쌍에 §4.2의 Elo를 적용한 뒤,
한 플레이어의 변동량은 **그가 참여한 2개 쌍의 변동을 합산하고 2로 나눈다**.

```
쌍: (1위,2위) (1위,3위) (2위,3위)
각 쌍에서 상위가 승(S=1), 하위가 패(S=0)
ΔR_x = ( Δ_쌍1 + Δ_쌍2 ) / 2        # x가 참여한 두 쌍
```

2로 나누는 이유: 나누지 않으면 3인전 1경기의 변동폭이 2인전의 2배가 되어
3인전만 반복하는 편법이 생긴다.

> 공동 순위는 해당 쌍을 무승부(S=0.5)로 처리한다.
