# 개발 환경 구성

> `docs/docker-guide.md` 는 이 문서로 통합되었습니다.

## 원칙 — 모든 것을 컨테이너에서

의존성(Python, PostgreSQL, Redis)은 **로컬에 설치하지 않습니다.** 실행·테스트·빌드는 전부 Docker Compose로 수행합니다.

**단 하나의 예외:** Flutter 앱을 에뮬레이터·실기기에서 띄우는 것(`flutter run`, hot reload)과 코드 생성(`build_runner`)은 로컬 Flutter SDK로 합니다. 컨테이너는 USB 패스스루와 GUI를 지원하지 않기 때문입니다.

| 작업 | 실행 위치 |
| :--- | :--- |
| 서버 실행 / API 테스트 | 컨테이너 |
| pytest (서버 + 게임 엔진) | 컨테이너 |
| flutter analyze / flutter test | 컨테이너 (CI와 동일 환경) |
| 웹 릴리스 빌드 | 컨테이너 |
| Android AAB/APK 빌드 | 컨테이너 (`release` profile) |
| **flutter run (에뮬레이터/실기기, hot reload)** | **로컬** |
| **dart run build_runner (drift/riverpod 코드 생성)** | **로컬** |

## 전제 조건

| 도구 | 버전 | 용도 |
| :--- | :--- | :--- |
| Docker Desktop | 최신 | 서버·DB·Redis·테스트·빌드 전부 |
| Flutter SDK | **`.flutter-version` 과 동일 버전** (현재 3.47.5 / Dart 3.13.4) | 로컬 `flutter run`, 코드 생성 |

### Flutter 버전 단일 기준 — `.flutter-version`

로컬·CI·컨테이너가 **동일한 Flutter 바이너리**를 씁니다. 기준은 저장소 루트 `.flutter-version` 하나입니다.

```bash
cat .flutter-version                        # 3.47.5
bash scripts/check-flutter-version.sh       # 기준 / Dockerfile / 로컬 SDK 3자 비교
```

| 경로 | 버전 출처 |
| :--- | :--- |
| 로컬 | 설치된 Flutter SDK |
| 컨테이너 | `client/Dockerfile` 이 Google 공식 아카이브에서 설치 (sha256 검증) |
| CI | `.flutter-version` 을 읽어 `flutter-action` 에 전달 |

CI의 `version-guard` 잡이 세 값의 불일치를 **가장 먼저 빌드 실패로** 잡습니다.

> 제3자 이미지(`ghcr.io/cirruslabs/flutter`)는 쓰지 않습니다. Flutter 릴리스를 여러 마이너 버전 뒤늦게 따라오며, 현재 최신(3.44.0 / Dart 3.12.0)이 `pubspec.yaml` 의 `sdk: ^3.13.4` 제약을 만족하지 못해 `flutter pub get` 자체가 실패합니다.

> Dart 3.13 미만에서는 `drift_dev`, `riverpod_generator`, `riverpod_lint` 가 `analyzer`/`meta` 버전 충돌로 해석되지 않습니다.

**버전을 올릴 때**는 반드시 순서를 지키세요: 로컬 `flutter upgrade` → `.flutter-version` 갱신 → `client/Dockerfile` 의 `ARG FLUTTER_VERSION` 갱신 → `docker-compose.yml` 기본값 갱신 → 가드 확인 → `flutter pub get`(lockfile) → 컨테이너 `--no-cache` 재빌드.

Android SDK는 **로컬에 설치하지 않아도 됩니다.** 컨테이너 `android` 스테이지에 JDK 17과 함께 포함됩니다. 단 로컬에서 `flutter run -d <android device>` 를 하려면 Android SDK와 Gradle 호환 JDK가 필요합니다.

## 버전 고정 — 자동 변경은 일어나지 않는다

모든 버전이 고정되어 있고, 고정이 풀리면 CI가 실패한다.

```bash
bash scripts/check-version-pinning.sh     # 7개 항목 검사 (CI version-guard 잡)
```

| 대상 | 고정 방식 |
| :--- | :--- |
| 서버 직접 의존성 | `server/pyproject.toml` 전부 `==` |
| 서버 **전이** 의존성 | `server/uv.lock` — URL + SHA256. `uv sync --frozen` 으로 설치 |
| `uv` 자체 | `server/Dockerfile` 의 `ARG UV_VERSION` |
| 컨테이너 이미지 | `name:tag@sha256:<digest>` — 태그는 가독성용, 실제로 받는 것은 다이제스트 |
| Flutter SDK | `.flutter-version` |
| Flutter 패키지 | `client/pubspec.yaml` 정확 버전 (캐럿 금지) + `pubspec.lock` |
| Dart SDK 제약 | `client/pubspec.yaml` 의 `sdk:` 정확 버전 — **제약을 낮춰 낡은 툴체인을 통과시키지 않는다.** 이미지를 프로젝트에 맞춘다 |
| 린트 플러그인 | `client/analysis_options.yaml` 의 `plugins:` 정확 버전 |
| Android SDK | `compileSdk`/`minSdk`/`targetSdk`/`ndkVersion` 명시 (`flutter.*` 위임 금지) |
| GitHub Actions | 40자 커밋 SHA |

### 서버 의존성을 바꿀 때

`pyproject.toml` 을 수정한 뒤 lock 을 재생성한다. **로컬에 `uv` 를 설치하지 않는다.**

```bash
docker run --rm -v "$PWD/server:/w" -w /w   python:3.13-slim@sha256:7c61056e61ac89e852de05f3dc6fa51a6dd2181797bceed46aa725dd7cb2cd3b   sh -c 'pip install -q uv==0.12.21 && uv lock --no-progress'

docker compose build server-test
docker compose run --rm server-test pytest -q
```

`uv sync --frozen` 은 lock 을 재해석하지 않는다. `pyproject.toml` 과 어긋나면
설치가 **실패한다** — 의도적이다.

### 베이스 이미지 다이제스트를 갱신할 때

업스트림이 보안 패치를 재발행하면 다이제스트가 바뀐다.

```bash
bash scripts/update-image-digests.sh           # 점검만 (차이 있으면 exit 1)
bash scripts/update-image-digests.sh --write    # 갱신
docker compose build && docker compose run --rm server-test pytest -q
```

CI 의 필수 게이트로 두지 않았다 — 업스트림 재발행은 정상적인 일이고, 그때
의도적으로 갱신하면 된다.

### 클라이언트 의존성을 바꿀 때

```bash
cd client
# pubspec.yaml 의 숫자를 직접 바꾼다. flutter pub upgrade 는 쓰지 않는다
flutter pub get && flutter analyze && flutter test
```

`flutter pub upgrade` 는 정확 고정을 무너뜨린다.

### 가드 스크립트 3종

| 스크립트 | 검사 |
| :--- | :--- |
| `scripts/check-version-pinning.sh` | 버전 고정 규율 7항목 |
| `scripts/check-legacy-paths.sh` | 폐기된 경로(`backend_fastapi/` 등) 부활 |
| `scripts/check-flutter-version.sh` | `.flutter-version` ↔ Dockerfile ↔ 로컬 SDK |
| `scripts/update-image-digests.sh` | 이미지 다이제스트 최신성 (갱신 도구) |
| `scripts/check-proxy-config.sh` | 프록시 신뢰 경계·토큰 로그(M4-1) — CI `version-guard` 에서도 실행 |

앞의 3종은 CI `version-guard` 잡에서 실행되며, 다른 잡이 `needs` 로 참조하므로
위반 시 빌드 전에 차단된다.

## 서비스 구성

### 기본 서비스 (`docker compose up`)

| 서비스 | 이미지 / 타겟 | 포트 | 역할 |
| :--- | :--- | :--- | :--- |
| `db` | postgres:16-alpine | 5432 | 유저 계정, 멀티 전적/MMR, 낱말 사전, 퍼즐 편지 메타데이터 |
| `redis` | redis:8-alpine | 6379 | 매치메이킹 큐, 실시간 방 상태, 턴 타이머, Pub/Sub |
| `server` | `server/Dockerfile` target `dev` | 8000 | FastAPI (소스 볼륨 마운트 + `--reload`) |

### 헬스 체크 응답

```json
{
  "status": "healthy",
  "environment": "local",
  "dependencies": {
    "database": { "status": "ok" },
    "redis": { "status": "ok" }
  },
  "rate_limit": { "enabled": true, "per_minute": 60 }
}
```

**DB/Redis 가 `unavailable` 이어도 HTTP 200 을 반환한다.** graceful degradation
설계상 서버 자체는 정상이며, 의존 서비스 장애는 `dependencies` 로 구분한다.
컨테이너 `HEALTHCHECK` 와 배포 플랫폼의 준비성 검사가 이 응답을 쓴다.

기동 로그에도 한 줄로 요약된다.

```
app.main: Startup complete — db=up redis=up rate_limit=on
```

### profile 서비스

| 명령 | profile | 역할 |
| :--- | :--- | :--- |
| `docker compose run --rm server-test` | `test` | pytest (서버 API + 게임 엔진). `gamemoa_test` DB 사용 |
| `docker compose run --rm client-test` | `client` | `flutter pub get && analyze && test` |
| `docker compose run --rm client-web` | `client` | 웹 릴리스 빌드 |
| `docker compose --profile release run --rm android-builder` | `release` | Android AAB 빌드 |

> `run` 은 해당 서비스의 profile을 자동으로 활성화하므로 `--profile test` 를 따로 붙이지 않아도 됩니다. `up` 으로 띄울 때만 `--profile` 이 필요합니다.

### 이미지 스테이지

**`server/Dockerfile`**

| 스테이지 | 용도 |
| :--- | :--- |
| `deps` | 런타임 의존성만 (venv `/opt/venv`) |
| `deps-dev` | `deps` + pytest |
| `dev` | 소스 볼륨 마운트 + `uvicorn --reload` + psql |
| `test` | pytest 실행 전용 |
| `prod` | **non-root**, reload 없음, 소스를 이미지에 포함, HEALTHCHECK 포함 |

**`client/Dockerfile`**

| 스테이지 | 용도 |
| :--- | :--- |
| `flutter-sdk` | 공식 아카이브에서 SDK 취득 + sha256 검증 (최종 이미지에 빌드 도구를 남기지 않음) |
| `toolchain` | analyze / test / codegen 용 (**Android SDK 없음**) |
| `web` | 웹 릴리스 빌드 |
| `android` | Android AAB/APK 빌드 (+JDK 17, +Android SDK) |

> `toolchain` 이미지는 약 5GB입니다. Android SDK는 `android` 스테이지에만 들어가므로 analyze/test만 할 때는 받지 않습니다.
>
> 이 이미지는 배포되지 않는 빌드 전용이라 **root로 동작**합니다 (바인드 마운트·named volume 소유권 충돌 회피). 서버 `prod` 이미지는 반대로 non-root입니다.

## 테스트

```bash
# 전체
docker compose run --rm server-test

# 게임 엔진만 (DB 불필요, 빠름)
docker compose run --rm server-test pytest tests/games -q

# 특정 파일 / 키워드
docker compose run --rm server-test pytest tests/api/test_ranking.py -v
docker compose run --rm server-test pytest -k wall -q

# Flutter
docker compose run --rm client-test
```

테스트는 `gamemoa_test` DB를 사용합니다. `conftest.py` 가 매 테스트마다 `create_all` / `drop_all` 을 수행하므로 개발 DB와 반드시 분리되어야 합니다. 이 DB는 `infra/postgres/init/01-create-test-db.sql` 로 생성되며, **해당 스크립트는 데이터 볼륨이 비어 있을 때만 실행**됩니다. 기존 볼륨을 쓰고 있었다면:

```bash
docker compose down -v && docker compose up -d
```

## 프로덕션 이미지

```bash
# 로컬 검증 (prod 오버레이: non-root, reload 없음, DB/Redis 포트 미노출)
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# 배포용 이미지 단독 빌드
docker build --target prod -t gamemoa-server ./server
```

실제 배포처(Fly.io / AWS ECS)에서는 `db`·`redis` 를 관리형 서비스로 대체하고 `server` 이미지만 올립니다. Stateful WebSocket 연결을 유지해야 하므로 컨테이너 기반 오토스케일링을 사용합니다.

## 환경 변수

`.env.example` 을 `.env` 로 복사해 사용합니다. `.env` 는 커밋하지 않습니다.

| 변수 | 기본값 | 설명 |
| :--- | :--- | :--- |
| `POSTGRES_DB` | `gamemoa` | 개발용 DB |
| `POSTGRES_TEST_DB` | `gamemoa_test` | 테스트용 DB |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | `postgres` / — | DB 인증 |
| `POSTGRES_PORT` / `REDIS_PORT` / `SERVER_PORT` | `5432` / `6379` / `8000` | 호스트 노출 포트 |
| `DB_ENABLED` | `true` | `false` 면 메모리 전용 모드 |
| `REDIS_URL` | `redis://redis:6379/0` | 앱 상태용 논리 DB |
| `PUBSUB_NAMESPACE` | `app` | Pub/Sub 채널 접두어. 채널은 논리 DB 로 격리되지 않으므로 테스트는 `test`(server-test 가 설정, 픽스처가 강제). production 에서 `test` 는 기동 거부 |
| `REDIS_PASSWORD` | — (**필수**) | Redis `requirepass`. 비어 있으면 compose 가 기동을 거부한다. CI 는 실행마다 무작위 값을 만든다 |
| `REDIS_ENABLED` | `true` | `false` 면 리미터가 메모리로 강등된다 |
| `REDIS_LIMITER_DB` | `2` | 레이트 리미터 전용 논리 DB |
| `RATE_LIMIT_ENABLED` | `true` | |
| `RATE_LIMIT_PER_MINUTE` | `60` | 클라이언트 IP 당 분당 요청 수 |
| `ENVIRONMENT` | `local` | `local` \| `ci` \| `production` |

**환경변수는 `server/app/core/config.py` 한 곳에서만 읽는다.** 코드에 `os.getenv`
를 흩뿌리지 않는다 — 기본값이 분산되고 어떤 값이 실제로 쓰이는지 추적할 수 없게 된다.

### Redis 논리 DB 분리

| DB | 용도 |
| :--- | :--- |
| 0 | 앱 상태 (매치메이킹 큐 / 방 / 세션) |
| 1 | 테스트 전용 |
| 2 | 레이트 리미터 카운터 |

리미터 카운터가 앱 상태와 같은 DB 를 쓰면 키 스캔·`FLUSHDB` 가 서로를 건드린다.

카카오 로그인 키, JWT 시크릿, Cloudflare R2 자격증명은 구현 단계에서 채웁니다 (`.env.example` 하단 주석 참조).

## 트러블슈팅

### Docker Desktop 미실행
```
error during connect: ... open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.
```
→ Docker Desktop을 시작하세요.

### 포트 충돌
```bash
netstat -ano | findstr :8000
netstat -ano | findstr :5432
```
→ 또는 `.env` 에서 `SERVER_PORT` / `POSTGRES_PORT` 를 바꿉니다.

### `gamemoa_test` DB 없음 (테스트 실패)
init 스크립트는 빈 볼륨에서만 실행됩니다. `docker compose down -v && docker compose up -d` 로 초기화하세요.

### DB 연결 실패
서버는 graceful degradation으로 **메모리 전용 모드**로 계속 동작합니다. 로그에 `Server will run in memory-only mode` 가 보이면 DB에 붙지 못한 상태입니다. `docker compose logs db` 로 확인하세요.

### hot reload 미작동
```bash
docker compose restart server
```

### 로컬 Android 빌드에서 Java/Gradle 버전 충돌
Gradle은 지원 JDK 범위가 좁습니다(현재 래퍼 8.14 → Java 17 이상 25 미만). 로컬 JDK가 범위를 벗어나면:
```bash
flutter config --jdk-dir=<호환 JDK 경로>
```
→ 또는 컨테이너 빌드(`android-builder`)를 사용하세요. JDK 17이 고정되어 로컬 JDK와 무관합니다.

### Flutter 의존성 해석 실패 (`analyzer` / `meta` 충돌)
로컬 Flutter가 `.flutter-version` 보다 낮은 경우입니다. `bash scripts/check-flutter-version.sh` 로 확인하고 `flutter upgrade` 하세요.

### 컨테이너 Flutter 버전이 로컬과 다름

## 리버스 프록시·네트워크 (M4-1)

**호스트 :8000 은 Caddy(`infra/caddy/Caddyfile`)다.** server 컨테이너는 호스트 포트를 열지 않는다 — 로컬·CI·배포가 같은 경로
(Caddy → uvicorn)를 탄다. 클라이언트 API Base URL(위 표)은 그대로다.

| 항목 | 값 |
| :--- | :--- |
| 네트워크 | 고정 서브넷 `GAMEMOA_SUBNET`(기본 `10.231.0.0/24` — Docker 기본 주소 풀 밖), 동적 할당은 `GAMEMOA_DYNAMIC_RANGE`(위쪽 절반) |
| proxy 주소 | `GAMEMOA_PROXY_IP`(기본 `.10`) — server 의 `FORWARDED_ALLOW_IPS` 가 이 주소만 믿는다 |
| 엣지 신뢰 | `CADDY_TRUSTED_PROXIES` — 로컬·CI 는 기본(루프백), **운영 오버레이는 필수** |
| 운영 이미지 | prod 스테이지 기본 `ENVIRONMENT=production`(오리진 fail-closed·JWT 키 32자·pubsub `test` 금지) |

호스트의 다른 네트워크(VPN 등)와 겹치면 위 세 값을 `.env` 에서 함께 바꾼다. 네트워크 설정이 바뀌면 `docker compose down` 후 다시 올린다.

```bash
bash scripts/e2e-proxy.sh            # 프록시 경유 E2E — 운영 이미지·운영 설정(CI proxy-e2e 와 같은 스크립트)
docker compose up -d --build         # 그 뒤 개발로 복귀 — 반드시 --build(같은 이미지 이름이라 prod 이미지를 재사용한다)
bash scripts/check-proxy-config.sh   # 신뢰 경계·토큰 로그 가드
```

## 폐기된 레거시 경로 — 3중 차단 상세

`backend_fastapi/ → server/`, `frontend_flutter/ → client/`, `games/ → server/app/games/maze/` (2026-09-30 구조 재편으로 영구 폐기).
`origin/develop`·`origin/dev-test` 는 이 경로들에 파일을 가진 히스토리다.

1. **ancestry 차단** — `feature/platform-restructure` 에서 두 원격 브랜치를 `git merge -s ours` 로 머지해 조상으로 편입했다. 이후 `git merge develop` 은 no-op 이다
2. **커밋 차단** — `.githooks/pre-commit` 이 레거시 경로 추적을 감지하면 커밋을 거부한다(계획서 규약도 함께 검사). 클론 후 1회: `git config core.hooksPath .githooks`
3. **CI 차단** — `version-guard` 잡의 `scripts/check-legacy-paths.sh`

원격 히스토리에서 코드를 가져올 때는 머지하지 말고 내용만: `git show origin/develop:<구 경로> > <새 경로>`
